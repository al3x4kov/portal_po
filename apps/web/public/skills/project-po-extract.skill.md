# /extract — Извлечение ФТ/НФТ из документации

Читает **предоставленный пользователем источник** (веб-документация по ссылке, локальный
PDF или локальный Word), **вычленяет** из него функциональные (ФТ) и нефункциональные (НФТ)
требования, складывает их в структурированный Markdown-файл, максимально удобный для
**MCP-сервера** `project_po` (`apps/mcp/dist/main.js`), и предлагает по этому файлу создать
новый проект в портале и наполнить его ФТ/НФТ.

Отличие от `/po` (senior-po): `/po` **генерирует** требования из знания о продукте (может
опираться на веб-поиск и реальную функциональность). `/extract` — **строго извлекает** только
то, что действительно есть в переданном источнике, и ничего сверх этого.

## Usage

```
/extract                                   # спросить источник и целевой проект
/extract <URL>                             # извлечь из веб-документации по ссылке
/extract <путь/к/файлу.pdf>                # извлечь из локального PDF
/extract <путь/к/файлу.docx>               # извлечь из локального Word (.docx/.doc)
/extract <источник> --project <id>         # сразу указать целевой проект портала
/extract <источник> --dry                  # только MD-черновик, без записи через MCP
/extract <источник> --repo <путь>          # путь к репозиторию project_po
```

Язык извлечённых требований — **русский** (как в источнике; при иноязычном источнике —
аккуратный перевод формулировок без добавления смысла). Код/идентификаторы — английские.

## ⛔ Золотое правило: никакого домысливания

Это главное требование к скиллу. Нарушать нельзя.

- Используется **только** тот контекст, который дал пользователь (переданный источник), и
  **не более**. Никакого веб-поиска «для полноты», никакого знания о продукте «из головы»,
  никаких «типичных для таких систем» требований.
- **Каждое** извлечённое ФТ/НФТ обязано иметь **источник** (`Источник`-колонку): раздел,
  страница, заголовок или URL, откуда оно взято. Требование, которое нельзя привязать к
  конкретному месту источника, **не создаётся**.
- Если чего-то в источнике **нет** (критичность, статус реализации, приоритет, зависимость) —
  это помечается как **`?` (неизвестно)**, а не выдумывается. Пробелы выносятся в отдельный
  раздел «Пробелы и допущения» и уточняются у пользователя.
- Описание требования — **пересказ формулировки из источника** (можно сжать/перефразировать),
  **без добавления фактов**, аспектов, чисел и «и т.п.», которых в источнике не было.
- Если источник неполный/обрезан/недоступен — честно сказать об этом и извлечь только
  доступное, а не «дорисовать».
- В шапке итогового MD и в отчёте в чат — **явная оговорка**: «Требования извлечены строго из
  указанного источника; всё, чего в источнике не было, помечено как неизвестное и требует
  подтверждения пользователя».

Перед записью прогони **чек-лист антидомысливания** (см. в конце). Если хоть один пункт
нарушен — не записывать, а вернуться к источнику или спросить пользователя.

## Модель данных портала (обязательно соблюдать)

Совпадает с порталом project_po (та же, что у `/po`):

- **Тип требования:** `FUNCTION` (ФТ) или `NFR` (НФТ).
- **Критичность:** `LOW | MEDIUM | HIGH | CRITICAL | BLOCKER` (BLOCKER — выше CRITICAL).
  В источнике её обычно нет напрямую → по умолчанию `?`, уточняется у пользователя.
- **Реализация:** `implemented: true|false`. Если `false` — обязательны `targetQuarter`
  (`Q1|Q2|Q3|Q4`) и `targetYear` (число). Если `true` — target НЕ указывать. В источнике
  статуса обычно нет → `?`, уточняется.
- **slug:** генерируется порталом из имени; уникален в проекте. Имена ФТ уникальны среди ФТ,
  НФТ — среди НФТ.
- **Связи (реципрокные):** `PARENT_OF`/`CHILD_OF` (иерархия, у узла ОДИН родитель),
  `RELATES_TO` (симметрична), `DEPENDS_ON`/`BLOCKED_BY` (пара). Циклы, висячие ссылки и
  self-link запрещены. Иерархию строим **только там, где структура источника её явно задаёт**
  (разделы/подразделы, «входит в», «часть модуля»), а не «на глаз».

## MCP-инструменты (сервер `apps/mcp`)

`list_projects`, `get_project`, `list_requirements {projectId}`,
`get_requirement {projectId, slug}`, `create_requirement {projectId, type, name,
criticality, implemented, description?, targetQuarter?, targetYear?}`,
`update_requirement {projectId, slug, …}`, `link_requirements {projectId, sourceSlug,
type, targetSlug}`, `delete_requirement {projectId, slug}`, `export_project {projectId,
format}`.

> **Важно:** создания проекта в MCP НЕТ. Если целевого проекта нет — создать его до
> наполнения (см. Шаг 4).

## Алгоритм (по шагам, не пропускать)

### Шаг 0. Вход и предпосылки

- Определить **источник** (URL / путь к PDF / путь к Word) и **целевой проект** (`id`; по
  умолчанию — осмысленное имя продукта из источника). Если источник не задан — спросить.
- Сразу озвучить пользователю **оговорку про источник** (золотое правило): будет извлечено
  только то, что есть в источнике.
- Найти репозиторий `project_po` (текущая директория или `--repo <путь>`); `PROJECTS_ROOT`
  по умолчанию `<repo>/Projects`.
- Если планируется запись через MCP (не `--dry`): собрать сервер и MCP —
  `npm run build` в корне репозитория (нужны `dist`). При необходимости сперва
  `npm install`/`npm ci`.

### Шаг 1. Прочитать источник (по типу)

Определи тип источника и извлеки из него **текст как есть**. Ничего не добавляй на этом шаге.

**A. Веб-документация (URL).**

- Прочитать страницу инструментом **WebFetch** (промпт: «Извлеки полный текст этой страницы:
  разделы, списки функций, требования, таблицы; ничего не добавляй от себя»).
- Если это **индекс/оглавление** документации (как порталы вида `.../docs/.../index.html`) —
  собрать ссылки навигации **в пределах той же документации** (тот же хост и базовый путь) и
  прочитать релевантные подстраницы по очереди. **Не уходить** на внешние сайты и в
  посторонние разделы. Кросс-хостовые редиректы WebFetch возвращает тебе — не следуй за ними
  автоматически, если это уводит за пределы документации.
- Разумно ограничить обход (глубина/кол-во страниц); в отчёте **перечислить, какие именно URL
  были прочитаны** — это и есть провенанс.
- Если WebFetch вернул мало/пусто (JS-рендер, доступ по логину) — честно сказать, что контент
  недоступен, и не выдумывать его.

**B. Локальный PDF.**

- Читать инструментом **Read** с параметром `pages` (например `"1-20"`). Ограничение — до
  **20 страниц за один вызов**; для больших PDF читать частями (`"1-20"`, `"21-40"`, …). Для
  PDF больше 10 страниц `pages` обязателен уже при первом чтении.
- Источник для провенанса — **номера страниц**.

**C. Локальный Word (.docx / .doc).**

- Read не читает Word напрямую. Сконвертировать в текст и прочитать результат:
  - macOS (по умолчанию есть `textutil`):
    `textutil -convert txt "<файл.docx>" -output "<scratch>/doc.txt"`
    (для сохранения таблиц/структуры можно `-convert html`).
  - Если установлен **pandoc** — лучше в Markdown (сохранит заголовки/таблицы):
    `pandoc "<файл.docx>" -t gfm -o "<scratch>/doc.md"`.
- Складывать конвертированный файл во временную папку скретчпада, затем читать его **Read**.
  Источник для провенанса — **заголовки/разделы** документа.

> Во всех трёх случаях: если объём большой — читать частями и вести список того, что уже
> прочитано, чтобы покрыть источник целиком и ничего не «досочинить» за непрочитанное.

### Шаг 2. Вычленить ФТ/НФТ (строго из прочитанного)

- Пройти по прочитанному тексту и **выписать** конкретные возможности/ограничения как
  требования. Для каждого:
  - **Тип:** `FUNCTION` — то, что система делает (функции, экраны, действия, интеграции);
    `NFR` — качества/ограничения (производительность, безопасность, совместимость,
    масштабируемость, доступность, лицензии, платформы/версии рантайма и т.п.), если они
    **явно** названы в источнике.
  - **Имя:** короткое, из формулировки источника; уникальное в рамках своего типа.
  - **Описание:** 1–2 предложения, пересказ из источника, без добавления фактов.
  - **Критичность / Реализация / target:** только если **явно** сказано в источнике; иначе
    `?`.
  - **Родитель:** только если иерархия **явно** следует из структуры источника (раздел →
    подраздел, «модуль X включает Y»). Ровно один родитель.
  - **Источник:** URL / № страницы / заголовок раздела — **обязательно**.
- Дубли и пересечения — схлопывать; противоречия в источнике — отметить как пробел, а не
  выбирать за автора.

### Шаг 3. Записать MD-черновик (формат для MCP)

Сложить результат в **`extract-out/<project>-requirements.md`** по формату из раздела
«Формат итогового MD» ниже. Обязательно: шапка с оговоркой и списком прочитанных источников,
таблица требований с колонкой **Источник**, таблица связей и раздел **«Пробелы и допущения»**
со всеми `?`.

При `--dry` — на этом остановиться: сообщить путь к файлу, кратко перечислить состав и
пробелы, MCP не трогать.

### Шаг 4. Уточнить пробелы и создать/выбрать проект

- Показать пользователю **пробелы** (все `?`): прежде всего **критичность** и **статус
  реализации**, потому что MCP `create_requirement` требует `criticality` и `implemented`.
  Значения **спросить у пользователя** (можно пакетно, с предложенным по смыслу вариантом —
  но выбор за пользователем), **не проставлять молча**. Для `implemented:false` — уточнить
  `targetQuarter`+`targetYear`.
- Проверить наличие проекта через MCP `list_projects`. Если целевого проекта нет — **создать**
  (MCP не умеет), любым способом:
  - **REST:** поднять собранный сервер и `POST /api/projects {"name":"<project>"}`; либо
  - **через `@po/server`** в том же seed-скрипте:
    ```js
    import { ProjectService } from '@po/server';
    const ps = new ProjectService(PROJECTS_ROOT, () => new Date().toISOString());
    if (!(await ps.list()).some((p) => p.id === PROJECT)) await ps.create(PROJECT);
    ```

### Шаг 5. Наполнить проект через MCP

MCP-клиент по stdio (шаблон ниже). Порядок:

1. `list_requirements` → карта `имя→slug` существующих (идемпотентность: не дублировать).
2. `create_requirement` на каждое НОВОЕ требование; собрать `имя→slug` из ответа
   (`structuredContent.requirement.slug`).
3. `link_requirements` на связи (child = `sourceSlug`, parent = `targetSlug`,
   `type: 'CHILD_OF'`; для отношений — соответствующий тип).
4. Доменные ошибки (уникальность, цикл, один родитель) приходят как `isError` — обработать,
   не молчать.

### Шаг 6. Проверить и отчитаться

- `list_requirements` → посчитать ФТ/НФТ и связи; убедиться, что `broken` пуст.
- В чат кратко: сколько ФТ/НФТ и связей создано, из каких источников, что осталось в
  пробелах, где лежит проект и MD-черновик. **Повторить оговорку**: состав отражает только
  переданный источник. Предложить открыть проект в портале или выгрузить (`export_project`).

## Формат итогового MD (`extract-out/<project>-requirements.md`)

Файл должен быть и человекочитаемым, и однозначно разбираемым для наполнения через MCP.

```markdown
---
product: <Название продукта из источника>
project: <id проекта в портале>
generated: <дата>
source_kind: web | pdf | word
sources:
  - <URL или путь + страницы/разделы, что прочитано>
disclaimer: >
  Требования извлечены строго из указанного источника. Всё, чего в источнике не было
  (критичность, статус реализации, приоритеты, часть связей), помечено «?» и требует
  подтверждения пользователя. Ничего не домысливалось.
---

# Требования: <Продукт>

## Функциональные требования (ФТ)

| #   | Имя               | Критичность | Реализовано | Target | Родитель         | Источник       | Описание                  |
| --- | ----------------- | ----------- | ----------- | ------ | ---------------- | -------------- | ------------------------- |
| F1  | Каталог объектов  | ?           | ?           | —      | —                | §2.1 «Каталог» | Ведение реестра объектов… |
| F2  | Поиск по каталогу | ?           | ?           | —      | Каталог объектов | §2.1.3         | Полнотекстовый поиск…     |

## Нефункциональные требования (НФТ)

| #   | Имя                          | Критичность | Реализовано | Target | Родитель | Источник                    | Описание |
| --- | ---------------------------- | ----------- | ----------- | ------ | -------- | --------------------------- | -------- |
| N1  | Совместимость с <платформой> | ?           | ?           | —      | —        | §1.4 «Системные требования» | …        |

## Связи (кроме иерархии выше)

| Источник (имя) | Тип        | Цель (имя)   |
| -------------- | ---------- | ------------ |
| Оплата         | DEPENDS_ON | Безопасность |

## ⚠️ Пробелы и допущения (уточнить у пользователя)

- Критичность всех требований в источнике не указана → нужно проставить.
- Статус реализации (`implemented`) в источнике не указан → нужно проставить; для плановых —
  `targetQuarter`/`targetYear`.
- <иные противоречия/непонятности источника>
```

Правила формата:

- **Колонка «Источник» обязательна и непуста** для каждой строки — это гарантия отсутствия
  домысливания.
- `?` — допустимое значение в MD для критичности/реализации; перед записью через MCP оно
  должно быть заменено подтверждённым пользователем значением (MCP требует эти поля).
- `Target` = «—», если реализовано или неизвестно; квартал+год — только для `implemented:false`.
- Иерархия задаётся колонкой «Родитель» (имя родительского требования того же проекта).

## Шаблон seed-скрипта (MCP-клиент, stdio)

Класть во временный файл **внутри репозитория** (иначе не резолвятся модули), запускать
`node <файл>.mjs`, затем удалять. Массивы `REQS`/`LINKS` заполняются из MD (после подтверждения
пробелов пользователем).

```js
import { Client } from '@modelcontextprotocol/sdk/client/index.js';
import { StdioClientTransport } from '@modelcontextprotocol/sdk/client/stdio.js';

const PROJECT = process.env.PROJECT;
const PROJECTS_ROOT = process.env.PROJECTS_ROOT; // <repo>/Projects

// [type, name, criticality, implemented, q, y, description, parentName|null]
const REQS = [/* … из MD, критичность/реализация уже подтверждены пользователем … */];
const LINKS = [/* [sourceName, type, targetName] — не-иерархические связи из MD */];

const transport = new StdioClientTransport({
  command: 'node',
  args: ['apps/mcp/dist/main.js'],
  env: { ...process.env, PROJECTS_ROOT },
});
const client = new Client({ name: 'doc-extract', version: '1.0.0' }, { capabilities: {} });
await client.connect(transport);

const existing = (
  await client.callTool({ name: 'list_requirements', arguments: { projectId: PROJECT } })
).structuredContent.requirements;
const slug = new Map(existing.map((r) => [r.name, r.slug]));

for (const [type, name, crit, impl, q, y, desc] of REQS) {
  if (slug.has(name)) continue; // идемпотентность
  const args = {
    projectId: PROJECT,
    type,
    name,
    criticality: crit,
    implemented: impl,
    description: desc,
  };
  if (!impl) {
    args.targetQuarter = q;
    args.targetYear = y;
  }
  const res = await client.callTool({ name: 'create_requirement', arguments: args });
  if (res.isError) throw new Error(`create "${name}": ${res.content?.[0]?.text}`);
  slug.set(name, res.structuredContent.requirement.slug);
}
for (const [type, name, , , , , , parent] of REQS)
  if (parent) {
    const r = await client.callTool({
      name: 'link_requirements',
      arguments: {
        projectId: PROJECT,
        sourceSlug: slug.get(name),
        type: 'CHILD_OF',
        targetSlug: slug.get(parent),
      },
    });
    if (r.isError) throw new Error(`link ${name} CHILD_OF ${parent}: ${r.content?.[0]?.text}`);
  }
for (const [s, type, t] of LINKS) {
  const r = await client.callTool({
    name: 'link_requirements',
    arguments: { projectId: PROJECT, sourceSlug: slug.get(s), type, targetSlug: slug.get(t) },
  });
  if (r.isError) throw new Error(`link ${s} ${type} ${t}: ${r.content?.[0]?.text}`);
}

const all = (
  await client.callTool({ name: 'list_requirements', arguments: { projectId: PROJECT } })
).structuredContent.requirements;
console.log(
  `ФТ=${all.filter((r) => r.type === 'FUNCTION').length}, НФТ=${all.filter((r) => r.type === 'NFR').length}`,
);
await client.close();
```

## Чек-лист антидомысливания (прогнать перед записью)

- [ ] У **каждого** требования заполнена непустая колонка «Источник» (URL/страница/раздел).
- [ ] Ни одно требование не опирается на знание о продукте вне источника и не взято из
      веб-поиска.
- [ ] Критичность/`implemented`/target проставлены **только** там, где это явно в источнике;
      остальное — `?` и вынесено в «Пробелы».
- [ ] Описания не содержат фактов/аспектов/чисел, которых не было в источнике; нет «и т.п.».
- [ ] Иерархия и связи следуют из явной структуры источника, а не додуманы.
- [ ] В шапке MD и в отчёте есть оговорка про источник.
- [ ] Перед MCP-записью все `?` заменены значениями, **подтверждёнными пользователем**.

## Принципы качества

- **Точность важнее полноты.** Лучше меньше требований, но каждое — из источника, чем «полный»
  список с домыслами.
- **Провенанс на всё.** Нет источника → нет требования.
- **Пробелы честно.** Неизвестное помечается, а не заполняется.
- **Удобство для MCP.** MD построен так, что из него напрямую собираются `REQS`/`LINKS` для
  seed-скрипта; критичность/реализацию подтверждает пользователь.
- **Идемпотентность.** Перед созданием сверяться со списком существующих (не дублировать).
