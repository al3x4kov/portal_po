# todo22-backlog-spec — AI-импорт бэклога из xlsx (пилот todo_22 №2)

Автор фазы: senior-po (конвейер /pipeline). Вход: `.dev/todo/todo_22.md` п.2 + пример
`Projects/Книга2.xlsx`. Спек — вход для дизайнера и архитектора.

## 0. Заземление

- **Пример файла** (`Книга2.xlsx`, Jira-выгрузка через queryTable): лист 1, колонки
  `A: Issue key` (CRPV-155771…), `B: Summary` (техформулировки: «Верстка графа коммитов»,
  «[PR-Создание] Панель статистики измененных файлов», «Доработка фильтров»…). ~50–500 строк.
- **Готовая инфраструктура (todo_20, реюзать, не дублировать):** джобы AI-импорта
  (`AiImportJobs`, чекпоинты в `Projects/<p>/.ai-jobs/`, resume, история, лог файлом),
  ретраи/таймауты/параллелизм (aiCall), бюджет/usage, таксономия ошибок
  (`AI_IMPORT_ERROR_CODES`), отчёт, structured output с фолбэком.
- **Источники требований (todo_19):** у требования 0..N `SourceEntry {type, name,
  priorityId, rice?, target*}`; словари источников/приоритетов проекта.
- **Контрактное правило:** `implemented=false` ⇒ обязательны `targetQuarter`+`targetYear`.
- Существующая точка входа: кнопка «AI подгрузка из документации» (Main) → AiImportModal.

## 1. Поведение

### П1. Точка входа
Рядом с «AI подгрузка из документации» — кнопка **«AI подгрузка из бэклога»** (та же
зона, тот же стиль, иконка отличается). Открывает модалку «AI импорт бэклога»
(размер — как у модалки документации после task24, ~70% экрана).

### П2. Загрузка и предпросмотр (без AI-вызовов)
1. Приём файла `.xlsx` (drag&drop + выбор), лимит разумный (например 10 МБ / 5000 строк).
2. Сервер детерминированно парсит первый лист: распознаёт колонку-ключ (опционально,
   паттерн вида ABC-123 или заголовок «Issue key»/«Key»/«ID») и колонку-формулировку
   (обязательна; заголовок «Summary»/«Название»/«Тема» или самая содержательная текстовая
   колонка). Распознавание — по содержимому, не только по заголовкам (инвариант todo_20).
3. Модалка показывает **предпросмотр**: какие колонки распознаны (ключ/формулировка),
   первые 5 строк, всего строк к обработке, пропущенные пустые/служебные строки,
   мини-смета (~вызовов/токенов). Кнопки «Начать анализ» / «Отмена».
4. Файл без пригодной текстовой колонки → понятная ошибка (таксономия, категория data).

### П3. AI-соотнесение с деревом (батчами)
1. Модель получает компактную карту существующего дерева ФТ/НФТ проекта (имена +
   иерархия, аналог archiveMap) и батч строк бэклога (≤20).
2. Для каждой строки модель возвращает: `parentName` (существующий узел, куда встроить,
   или null), `duplicateOf` (имя существующего требования, если строка о том же, или null),
   `businessName` (переписанное конструктивное бизнес-имя, рус.), `type`
   (FUNCTION по умолчанию; NFR — если формулировка явно нефункциональная).
3. Детерминированная пост-обработка: валидация parentName/duplicateOf по реальному дереву
   (галлюцинации → null), дедуп строк между собой (нормализация+fuzzy из todo_20).
4. Надёжность: реюз ретраев/таймаутов/параллелизма/чекпоинтов todo_20; resume после
   сбоя; невалидный JSON → повторы и деление батча пополам (аналог адаптивного чанкера).

### П4. Создание требований
1. Каждая несдублированная строка → новое требование: имя = `businessName`
   (при коллизии имён — суффикс-нумерация как в существующем populate), тип из П3.
2. **Описание** = исходная формулировка из бэклога (дословно) + строка «Ключ бэклога:
   CRPV-…» (если ключ распознан).
3. Связь `CHILD_OF` к узлу `parentName`; строка без родителя → под корневой узел-ФТ
   **«Бэклог»** (создаётся один раз при необходимости) [решение по умолчанию, см. Вопросы].
4. **Источник**: каждому созданному требованию — SourceEntry типа `TEXT` с именем
   «Бэклог: <имя файла>» (имя попадает в словарь источников проекта автосбором;
   приоритет — дефолтный словаря) [см. Вопросы].
5. `implemented=false` + target: дефолт — ближайший следующий квартал от текущей даты
   [см. Вопросы].
6. Дубликаты (`duplicateOf`): требование НЕ создаётся; в отчёте — строка «пропущено как
   дубль “X”» [альтернатива — обогащение описания существующего; см. Вопросы].
7. Populate идемпотентен (реюз todo_20): resume не создаёт дублей.

### П5. Прогресс, ошибки, отчёт (реюз паттернов todo_20)
1. Прогресс: «батч X из Y», создано ФТ/НФТ/связей, пропущено дублей, токены, события.
2. Ошибки: таксономия (коды/категория/действие/resumable), «Продолжить» работает.
3. Итоговый отчёт: счётчики (строк прочитано/создано/дублей/в «Бэклог» без родителя);
   **таблица соответствий**: исходная формулировка → бизнес-имя → родительский узел
   (+пометки «дубль», «без родителя»); скачивание лога. Отчёт есть и при частичном фейле.
4. История джоб — общая с импортом документации (тип джобы виден в списке).

## 2. НФТ

- Н1: до 5000 строк / 10 МБ xlsx; парсинг потоковый/ограниченный по памяти.
- Н2: батчи ≤20 строк; параллелизм/ретраи/тайм-ауты — настройки пресета todo_20.
- Н3: живучесть = todo_20 (чекпоинт на батч, resume, рестарт сервера).
- Н4: только OpenAI-совместимый API, structured output строго с фолбэком.
- Н5: содержимое бэклога не логируется целиком; ключ API не в логах.
- Н6: xlsx-парсер устойчив к чужим диалектам (queryTable/connections Jira, inline
  strings, пустые строки/колонки, объединённые ячейки) — никакой файл не роняет сервер.

## 3. Критерии приёмки

1. Книга2.xlsx (эталон пилота): все непустые строки распознаны, предпросмотр показывает
   колонки Issue key/Summary; после прогона (мок-модель в тестах) — требования созданы
   с бизнес-именами, исходники в описаниях, ключи сохранены, связи к узлам валидны.
2. xlsx без ключевой колонки (только формулировки) — работает; без текстовой колонки —
   понятная ошибка с действием.
3. Сбой AI на середине → ошибка с «Продолжить» → resume доводит без дублей.
4. Дубликат строки к существующему ФТ — не создан, виден в отчёте.
5. Строка без подходящего узла — попала под «Бэклог», видна в отчёте.
6. Гейты качества зелёные; покрытие core ≥90% держится.

## 4. Бриф дизайнеру

Модалка «AI импорт бэклога» (размер как AiImportModal после task24), 4 состояния +
кнопка. Реюз визуальных паттернов todo20 (design-out/todo20/*): каркас модалки, лента
событий, блоки ошибок/отчёта.

1. **Кнопка** «AI подгрузка из бэклога» рядом с «AI подгрузка из документации».
2. **Экран загрузки+предпросмотра**: зона файла; после выбора — распознанные колонки
   (чипы «Ключ: A — Issue key», «Формулировка: B — Summary»), таблица первых 5 строк,
   «всего N строк, пропущено M пустых», мини-смета; «Начать анализ»/«Отмена».
3. **Прогресс**: «батч X из Y», счётчики (создано ФТ/НФТ/связей, дублей пропущено),
   токены, события; «Остановить».
4. **Ошибка**: паттерн todo20 (код/действие/счётчики/«Продолжить»/детали).
5. **Итоговый отчёт**: счётчики + таблица соответствий (исходная формулировка →
   бизнес-имя → родитель; бейджи «дубль»/«без родителя»); «Скачать лог», «Открыть проект».

## 5. Вне объёма

- Форматы кроме .xlsx (csv/Google Sheets) — отдельное ТЗ.
- Двусторонняя синхронизация с Jira, обновление статусов.
- Автопростановка криттичности/RICE по бэклогу.
- Редактирование соответствий в UI до создания (интерактивный review) — v2.

## 6. Решения PO (гейт после макета, 2026-08-03)

1. **Несоотнесённые строки — узла-свалки «Бэклог» НЕ будет.** Модель обязана предлагать
   для каждой строки БИЗНЕСОВЫЙ узел: существующий или НОВЫЙ узел-функцию продукта
   (в т.ч. новый корневой, если строка сама по себе — функция верхнего уровня).
   «Узлы без бизнесовой связи запрещены» — техническая свалка недопустима.
   **Обязательный этап выверки перед записью**: после AI-соотнесения и ДО populate
   пользователь видит полную разметку (таблица соответствий + отдельный список
   предлагаемых НОВЫХ узлов) и подтверждает запись. Минимум v1: чекбоксы строк
   (по умолчанию включены), явный блок «Будут созданы новые узлы», кнопки
   «Записать в проект» / «Отмена». До подтверждения в проект ничего не пишется.
2. **Дубли**: пропускать; пометка «дубль» в отчёте (существующее не менять).
3. **Target**: если в файле есть информация о сроке (колонки вида due date / fix
   version / target — распознавать по содержимому) — брать из файла для конкретной
   строки; иначе — общий выбор «целевой квартал/год» в модалке на шаге предпросмотра
   (обязательное поле с дефолтом = ближайший следующий квартал).
4. **Источник**: НОВЫЙ тип `BACKLOG` в контракте SourceType (@po/core) + подпись
   («Бэклог»), иконка и участие во всех местах UI, где различаются типы источников
   (формы, бейджи, фильтры, словари). Имя источника — «Бэклог: <имя файла>».
5. НФТ: модели разрешён тип NFR для явно нефункциональных формулировок (дефолт принят).
6. Маппинг колонок: v1 — автоматический с предпросмотром, без ручного выбора (принято).

Следствия для дизайна (обновление брифа): в модалке появляется шаг «Выверка разметки»
между прогрессом и записью — таблица соответствий с чекбоксами + блок новых узлов +
«Записать в проект»; на шаге предпросмотра — поле «целевой квартал/год (если не найден
в файле)». Итоговый отчёт остаётся (после записи).

## 6-бис. Исходные открытые вопросы (история)

1. **Несоотнесённые строки**: корневой узел «Бэклог» (дефолт) / пропускать с отчётом /
   падать с просьбой доработать дерево?
2. **Дубликаты**: пропускать (дефолт) или обогащать описание существующего требования
   исходной формулировкой + ключом?
3. **Target для новых требований** (`implemented=false`): ближайший следующий квартал
   (дефолт) или спрашивать в модалке перед стартом?
4. **Тип источника**: `TEXT` «Бэклог: <файл>» (дефолт, без изменения контракта) или
   новый `SourceType BACKLOG` (потянет словари/иконки/фильтры)?
5. **НФТ из бэклога**: разрешить модели тип NFR (дефолт) или всё в ФТ?
6. **Ручной маппинг колонок**: нужен ли выбор колонок вручную при неуверенном
   распознавании (дефолт: авто + предпросмотр, без ручного выбора в v1)?
