## Замечания с демо (первоисточник)

1. Нет скоринга (нужен RICE, хотя бы базовый).
2. Нет учёта источника требований (клиент, стейкхолдер, внутренний стандарт).
3. Нет приоритета от источника — отдельная линейка (шоустоппер для сделки, квартальная цель стейкхолдера), чтобы всегда можно было показать стейкхолдеру его фичи с верхним приоритетом.
4. Look-n-feel и UX причесать; атрибутивный состав объектов беден.

## Текущее состояние (по графу кода)

- Дерево (TreeTable): колонки Требование / Критичность / Реализация / Источник / Связи / Описание.

## Решения PO (Гейт 1, зафиксировано)

- **RICE**: базовых шкал-селектов достаточно (Reach — селект, не свободное число).
- **Агрегация**: итоговый RICE требования = max по источникам; итоговый приоритет = старший по справочнику.
- **Справочники — отдельный пункт меню «Справочники»** (управление на уровне проекта): туда складываются все справочники (источники, приоритеты источников и т.д.), пользователь редактирует названия и **выбирает цвет подсветки**. Значения подтягиваются в карточку требования.
  - Справочник приоритетов источников: элемент = название + цвет + порядок (старшинство). **Дефолт поставки — один элемент «Квартальная цель»**; остальные пользователь заводит сам (или удаляет дефолтный).
  - Справочник источников: элемент = имя + тип + (опц.) цвет; наполняется и из меню, и автосбором введённых в требованиях имён.
- **Быстрое добавление с формы**: в выпадающем списке приоритета есть пункт «Добавить свой вариант…» — инлайн-создание (название + цвет), новый элемент попадает в справочник проекта.
- **Даты**: у источника и в «Дате выпуска» PO — дата без времени. Если дата вне выбранного квартала — **бледная подсветка-предупреждение (не блокирует сохранение)**.
- **Пресеты «АС21», «ПАО»**: это имена источников типа «текст» (OTHER); мигрируют в `sources[0].name`.
- **Look-n-feel**: НЕ ограничиваемся блоком 4 — делаем полный проход по `norman-review.md` (systemic + по экранам), в разумном объёме итерации.

## Ключевое уточнение PO (Гейт 1, итерация 2)

На одно требование может быть **несколько заказчиков/источников, у каждого свой приоритет и своя оценка**. Поэтому источник, приоритет источника и RICE-оценка объединяются в один повторяемый блок:

```
sources: SourceEntry[]           // 0..N на требование
SourceEntry = {
  type: CLIENT | STAKEHOLDER | STANDARD | OTHER,
  name: string,                  // имя источника (справочник проекта)
  priority: string,              // код из КОНФИГУРИРУЕМОГО справочника приоритетов проекта
  rice?: { reach, impact, confidence, effort },  // оценка ЭТОГО источника
  targetQuarter?: Q1..Q4,        // желаемый срок ЭТОГО источника
  targetYear?: number,
  targetDate?: ISO-date          // опционально: конкретная желаемая дата
}
```

**Приоритет источника конфигурируем** (итерация 3): на уровне проекта — справочник `sourcePriorities` (дефолт: S0–S3 ниже), упорядоченный по старшинству; в UI — выпадающий список + пункт «Добавить свой вариант…» (новый код попадает в справочник проекта).

**Сроки** (итерация 3): каждый источник может привязать пожелание к кварталу+году и/или к конкретной дате. Это входные данные для PO, а не план.

**Решение PO**: на уровне требования остаются существующие `targetQuarter`/`targetYear` (план реализации) + новое поле `releaseDate?` (конкретная дата выпуска, опционально). PO выставляет их, глядя на список сроков источников.

Итоговые значения требования — агрегаты: приоритет = старший по порядку справочника (S0 побеждает), `riceScore = max` score по источникам (правило агрегации — открытый вопрос). В дереве показываются агрегаты + количество источников.

## Предложение 1 — Базовый RICE-скоринг (на каждый источник)

Опциональный блок `rice` внутри каждого элемента `sources`:

| Поле | Шкала (базовая) | Подсказка в UI |
|---|---|---|
| Reach | 1–5 (сколько пользователей/сделок затронет за квартал) | 1 = единичные, 5 = почти все |
| Impact | 0.25 / 0.5 / 1 / 2 / 3 | стандартная шкала Intercom |
| Confidence | 50% / 80% / 100% | уверенность в оценках |
| Effort | 0.5 / 1 / 2 / 3 / 5 / 8 (чел-недели) | грубая оценка команды |

`score = Reach × Impact × Confidence / Effort` — считается автоматически на источник; итог требования — агрегат по источникам (не хранится, вычисляется).

UI: карточка источника в модалке содержит 4 селекта + живой score-бейдж; колонка «RICE» в дереве (агрегат, с сортировкой), топ-5 по RICE на дашборде.

## Предложение 2 — Структурированные источники (список)

Вместо свободной строки `source` — список `sources` (см. выше):

- `type`: `CLIENT` (клиент/сделка) · `STAKEHOLDER` (внутренний стейкхолдер) · `STANDARD` (внутренний стандарт/регламент) · `OTHER`
- `name`: имя источника (комбобокс со справочником уже использованных в проекте имён; текущие значения `source` мигрируют в первый элемент `sources` с типом OTHER)

UI: в модалке — список карточек источников с кнопкой «Добавить источник»; поле имени источника — combobox с поиском/подстановкой по уже заведённым источникам проекта (по вводу подсказываются совпадения + пункт «Создать новый источник»); в дереве — бейдж первого/старшего источника с иконкой типа (Briefcase/User/BookMarked) + чип «+N».

## Предложение 3 — Приоритет от источника (конфигурируемая линейка, у каждого источника свой)

`priority` элемента `sources`, независим от нашей `criticality`. Значения — из справочника проекта `sourcePriorities` (упорядочен по старшинству, редактируемый). **В UI показывается только название + цвет, кодов вроде «S0» пользователь не видит** (порядок/цвет несут срочность; внутренний идентификатор — деталь реализации). Дефолтный набор (сверху — старший):

| Название | Смысл | Цвет |
|---|---|---|
| Критично для сделки | блокирует заключение/исполнение сделки, риск потери клиента | красный |
| Квартальная цель | обязательство источника на квартал | янтарный |
| Важно | явный запрос, без жёсткого срока | синий |
| Пожелание | «хорошо бы» | серый |

UI выбора: выпадающий список значений справочника + пункт «Добавить свой вариант…» (инлайн-создание кастомного приоритета, попадает в справочник проекта и доступен всем требованиям).

## Предложение 3а — Сроки: пожелания источников и решение PO

- У каждого источника: `targetQuarter`+`targetYear` (желаемый квартал) и/или `targetDate` (конкретная желаемая дата) — опционально.
- У требования (решение PO): существующие `targetQuarter`/`targetYear` + новое `releaseDate?` (конкретная дата выпуска). В модалке рядом с полями PO показывается сводка пожеланий источников, чтобы решение принималось «глядя на список».

UI: колонка «Срок реализации» в дереве — двухуровневая ячейка (сверху квартал/год = план PO, под ним дата выпуска только если задана; «Реализовано» для готовых), а не квартал+год+дата в одну строку. Колонка источников показывает старший источник + приоритет названием (без кодов) + чип «+N». Фильтры по типу источника/имени/приоритету; срез «по источникам» (группировка: источник → счётчики верхних приоритетов + список; требование с N источниками появляется в N группах со СВОИМ приоритетом в каждой) — то самое «ткнуть стейкхолдеру».

## Предложение 4 — Look-n-feel (из ревью Нормана, войдёт независимым треком)

1. [HIGH] Действия строки дерева видимы всегда (приглушённые иконки, не opacity-0; focus-within).
2. [HIGH] Шапка: имя проекта крупно и первым, путь — вторичная строка.
3. [HIGH] Модалка требования: секции-вкладки «Основное / Приоритизация / Описание / Связи / Справочно»; убрать confirm на обычное сохранение.
4. [MED] 100% Lucide-иконки вместо эмодзи.
5. [MED] Развести Toast и FAB чата по углам.
6. [MED] Иконки добавления ФТ/НФТ различать формой, а не только цветом.
