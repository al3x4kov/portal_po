# todo20-spec — Качество AI-анализа загруженной документации (AI Hub)

Автор фазы: senior-po (конвейер /pipeline). Вход: `.dev/todo/todo_20_ai_hub_import_quality.md`
+ пилотное замечание №3 из `.dev/todo/todo_21.md` (неинформативный Timeout при AI-вычленении,
при работающем чат-виджете на той же модели). Этот спек — вход для дизайнера (макеты) и
архитектора (декомпозиция + контракт).

## 0. Текущее состояние (заземление на код)

- Конвейер: `AiImportService.run()` = unpack → analyze → structure → aggregate → populate →
  (опц.) relate; стадии в `apps/server/src/services/aiImport/*`.
- AI-вызов: `chatWithJsonRetries` — до N попыток на невалидный JSON; **любая** upstream-ошибка
  (`kind:'upstream'`: сеть/429/5xx/таймаут SDK) НЕ ретраится и валит джобу.
- Пресеты моделей: `@po/core` `aiModelPresetSchema` {temperature, maxOutputTokens, chunkChars,
  reasoning, topP} + `resolveModelPreset` (generic ← default-by-id ← override).
- Контракт джобы: `aiImportJobViewSchema` {status, stage, progress, log, result?, error?{message,hint},
  relate?}. Чекпоинтов нет, resume нет, usage-токены не собираются, сметы нет, описи файлов нет.
- UI: `AiImportModal` (запуск, прогресс-поллинг, лог), `AiPage` (настройки: ключ, модель,
  пресеты — `AiModelPresetForm`), `AiGenerationPanel`/чат-виджет.
- Джобы живут в памяти (`AiImportJobs`) — рестарт сервера теряет всё.

## 1. Поведение (что должно стать)

### П1. Опись и триаж после распаковки (todo_20 A1, A2, A3)

1. После unpack строится **опись** (inventory): для каждого файла — путь, тип
   (md/json/yaml/text/бинарь), размер, оценка токенов, класс источника
   `release-notes | user-guide | admin-guide | security | api-spec | config | other`,
   решение `process | skip` + причина skip (бинарь, изображение, lock-файл…).
2. Классификация **контентная**, не по именам путей: (а) дешёвые эвристики по содержимому
   (структура JSON с полями изменений, таблицы «функция/описание», заголовки «Что нового»/
   «Release notes»/«Руководство…» в любом регистре/языке); (б) для неопознанных — батчевая
   LLM-классификация по первым N строкам (до 30 файлов/вызов); (в) не удалось — класс `other`,
   файл ВСЁ РАВНО обрабатывается с базовым приоритетом. Имена путей — только слабый сигнал.
3. Нормализация до LLM (format-aware, по sniffing содержимого): JSON-массивы изменений →
   плоские записи детерминированным кодом; MD-таблицы → списки «имя — описание»; YAML → пары
   ключ/значение; неизвестная структура → как обычный текст, без падения.
4. Порядок обработки — по приоритету класса (release-notes и функции продукта первыми), чтобы
   при остановке/лимите самое ценное уже было извлечено.
5. Опись — часть состояния джобы, видна в UI (сводка) и в итоговом отчёте; исключения из
   обработки всегда с причиной, никогда молча.

### П2. Смета до старта (A4)

1. Новый предварительный шаг: по загруженному архиву — «план прогона»: файлов к обработке /
   исключено (и почему), примерно чанков, AI-вызовов, оценка токенов.
2. Если оценка выше настраиваемого порога — старт только после явного подтверждения
   пользователя (кнопка «Запустить всё равно»); ниже порога — смета показывается, старт сразу.
3. Порог — в настройках AI (разумный дефолт), выключаем (0 = всегда спрашивать? — см. Вопросы PO).

### П3. Конвейер, дружелюбный к слабым моделям (B1–B6)

1. **Адаптивные чанки:** старт с `preset.chunkChars`; при `finish_reason=length`, двух подряд
   невалидных JSON или ошибке контекстного окна — чанк делится пополам (до минимального
   порога) и повторяется; серия успехов постепенно возвращает размер к пресету. Каждое
   деление — warn в лог человеческим языком.
2. **Structured output с фолбэком:** первый вызов прогона пробует `response_format`
   (json_schema, при отказе json_object); ошибка на параметр запоминается на прогон → работа
   по текущей схеме «текст + парсер». Ничего не ломается на vLLM/Ollama/прокси (НФТ Н5).
3. **Плоская схема шага analyze** для слабых моделей: `{name, type, description}` без
   вложенности; иерархия/связи — существующими шагами structure/relate; few-shot примеры
   в промпте по классу источника (1–2 на класс).
4. **Дедупликация map-reduce:** слияние результатов чанков — детерминированный код
   (нормализация имени + fuzzy-порог); спорные пары — модели батчами ≤20 пар, бинарный ответ.
5. **Контроль полноты чанка:** после extract сравнить число позиций с эвристикой плотности
   (для release notes — число записей из нормализации П1.3); при <50% ожидаемого — один
   повторный проход «извлеки ВСЕ записи, сейчас N из ~M».
6. **Бюджет прогона:** настраиваемый лимит вызовов/токенов на джобу; достижение → мягкая
   остановка с сохранением результата и понятным сообщением + предложением продолжить
   (resume) с повышенным лимитом.

### П4. Устойчивость к OpenAI-совместимому API (C1–C4; закрывает пилотный баг №3)

1. **Классификация и ретраи upstream:** 429/5xx/сетевые/таймауты → экспоненциальный backoff
   с джиттером (1s→2s→4s→8s, максимум N попыток), уважать `Retry-After`; `400 context_length`
   → в деление чанка (П3.1), не ретраить; `401/403` → немедленный fail «проверьте ключ»;
   `404 model` → fail со списком доступных моделей (если API отдаёт).
2. **Параллелизм с лимитом:** пул K параллельных вызовов чанков (настройка пресета, дефолт
   2–3 консервативно); первый 429 → K=1 до конца «окна», затем постепенное восстановление.
3. **Per-call timeout:** явный тайм-аут на вызов (настройка; дефолт с запасом на
   thinking-модели), попадает в ретраи П4.1. Диагностика в лог: сколько ждали, какой стадии,
   какой чанк — чтобы «Timeout» больше никогда не был голым словом (пилотный баг №3).
4. **Учёт токенов:** копить `usage` из каждого ответа; показывать в прогрессе и итоговом
   отчёте (prompt/completion, средняя цена чанка); эти же данные калибруют смету П2.

### П5. Чекпоинты и возобновление (D1–D3)

1. После каждого чанка/стадии — чекпоинт на диск в каталоге джобы (extracted-записи, позиция
   в описи, usage, адаптивное состояние); формат переживает рестарт сервера.
2. `resume` джобы в статусе `failed`/`cancelled` (и «обнаруженной после рестарта»): продолжение
   с последнего чекпоинта, пройденные чанки не переоплачиваются. Кнопка в UI рядом с ошибкой.
3. Идемпотентность populate (skip existing + доливка недостающих связей) — зафиксировать
   контрактом и покрыть тестами resume-сценария.

### П6. Ошибки и коммуникация (E1–E4; закрывает пилотный баг №3)

1. **Таксономия ошибок** — единый реестр: `code`, категория
   (`data | model | network | config | budget`), сообщение по-русски без техножаргона,
   конкретное действие, ссылка на подробный лог. Технические детали (HTTP-код, тело ответа) —
   сворачиваемый блок, не первая строка.
2. `job.error` расширяется: `{ message, hint, code, category, action, resumable }`
   (обратная совместимость: message+hint остаются).
3. UI при fail: что случилось (по-русски), что уже создано (счётчики), кнопки: «Продолжить»
   (resume), «Повторить с меньшими чанками», «Открыть частичный результат».
4. **Прогресс с содержанием:** текущий файл/класс, чанк X из Y, создано ФТ/НФТ, токены,
   оценка оставшегося времени; деградации (деление чанка, снижение параллелизма, фолбэк
   парсера) — warn-события человеческим языком.
5. **Итоговый отчёт качества:** покрытие описи (обработано/исключено/с ошибками), извлечено
   по классам источников, чанков с повтором П3.5, где были обрезания — слепые зоны видны PO.

### П7. Эталон и метрика качества (A5, F3)

1. Fixture: эталонный набор (архив + список ФТ имя/область/источник) в тестовых fixtures;
   для CI — синтетический (мок-модель), для ручных прогонов — реальный `docsourcecontrol`
   (810 ФТ) вне репо.
2. Команда сравнения результата прогона с эталоном: полнота/точность по нормализованным
   именам/областям; отчёт прикладывается к прогону.

## 2. НФТ (из todo_20 §4, обязательны для архитектора)

- Н1: архив до 200 МБ / 2000 текстовых файлов; опись и чанкование потоково, пик памяти
  ≤512 МБ на джобу. (Внимание: текущий лимит 50 МБ — поднять по контракту, см. Вопросы PO.)
- Н2: эталонный прогон на слабой модели — часы, не сутки; джоба асинхронная, UI отзывчив.
- Н3: единичные сбои не теряют прогон; сервер перезапускаем — джоба возобновляема.
- Н4: структурированный лог + счётчики ретраев/делений/токенов; выгрузка лога файлом.
- Н5: только OpenAI-совместимый Chat Completions; `response_format` строго с фолбэком.
- Н6: содержимое документов не логируется целиком; ключ не попадает в лог/отчёты.

## 3. Критерии приёмки (сквозные, из todo_20 §5)

1. Эталон: полнота ≥80% (сильная модель) / ≥60% (слабая), отчёт сравнения прилагается.
2. «500 вызовов, 5% отвечают 429/500/таймаут» (мок) — завершение без участия пользователя.
3. Kill сервера на середине → рестарт → «Продолжить» → джоба доходит до конца; дублей
   ФТ/связей нет, пройденные чанки не переоплачиваются.
4. `400 context_length` → автоделение чанка, прогон продолжается, warn по-русски в логе.
5. Любой fail: код, причина по-русски, следующее действие, счётчики созданного; кнопка работает.
6. Бэкенд без `response_format` — не хуже текущего поведения.
   6b. Другая раскладка/имена того же контента — полнота в пределах 5%; классы определены по
   содержимому; `other`-файлы обработаны.
7. Покрытие: core ≥90% не нарушен; e2e больших объёмов зелёный в CI.

## 4. Бриф дизайнеру (какие экраны/состояния)

Стек макета: HTML + Tailwind, токены из docs/design/. Тёмная/светлая темы. Русский язык.
Затрагивается **модалка AI-импорта** (основное) + точечно экран AI (настройки).

1. **Шаг «Смета» (новый, до старта):** сводка описи — файлов к обработке по классам
   (release notes / руководства / security / api / config / прочее), исключено с причинами
   (раскрываемый список), оценка: чанков, AI-вызовов, токенов; при превышении порога — блок
   предупреждения + кнопка «Запустить всё равно» / «Отмена»; ниже порога — «Запустить».
2. **Прогресс (обновлённый):** стадия + текущий файл и его класс, «чанк X из Y», счётчики
   создано ФТ/НФТ/связей, потрачено токенов, оценка оставшегося времени; лента событий
   (info/warn) с человеческими формулировками деградаций; кнопка «Остановить».
3. **Ошибка (обновлённая):** первая строка — по-русски что случилось; блок «Что уже создано»
   (счётчики); ряд действий: «Продолжить» (когда resumable), «Повторить с меньшими чанками»,
   «Открыть частичный результат»; сворачиваемые «Технические детали» (код, HTTP, фрагмент
   ответа); ссылка «Скачать лог».
4. **Итог (обновлённый):** итоговый отчёт качества — покрытие описи (обработано/исключено/
   с ошибками), извлечено по классам источников, предупреждения о слепых зонах (обрезания,
   повторные проходы), токены; действия «Открыть проект», «Скачать отчёт/лог».
5. **Экран AI (настройки, точечно):** в пресет модели добавляются поля: параллелизм K,
   per-call timeout, бюджет прогона (вызовы/токены), порог сметы. Подписи с пояснениями
   в стиле существующей секции «Параметры модели» (todo_18).
6. **Джоба после рестарта сервера:** состояние «прервана рестартом» в списке/модалке с
   кнопкой «Продолжить».

Дизайнеру НЕ надо: чат-виджет, генерация описаний, дерево требований.

## 6. Решения PO (гейт после макета, 2026-08-03)

1. **Лимит архива:** поднять до **200 МБ** в рамках этой задачи (Н1 закрывается полностью);
   опись/чанкование потоково, пик памяти ≤512 МБ.
2. **Порог сметы:** дефолт **2 млн токенов**; 0 = подтверждать всегда; пусто = не спрашивать.
3. **Чекпоинты:** **внутри каталога проекта** — `Projects/<project>/.ai-jobs/<jobId>/`.
   ОБЯЗАТЕЛЬНО: каталог `.ai-jobs/` исключается из экспорта проекта (zip/targz) и
   игнорируется при импорте архива и открытии проекта (не является требованием/спекой).
4. **История джоб:** **полная история** прогонов проекта в UI: список джоб с статусом,
   счётчиками и датой; у каждой — отчёт/лог; незавершённая — кнопка «Продолжить».
   (Расширяет волну frontend: список + переход к отчёту.)
5. **Эталон docsourcecontrol (810 ФТ):** канонический реестр — вне репо (путь передаётся
   команде сравнения параметром); в репо — только синтетический fixture для CI.
6. **Оценка оставшегося времени:** показывать после первых успешных фрагментов
   (экстраполяция по фактической скорости), до этого — «оценивается…».

## 6-бис. Исходные открытые вопросы (для истории)

1. **Лимит архива:** поднимать текущие 50 МБ до 200 МБ (Н1) сразу в этой задаче или отдельной?
   (Влияет на unpack и на потоковую опись.)
2. **Порог сметы:** дефолт порога подтверждения (например 200 вызовов или ~1 млн токенов)?
   Значение 0 = «всегда подтверждать» или «никогда»?
3. **Хранение чекпоинтов:** каталог джобы внутри `PROJECTS_ROOT/<project>/.ai-jobs/` или в
   служебном каталоге приложения? (Влияет на экспорт/импорт проекта — чекпоинты не должны
   попадать в архив экспорта.)
4. **Список джоб:** нужен ли отдельный список прошлых джоб в UI (история) или достаточно
   «последняя джоба проекта» с resume? (Спек предполагает минимум: последняя + resume.)
5. **Эталонный архив docsourcecontrol** (810 ФТ) — где хранится канонический реестр для
   ручной регрессии F3 (вне репо)? В репо кладём только синтетический fixture.
6. **Оценка оставшегося времени:** показывать всегда (грубая экстраполяция) или после
   первых K чанков (точнее, но поздно)?
