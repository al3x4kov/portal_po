## ЗАДАЧИ

**PO-T1 · QA + backend · P1.** Как PO я хочу, чтобы бенчмарки NFR-3 проверяли именно заявленный
fit-критерий, чтобы деградация на целевом масштабе (1000 требований) не проходила CI «зелёной».
Приёмка: [ ] серверный perf-тест на 1000 требований меряет CRUD (create/update/delete c записью
файла) и list, порог p95 < 200 мс (или ТЗ §4/NFR-3 честно скорректировано и совет уведомлён);
[ ] бюджет `perf.test.ts` (сейчас p50 800 мс @500) выровнен с ТЗ; [ ] e2e меряет первичный рендер
Main < 1.5 c на проекте ≥1000 (допустим отдельный perf-прогон, не гейтящий flaky-бюджет основного);
[ ] DoD п.6 ссылается на реальные тесты.

**PO-T2 · backend (QA-ревью) · P1.** Как PO я хочу быть уверенным, что AI-импорт, пишущий в живой
проект пользователя, при сбое посреди пайплайна не оставляет проект полусозданным «молча».
Приёмка: [ ] тест: инжектированный сбой между созданием требований и созданием связей → проект
валиден (нет висячих ссылок), job в состоянии error с понятным сообщением; [ ] тест: повторный
запуск после такого сбоя достраивает недостающее без дублей (расширение существующего
идемпотентного теста на «частичный» проект); [ ] тест поведения при потере job (рестарт сервера,
in-memory jobs): `GET /api/ai-import/:jobId` возвращает распознаваемую ошибку, UI показывает
«Повторить анализ», а не вечный прогресс.

**PO-T3 · QA (frontend-поддержка) · P2.** Как PO я хочу, чтобы DoD-критерий NFR-7 («axe на ключевых
экранах») покрывал и новые AI-поверхности, чтобы регресс доступности не проникал через самые свежие
фичи. Приёмка: [ ] axe-скан: экран AI, открытый чат-виджет, модалка AI-импорта, модалка экспорта —
0 serious/critical; [ ] e2e: FAB чата и виджет управляются с клавиатуры (открыть по Enter/Space, фокус внутри, закрыть Esc);
[ ] focus-trap модалки AI-импорта в состоянии running (X → ConfirmDialog) проверен.

**PO-T4 · backend (QA-ревью) · P2.** Как PO я хочу автотест байт-детерминизма экспорта, потому что
это заявленный fit-критерий ценности «AI-ready» (§1.2) и защита round-trip как «метрики успеха».
Приёмка: [ ] тест: два вызова `GET .../requirements?format=openspec` на неизменном проекте —
байт-в-байт идентичны; [ ] тест: экспорт архива с «все поля выбраны» байт-в-байт совпадает с
экспортом без выбора полей (заявлено в RELEASE_NOTES, тестом не закреплено); [ ] тест: re-import
экспортированного архива → повторный экспорт идентичен (устойчивый round-trip).

**PO-T5 · QA · P2.** Как PO я хочу e2e-подтверждение юзабельности UI на целевом масштабе 1000
(сейчас 300), чтобы обещание NFR-3 проверялось там, где живёт пользователь. Приёмка: [ ] scale-тест
на ~1000 требований: раскрытие, поиск, мультиселект-фильтр, открытие модалки — без таймаутов и
h-scroll; [ ] выполняется в CI (допустимо в отдельном не-flaky-критичном джобе с зафиксированной
reference-конфигурацией из §4).

**PO-T6 · QA · P3.** Как PO я хочу минимальный кросс-браузерный смоук для AI-поверхностей (сейчас
webkit/firefox гоняют только базовый happy-path), чтобы чат-виджет с drag-логикой и экран AI не
ломались тихо вне Chromium. Приёмка: [ ] @smoke-тест: FAB виден и открывает виджет, экран AI
рендерится — в webkit-smoke и firefox-smoke.

## Топ-5 слепых зон по риску (сводка)

1. **NFR-3 не проверяется как заявлено в DoD** — CRUD p95<200мс@1000 и первичный рендер <1.5с не
   меряются, серверный бюджет в 4 раза мягче ТЗ (PO-T1).
2. **Сбой AI-импорта посреди записи в живой проект** — полусозданное состояние/потерянный job не
   тестируются (PO-T2).
3. **Байт-детерминизм экспорта (fit-критерий «AI-ready») без теста** — включая «все поля = прежняя
   выгрузка» нового экспорта с выбором полей (PO-T4).
4. **a11y новых AI-поверхностей вне axe-скана**, клавиатурный доступ к чат-виджету не проверен (PO-T3).
5. **UI-масштаб 1000 не подтверждён e2e** — scale-тест остановился на 300 (PO-T5).
