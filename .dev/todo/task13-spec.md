## Трек A — независимые backend-фиксы (без изменения контракта)

### A1. Поле «Источник» не заполнять
Сейчас при создании требования пишется `source: record.source.slice(0, REQUIREMENT_SOURCE_MAX)`.
Поле «Источник» — бизнес-поле (какая компания запрашивала ФТ/НФТ), имена файлов туда попадать не должны.
- При создании требования `source` НЕ передавать (оставить пустым).
- `source` в `aiExtractedRequirementSchema` ОСТАВИТЬ обязательным — это провенанс
  («golden rule»: нет источника — нет требования) и участвует в логах/отсеве. Меняется только populate.

### A2. «Реализация» принудительно «Реализовано»
- Все создаваемые из импорта требования: `implemented: true` всегда, независимо от того, что вернула модель.
- Следствие: `targetQuarter`/`targetYear` не передаются (правило rules.ts: квартал/год только при implemented=false);
  хелпер nextQuarter для импорта больше не нужен — убрать его использование в populate (не ломая другие места).
- Критичность: как сейчас — из модели, дефолт MEDIUM. Не менять.

### A3. 3 попытки получить JSON от AI hub (extraction)
Сейчас при `parseExtractionResponse(content) === null` фрагмент сразу пропускается с warn.
- Для каждого фрагмента: до 3 попыток вызова AI hub, пока ответ не распарсится как JSON-массив.
- Между попытками — warn-лог: `Файл X (фрагмент i/n): ответ не распознан как JSON (попытка k из 3)…`.
- После 3 неудач — текущее поведение (warn «фрагмент пропущен»).
- Ретраи ТОЛЬКО на не-JSON ответ. Сетевые/upstream-ошибки — текущее поведение (fail job), не менять.
- Учесть cancel: проверять cancelRequested между попытками.

## Трек B — сквозной: стадия structure + дерево через AI hub

### B1. Контракт (@po/core)
- `AI_IMPORT_STAGES`: добавить `'structure'` между `'analyze'` и `'aggregate'`:
  `['unpack','analyze','structure','aggregate','populate','done']`.
- Новая Zod-схема ответа структуризации (в ai.ts):
  `aiStructureNodeSchema = { type: REQUIREMENT_TYPES, name: string(1..200), parentName: string().nullable() }`
  (+ тип, + тест в ai.test.ts).
- Прогресс-диапазоны (обновить комментарий у AI_IMPORT_STAGES): unpack 0–5, analyze 5–65,
  structure 65–80, aggregate 80–85, populate 85–100.

### B2. Сервер — этап построения дерева
После analyze (когда `extracted` собран), НОВАЯ стадия `structure`:
- Лог: `Построение древовидной структуры ФТ/НФТ через AI hub…`
- Отдельный system-prompt в `aiImportPrompt.ts` (`buildStructureMessages`): на вход — список всех
  извлечённых требований (type + name, ФТ и НФТ), карта архива (buildArchiveMap уже есть).
  Задача модели: собрать дерево максимально похожее на структуру документации — корневые
  группы-разделы и дети под ними (эталон: проект Jenkins). Ответ — СТРОГО JSON-массив
  `[{"type":"FUNCTION|NFR","name":"...","parentName":"...|null"}]`, по одному элементу на КАЖДОЕ
  переданное требование. Иерархия только внутри одного типа (FUNCTION под FUNCTION, NFR под NFR) —
  таково правило CHILD_OF в графе.
- Если требований много — батчи (напр. по 100 записей на вызов), карта архива в каждом.
- Парсинг ответа с валидацией схемой; до 3 попыток на батч при не-JSON/невалидном ответе (как A3).
- Слияние: parentName из structure-ответа ПЕРЕКРЫВАЕТ parentName из extraction (structure видит весь
  набор целиком, extraction — только фрагмент). Записи, которых нет в ответе / null parent — корневые.
  Защита от самородителя и от родителя другого типа — уже есть в агрегации/интеграции (nameKey, цикл-проверки
  в LinkService) — переиспользовать, не дублировать.
- Если после 3 попыток батч не разобран — warn `Структура для батча не получена — записи останутся корневыми`
  и продолжить (job НЕ фейлить: требования важнее дерева).
- Прогресс: в диапазоне 65–80 по батчам. analyze пересчитать на 5–65.
- Cancel: проверка между батчами.
