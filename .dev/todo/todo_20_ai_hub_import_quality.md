# todo_20 — Корректирующие мероприятия: качество AI-анализа загруженной документации (AI Hub)

## 1. Контекст и проблема

Эталонный кейс: разбор реальной документации `Projects/docsourcecontrol` (Platform V
Works::SourceControl / GitTech) — ~500 файлов (Markdown, JSON release notes, YAML,
изображения), 58 релизных заметок, руководства по ролям, админ- и security-гайды.
Ручной разбор дал **810 ФТ**; текущий AI-импорт портала на слабых моделях выдаёт
кратно меньше и хуже структурированные ФТ/НФТ.

Наблюдаемые причины деградации (по коду `apps/server/src/services/AiImportService.ts`
и `aiImport/*`):

1. **Слабая модель + большой чанк.** Размер чанка (`preset.chunkChars`) фиксирован на
   весь прогон; слабые модели на больших чанках теряют часть фактов и ломают JSON.
2. **Нет structured output.** Ответ парсится из свободного текста
   (`chatWithJsonRetries` + `stripReasoning`); `response_format`/JSON Schema
   OpenAI-совместимого API не используется — на слабых моделях это главный источник
   невалидного JSON.
3. **Upstream-ошибки не ретраятся.** Любая сетевая ошибка/429/5xx (`kind: 'upstream'`)
   валит джобу целиком; на длинных прогонах (сотни вызовов) вероятность сбоя ~1.
4. **Нет чекпоинтов.** Падение на 80% прогона теряет всё; повторный запуск платит
   токены заново (частично спасает только `skippedExisting` на стадии populate).
5. **Нет триажа файлов.** Все файлы равнозначны: release notes (богатый источник ФТ)
   и, например, лицензионные отчёты идут одним потоком; JSON/таблицы скармливаются
   как плоский текст.
6. **Ошибки не «ведут за руку».** `fail(message, hint)` существует, но таксономии нет:
   пользователь видит техническую строку без ответа «что мне теперь сделать».

## 2. Цели

- **Ц1. Полнота:** на эталонном архиве docsourcecontrol извлечение не хуже 80% от
  эталонного реестра (810 ФТ) на «сильной» модели и не хуже 60% на «слабой»
  (замер — по автоматическому сравнению имён/областей, см. A5).
- **Ц2. Живучесть:** прогон из ≥500 AI-вызовов завершается при единичных 429/5xx/
  тайм-аутах без участия пользователя; после аварийного падения возобновляется с
  чекпоинта без повторной оплаты пройденных чанков.
- **Ц3. UX ошибок:** каждая ошибка/деградация показывается человеческим языком с
  конкретным следующим шагом; частичный результат никогда не пропадает молча.

## 3. Мероприятия (объём работ)

### A. Подготовка данных до вызовов модели

- **A1. Инвентаризация и триаж архива.** После unpack строить опись: тип файла
  (md/json/yaml/бинарь), размер, оценка токенов, класс источника
  (`release-notes | user-guide | admin-guide | security | api-spec | config | прочее`).
  **Классификация не должна зависеть от имён каталогов и файлов** — структура
  каждого архива своя. Порядок определения класса: (1) дешёвые контентные признаки
  (структура JSON с полями изменений, таблицы «функция/описание», заголовки
  «Что нового»/«Release notes»/«Руководство…» в любом регистре и языке);
  (2) для неопознанных файлов — LLM-классификация по образцу содержимого (первые
  N строк файла, батчами до 30 файлов за вызов, дёшево даже на слабой модели);
  (3) не удалось классифицировать — класс `прочее`, файл ВСЁ РАВНО обрабатывается
  (просто с базовым приоритетом), а не выбрасывается. Имена путей допустимы только
  как слабый дополнительный сигнал, не как решающее правило. Бинарные и
  нерелевантные файлы (изображения, lock-файлы) исключать с записью в опись, а не
  молча.
- **A2. Format-aware извлечение.** Перед LLM: структурированные форматы
  распознавать **по содержимому (sniffing), а не по расширению или имени файла**:
  JSON с массивами изменений разворачивать в плоские записи детерминированным
  кодом (схему полей определять по фактическим ключам, не по ожидаемым именам
  вида `rn-*.json`); Markdown-таблицы конвертировать в списки «имя — описание»;
  YAML — в пары ключ/значение. Неизвестная структура — файл идёт как обычный
  текст, без падения. LLM получает уже нормализованный текст, а не сырой формат.
- **A3. Приоритизация.** Порядок обработки по классу источника (release notes и
  функции продукта — первыми), чтобы при остановке/бюджетном лимите наиболее ценные
  ФТ уже были извлечены.
- **A4. Предварительный план и смета.** До старта показывать пользователю: сколько
  файлов, примерно сколько чанков/вызовов/токенов, что исключено и почему; требовать
  подтверждения при смете выше настраиваемого порога.
- **A5. Эталонный набор для регрессии качества.** Зафиксировать
  `docsourcecontrol` + эталонный список ФТ (имя/область/источник) как fixture;
  добавить команду сравнения результата прогона с эталоном (полнота/точность) — это
  метрика Ц1 в CI (на мок-модели) и в ручных прогонах.

### B. Конвейер, дружелюбный к слабым моделям

- **B1. Микро-чанки с адаптацией.** Стартовый размер чанка — из пресета, но при
  `finish_reason=length`, невалидном JSON два раза подряд или ошибке контекстного
  окна — автоматически делить чанк пополам (до минимального порога) и повторять.
  Успешные серии постепенно возвращают размер к пресету.
- **B2. Structured output с фолбэком.** Пробовать `response_format: json_schema`
  (или `json_object`) в первом вызове; если бэкенд отвечает ошибкой на параметр —
  запомнить на прогон и работать по текущей схеме «текст + парсер». Схемы на шаг —
  минимальные (см. B3).
- **B3. Один шаг — одна простая задача.** Для слабых моделей упростить схему шага
  analyze до плоского списка `{name, type, description}` без вложенности; иерархию и
  связи выводить отдельными шагами (уже есть structure/relate) с few-shot примерами
  в промпте (1–2 эталонных примера на класс источника из A1).
- **B4. Map-reduce дедупликация.** Слияние результатов чанков — детерминированным
  кодом (нормализация имени + fuzzy-порог), а не моделью; спорные пары (похожие, но
  не идентичные) отправлять модели пачками ≤20 пар с бинарным ответом.
- **B5. Контроль полноты чанка.** После extract сравнивать число извлечённых позиций
  с эвристикой плотности источника (для release notes — числом записей из A2); при
  подозрении на потерю (<50% ожидаемого) — один повторный проход чанка с указанием
  «извлеки ВСЕ записи, сейчас найдено N из ~M».
- **B6. Бюджет прогона.** Настраиваемый лимит вызовов/токенов на джобу; при
  достижении — мягкая остановка с сохранением результата и понятным сообщением
  (см. E2), а не обрыв.

### C. Устойчивость работы с OpenAI-совместимым API

- **C1. Ретраи upstream с backoff.** Классифицировать ошибки клиента: `429`,
  `5xx`, сетевые/таймауты — ретраить с экспоненциальной задержкой и джиттером
  (например 1s → 2s → 4s → 8s, максимум N попыток), уважая `Retry-After`;
  `400 context_length` — не ретраить, а отдавать в B1 на деление чанка; `401/403` —
  немедленный fail с подсказкой про ключ; `404 model` — fail со списком доступных
  моделей, если API их отдаёт.
- **C2. Параллелизм с лимитом.** Обрабатывать чанки пуллом из K параллельных вызовов
  (настройка пресета, по умолчанию консервативно 2–3); при первом 429 — снижать K до
  1 до конца «окна» и постепенно восстанавливать.
- **C3. Тайм-аут на вызов.** Явный per-call timeout (настройка; по умолчанию с
  запасом на thinking-модели) с попаданием в ретраи C1, чтобы зависший запрос не
  подвешивал джобу навсегда.
- **C4. Учёт токенов.** Копить `usage` из ответов; показывать в прогрессе и итоговом
  отчёте (потрачено prompt/completion токенов, средняя цена чанка) — это же источник
  данных для сметы A4.

### D. Чекпоинты и возобновление

- **D1. Чекпоинт после каждого чанка/стадии.** Персистить промежуточный результат
  джобы (extracted-записи, позицию в описи) на диск в каталоге джобы; формат —
  переживающий рестарт сервера.
- **D2. Возобновление.** `resume` для джобы в статусе `failed`/`cancelled`:
  продолжить с последнего чекпоинта, пройденные чанки не переоплачиваются. Кнопка в
  UI рядом с сообщением об ошибке (см. E2).
- **D3. Идемпотентность populate — сохранить и покрыть тестами.** Существующее
  поведение (skip existing, доливка недостающих связей) — зафиксировать как контракт
  и прогонять в тестах resume-сценария.

### E. Ошибки и коммуникация с пользователем (без стресса)

- **E1. Таксономия ошибок.** Единый реестр: код, категория (данные / модель / сеть /
  конфигурация / бюджет), сообщение по-русски без техножаргона, конкретное действие
  («Уменьшите размер чанка в настройках модели», «Проверьте API-ключ в Настройках →
  AI», «Нажмите „Продолжить“ — прогон возобновится с места остановки»), ссылка на
  подробный лог. Технические детали (HTTP-код, тело ответа) — сворачиваемый блок,
  не первая строка.
- **E2. Каждый fail — с планом действий.** Расширить `job.error` полями
  `{ code, category, action, resumable }`; UI показывает: что случилось, что уже
  успели создать (счётчики), какая кнопка что сделает («Продолжить», «Повторить с
  меньшими чанками», «Открыть частичный результат»).
- **E3. Прогресс с содержанием.** В прогрессе джобы: текущий файл/класс источника,
  чанк X из Y, создано ФТ/НФТ, потрачено токенов, оценка оставшегося времени;
  деградации (уменьшили чанк, снизили параллелизм, включили фолбэк-парсер) — как
  warn-события в лог с человеческой формулировкой.
- **E4. Итоговый отчёт качества.** По завершении: покрытие описи (файлов обработано /
  исключено / с ошибками), извлечено по классам источников, сколько чанков прошло с
  повтором B5, где модель «обрезалась» — чтобы PO видел слепые зоны, а не только
  общий счётчик.

### F. Тестирование

- **F1. Мок «слабой модели».** Fixture-клиент, который: рвёт JSON, отвечает с
  `finish_reason=length`, отдаёт 429/500/таймауты по сценарию — юнит-тесты на B1,
  B2, C1–C3, D2 (в `apps/server/test`, по образцу `ai-import-resilience.test.ts`).
- **F2. E2E больших объёмов.** Синтетический архив ≥200 файлов (генератор в
  fixtures) — прогон на мок-модели: чекпоинты, resume после «падения», смета A4,
  отчёт E4.
- **F2b. Инвариантность к структуре архива.** Тот же контент, что в F2, но с
  другой раскладкой: переименованные каталоги/файлы (в т.ч. кириллица и
  «неговорящие» имена вида `doc1/`, `Приложение_3.md`), другая вложенность,
  release notes в другом JSON-диалекте. Результат триажа (A1) и полнота извлечения
  не должны деградировать более чем на 5% относительно F2.
- **F3. Регрессия качества.** Прогон A5-эталона в ручном режиме перед релизом;
  фиксация метрик полноты в отчёте.

## 4. НФТ

- **Н1. Объёмы:** архив до 200 МБ / 2000 текстовых файлов; опись и чанкование —
  потоково, без загрузки всего архива в память (пиковая память сервера ≤ 512 МБ на
  джобу).
- **Н2. Длительность:** прогон эталонного архива на слабой модели — часы, не сутки;
  UI остаётся отзывчивым (джоба асинхронная, как сейчас).
- **Н3. Надёжность:** единичные сбои сети/API не приводят к потере прогона (Ц2);
  сервер можно перезапустить — джоба возобновляема с чекпоинта.
- **Н4. Наблюдаемость:** структурированный лог джобы (уже есть) + счётчики ретраев,
  делений чанков, токенов; выгрузка лога файлом.
- **Н5. Совместимость:** только OpenAI-совместимый Chat Completions API; фичи типа
  `response_format` — строго с фолбэком (B2), ничего не должно ломаться на бэкендах
  без их поддержки (vLLM/Ollama/прокси).
- **Н6. Безопасность:** содержимое документов не логируется целиком (только имена
  файлов/счётчики); API-ключ — как сейчас, не попадает в лог и отчёты.

## 5. Критерии приёмки

1. На эталоне A5: полнота ≥80% (сильная модель) / ≥60% (слабая) — отчёт сравнения
   прилагается к прогону.
2. Сценарий «500 вызовов, из них 5% отвечают 429/500/таймаут» (мок F1) завершается
   успешно без действий пользователя.
3. Kill сервера на середине прогона → рестарт → «Продолжить» → джоба доходит до
   конца; повторно созданных ФТ/связей нет, пройденные чанки не вызывались повторно.
4. `400 context_length` на чанке → чанк автоматически делится, прогон продолжается,
   в логе — warn с человеческой формулировкой.
5. Любой fail джобы показывает: код, причину по-русски, следующее действие и счётчики
   уже созданного; кнопка действия работает.
6. Прогон на бэкенде без `response_format` работает не хуже текущего поведения.
6b. Прогон F2b (тот же контент, другая раскладка и имена) даёт полноту в пределах
   5% от F2; в отчёте E4 классы источников определены по содержимому, файлы класса
   `прочее` обработаны, а не пропущены.
7. Все новые ветки покрыты юнит-тестами (порог покрытия core ≥90% не нарушен), e2e
   F2 зелёный в CI.

## 6. Вне объёма

- Смена протокола (Assistants API, streaming, embeddings/RAG) — отдельное ТЗ.
- Автоматическая оценка критичности извлечённых ФТ.
- Мультиязычное извлечение (сейчас — русский/английский исходник → русские ФТ/НФТ).
- Изменения ванильного чат-виджета вне сценария импорта.
