## Мероприятия (согласовано PO 2026-08-04)

### M1. Батчинг мелких файлов (backend)
Файлы одного класса источника, каждый меньше остатка фрагмента, паковать в общий
фрагмент до `preset.chunkChars` (с разделителями «=== Файл: path ===»; provenance
записей сохраняется по файлам). Большие файлы — как сейчас. Ожидание: 200+ одиночных
вызовов → десятки. Лог и прогресс показывают «фрагмент X из Y (N файлов)»; отчёт
покрытия по классам не деградирует.

### M2. Контроль полноты — только там, где он честный (backend)
- Применять ТОЛЬКО к классу release-notes (как в спеке todo_20 П3.5/B5).
- Не более одного повторного прохода на фрагмент (подтвердить/зафиксировать тестом).
- Не запускать повтор, если первый проход дал 0 записей, а класс не release-notes.
- expectedRecords из md-таблиц не считать ожиданием для не-RN классов.

### M3. Честные счётчики и остановка (backend + frontend)
- Контракт: в result/view добавить `extractedFunctions`, `extractedNfrs`
  (извлечено, ещё не записано) — заполняются по ходу analyze из чекпоинта.
- Прогресс UI: рядом с «создано» показывать «извлечено (ждёт записи): N ФТ, M НФТ».
- Сообщение остановки/ошибки: если extracted > created — явная строка «Извлечено N
  записей — они сохранены в контрольной точке; „Продолжить“ доведёт до создания».
- Инкрементальный populate — ВНЕ объёма (отдельное ТЗ; риски целостности/дублей).

### M4. Быстрее восстанавливаться после сбоев (backend)
- Первый повтор после per-call тайм-аута — короткий (не полный 120с бюджет ожидания
  заново, а backoff от 15–30с; сам тайм-аут вызова не менять).
- Восстановление параллелизма после деградации — быстрее (например, после 3 подряд
  успехов +1 к K до пресета; сейчас фактически остаётся 1 до конца прогона).
- Диагностика в лог: текущий эффективный K при изменениях.

### M5. Пульс инвентаризации (backend)
На стадиях распаковки/описи/классификации — INFO-строки прогресса не реже чем раз
в ~15с (файлов просмотрено / классифицировано батчей), чтобы не было минут тишины.

## Критерии приёмки

1. На синтетическом архиве из ≥100 мелких файлов одного класса число extraction-вызовов
   ≤ ceil(суммарный размер / chunkChars) + число больших файлов (тест).
2. Повторный проход не запускается: для не-RN классов при 0 извлечённых; больше
   1 раза на фрагмент — никогда (тесты).
3. В прогрессе и при остановке видны extracted-счётчики; сообщение остановки при
   extracted>0 и created=0 содержит «сохранены в контрольной точке» (unit + e2e).
4. После таймаут-деградации K восстанавливается до пресета за ≤N успешных вызовов (тест).
5. Стадия инвентаризации пишет прогресс (тест на наличие строк).
6. Все гейты качества зелёные; смета/отчёт/resume todo_20 не регрессируют.

## Вне объёма
