# task25 — Редактирование разметки на шаге «Выверка» AI-импорта бэклога

## Требование (PO, 2026-08-04)

В таблице соответствий шага выверки (модалка «AI-импорт бэклога», статус
`awaiting-review`) дать возможность до записи:
1. **«Бизнес-имя»** — редактировать имя будущего требования.
2. **«Узел (куда встроится)»** — переопределить родительский узел: поиск по
   существующим узлам дерева ИЛИ создание нового узла со своим именем.
3. **«Target» → переименовать в «Срок реализации»** — переопределить квартал и год
   для конкретной строки.

## Контракт (@po/core, обратная совместимость)

`aiBacklogApplyBodySchema` расширяется опциональным полем:

```
overrides?: Record<rowId, {
  businessName?: string (1..200, trimmed),
  parent?: { kind: 'existing', name: string }        // точное имя узла из дерева
          | { kind: 'new', name: string (1..200) },  // новый КОРНЕВОЙ узел (v1)
  targetQuarter?: TargetQuarter,  // пара: оба или ни одного
  targetYear?: number (2020..2100),
}>
```

- `rowIds` — как раньше (выбранные строки); overrides применяются только к строкам
  из rowIds; override для невыбранной/неизвестной строки → 400.
- Сервер мерджит overrides в mappings ДО populate:
  - `parent.kind='existing'`: имя валидируется по реальному дереву С УЧЁТОМ ТИПА
    строки (CHILD_OF только внутри типа); не найден → 400 с именем узла и rowId;
  - `parent.kind='new'`: узел создаётся корневым, тип = типу строки; имя проходит
    ту же нормализацию/дедуп, что узлы модели (совпадение с уже предлагаемым новым
    узлом → тот же узел, не дубль);
  - `businessName`: та же валидация, что у имени требования; коллизии — существующий
    суффикс-механизм populate;
  - target-пара валидируется как в контракте требования.
- Отчёт (`backlogReport`/таблица соответствий) отражает итоговые (отредактированные)
  значения автоматически — он строится из смердженных mappings.
- Чекпоинт: применённые overrides сохраняются (идемпотентный повторный apply
  после сбоя populate использует те же значения).

## UI (шаг выверки, AiBacklogImportModal)

1. **Бизнес-имя**: клик по значению (или иконка ✎) → инлайн-`input` в ячейке;
   Enter/blur сохраняет в локальное состояние, Esc отменяет; пустое имя не
   сохраняется (валидация с подсказкой). Отредактированное значение помечается
   (например, точка/бейдж «изменено»).
2. **Узел (куда встроится)**: кнопка в ячейке открывает поповер/малый диалог:
   - поле поиска по существующим узлам дерева НУЖНОГО ТИПА (список — из
     `GET /api/projects/:id/requirements`, фильтр по подстроке, регистронезависимо);
   - вариант «Создать новый узел: „<введённый текст>“» (когда текст не пустой);
   - выбор проставляет parent-override; отметка «изменено»; сброс к предложению
     модели (кнопка «вернуть предложенное»).
3. **«Срок реализации»** (переименованная колонка Target): в ячейке — компактные
   селект квартала (Q1–Q4) и инпут года; префилл текущим значением строки;
   изменение = override; 📄-маркер «из файла» остаётся, пока значение не
   переопределено (после — маркер «изменено»).
4. Кнопка «Записать в проект (N)» отправляет `{rowIds, overrides}` (overrides —
   только для реально изменённых строк).
5. Дубли (disabled-строки) не редактируются.
6. Сохранение локальных правок при переоткрытии шага из истории НЕ требуется (v1):
   правки живут в состоянии модалки до apply.

## Критерии приёмки

1. Изменение бизнес-имени доезжает до созданного требования (API-проверка).
2. Переопределение узла на существующий: требование создаётся под ним; на новый —
   узел создан корневым с заданным именем, строка под ним.
3. Переопределение срока: у созданного требования target = введённые квартал/год.
4. Невалидные overrides (несуществующий existing-узел, пустое имя, год вне
   диапазона) → 400 с понятным текстом, шаг выверки не ломается.
5. Отчёт показывает отредактированные значения.
6. Обратная совместимость: apply без overrides работает как раньше (регрессия
   зелёная); старые клиенты не ломаются.
7. Колонка называется «Срок реализации» во выверке и отчёте.

## Вне объёма
Родитель для нового узла, создаваемого вручную (v1 — только корневой);
персистенс недоприменённых правок; массовое редактирование.
