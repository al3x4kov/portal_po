# Task 14 — валидность дерева ФТ/НФТ/связей из AI-импорта (аудит после задачи 13)

Цель: максимально валидные ФТ/НФТ и CHILD_OF-связи относительно подгруженной документации.
Прогресс-бар/стадии НЕ меняются (контракт AI_IMPORT_STAGES остаётся), фронт не затрагивается.
Затронуто: `packages/core/src/validation/ai.ts` (константы), `apps/server/src/services/{AiImportService,aiImportPrompt}.ts` + тесты, `e2e/` (мок + актуализация).

## B1. Токен-бюджет structure-вызова (БАГ — обязательный фикс)
Сейчас structure-вызов идёт с общим `AI_IMPORT_MAX_TOKENS = 2000`, а JSON-ответ на батч из
100 узлов — ~3000–5000 токенов (кириллица). Ответ обрезается → не парсится → 3 ретрая с тем же
лимитом → «Структура для батча не получена» на любом крупном проекте.
- Новая константа в core ai.ts: `AI_IMPORT_STRUCTURE_MAX_TOKENS = 4000` (+ комментарий с арифметикой).
- `AI_IMPORT_STRUCTURE_BATCH` уменьшить до 50 (вынести в core рядом с остальными константами импорта,
  если сейчас в сервере — перенести; server override `deps.structureBatch` для тестов оставить).
- `chatWithJsonRetries` принимает `maxTokens` параметром (extraction — как было 2000, structure — 4000).

## B2. Salvage обрезанного/грязного JSON
- `extractJsonArray`: если ни один кандидат не парсится, попытаться восстановить массив,
  обрезанный на середине объекта: взять текст от первого `[`, найти последний полный `}`,
  закрыть `]`, распарсить. Восстановление — последний кандидат (после существующих).
- Детект обрезки: если у ответа `finish_reason === 'length'` (choices[0].finish_reason),
  писать warn в лог джобы: «ответ модели обрезан по лимиту токенов…» (и для extraction, и для
  structure). `chatWithJsonRetries` должен получать finish_reason из ответа.
- Unit-тесты: восстановление массива с недописанным последним объектом; мусор до/после; ничего
  не восстановилось → null (как раньше).

## B3. Полный контекст родителей в каждом structure-батче (анти-фрагментация)
Сейчас батч видит только свои ~50–100 имён → родитель из другого батча невозможен, дерево рвётся.
- В user-сообщение КАЖДОГО батча добавить компактный полный список всех требований
  («Полный список требований (допустимые родители)» — только имена по типам), с бюджетом
  символов (константа, например 4000 chars; при превышении — обрезка с «…и ещё N»).
- В system-prompt: «parentName выбирай из полного списка; узлы верни только для требований
  из секции "Батч"».
- Ответные узлы по-прежнему ожидаются только для элементов батча; лишние — см. B5.

## B4. Провенанс в structure-вызове (главный сигнал качества дерева)
- `StructureItem` расширить полем `source` (провенанс «файл § раздел» из extraction; у записи он
  обязателен). Строки батча: `TYPE\tимя\tисточник`.
- System-prompt: «группируй по файлам/разделам из поля источника: требования одного файла/раздела —
  под общим корнем-разделом; структура дерева должна повторять структуру документации».
- ВНИМАНИЕ: e2e-мок (e2e/tests/helpers/ai-stub.ts) парсит строки `TYPE\t<имя>` — QA-агент обновит
  под третье поле. Формат зафиксировать в отчёте для QA.

## B5. Отчёт покрытия structure-ответа (логирование)
После каждого успешного батча считать и логировать:
- узлы ответа, не соответствующие ни одному извлечённому требованию (по nameKey) — warn
  «посторонних узлов проигнорировано: P» (сейчас молча попадают в map и не используются —
  заодно НЕ класть их в structureParentByKey);
- требования батча без узла в ответе — warn «без узла в ответе: Q (останутся корневыми)»;
- конфликт: два узла на одно (тип, имя) с разными parentName — первый выигрывает, warn.

## B6. Валидация дерева перед populate
После слияния structureParentByKey → перед агрегацией:
- разрыв циклов (A→B→…→A): пройти цепочки родителей, у узла, замыкающего цикл, убрать родителя,
  warn «цикл разорван: «X» становится корневым» (детерминированно; чистая функция + unit-тесты);
- родитель другого типа: сейчас ищется только nameKey(тип_записи, parentName) и падает в общий
  «родитель не найден». Если имя существует у ДРУГОГО типа — отдельный warn «родитель «Y» имеет
  другой тип — иерархия допустима только внутри одного типа; пропущена»;
- сводка дерева в лог (info) в конце стадии structure: «Дерево: ФТ — X корней, Y с родителем;
  НФТ — A корней, B с родителем; максимальная глубина D».

## B7. Best-effort на последней попытке structure
`parseStructureResponse` строгий (1 невалидный узел → null → ретрай). На ПОСЛЕДНЕЙ (3-й) попытке
принимать валидные узлы, отбрасывая невалидные с warn «принято N из M узлов, невалидных отброшено K»
(вместо полной потери батча). Реализация: parse-функция с режимом strict/lenient или отдельный
parseStructureResponseLenient; chatWithJsonRetries — хук на последнюю попытку (аккуратно, не
ломая extraction-поведение).

## B8. Ретрай extraction при «массив есть, но все записи невалидны»
Ответ с массивом, где `items.length === 0 && (droppedNoSource + droppedInvalid) > 0` — это сбой
формата, считать неудачной попыткой (ретрай как не-JSON, warn «попытка k из 3»). Реально пустой
`[]` (массив длины 0) — валидный ответ «требований нет», НЕ ретраить.

## B9. Стартовый лог объёма
После подсчёта фрагментов, до первого вызова: info «Модель: <model>. Файлов: N, фрагментов: M.»
При 0 извлечённых требований стадию structure проходить без вызовов к hub (лог «Структурировать
нечего — требования не извлечены.»), не слать пустой батч.

## Тесты
Unit (TDD): все пункты B1–B9 (обрезанный JSON, батч 50/4000, полный список родителей в сообщении,
source в строках, посторонние/недостающие узлы, цикл, родитель другого типа, сводка дерева,
lenient на 3-й попытке, ретрай all-invalid, стартовый лог, 0 требований без вызовов).
E2E (QA, зона e2e/): обновить ai-stub под формат `TYPE\tимя\tисточник` и секцию полного списка;
существующие сценарии зелёные; +1 сценарий: warn покрытия или сводка дерева видна в ai-import-log.
