# ADR-001 — Формат хранения требований: переход на OpenSpec + судьба `id`

Статус: **Принято** · 2026-07-01 · Автор: Архитектор
Закрывает: todo_1 A1 (исх. 1), частично A6 (коллизия «удаление id ↔ связи по targetId»).

## Контекст

Сейчас каждое требование хранится как `requirements/<ULID>.md` с YAML-frontmatter
(`id,type,name,criticality,implemented,targetQuarter,targetYear,links,createdAt,updatedAt`)
и телом-описанием. Связи — реципрокные пары `{ type, targetId: <ULID> }` в **обоих** файлах.

Задача: перейти к формату **OpenSpec** (Fission-AI) — один файл на ФТ/НФТ, и решить,
нужен ли `id` (если не важен — убрать). Данных на диске нет → миграция не требуется.

### Что такое OpenSpec (реальный формат)

- Каталог `openspec/` с `specs/<capability>/spec.md` (текущая истина) и `changes/` (дельты).
- Требование: заголовок `### Requirement: <name>`, тело с RFC-2119 (`SHALL/MUST/SHOULD/MAY`).
- Сценарий: `#### Scenario: <name>` с булитами `- GIVEN / WHEN / THEN / AND`.
- Дельты в `changes/<name>/specs/.../spec.md` секциями `## ADDED|MODIFIED|REMOVED Requirements`.

**Расхождение с нашей моделью:** OpenSpec группирует *несколько* требований в один
`spec.md` на capability; приложение же управляет **одним требованием на файл** (единица
CRUD в UI). Мы принимаем **гибрид** (см. решение) и честно фиксируем отклонение.

## Решение

### 1. Раскладка внутри проекта

```
<project>/
  openspec/
    project.md                 # манифест: name, schemaVersion, createdAt (frontmatter)
    specs/
      functions/               # domain = тип требования
        <slug>.md              # одно ФТ = один файл
      nfr/
        <slug>.md              # одно НФТ = один файл
    changes/                   # [задел] дельты правок; в MVP не заполняется UI
```

Каждый `<slug>.md` — самодостаточный фрагмент OpenSpec: заголовок `### Requirement:`,
метаданные, тело-описание, опциональные `#### Scenario:`.

### 2. Судьба `id` — заменяем ULID на человекочитаемый **slug**

Прямой ответ на «нужен ли id»: **непрозрачный ULID не нужен**, но полностью убирать
идентификатор **нельзя** — связи (`links[].targetId`) адресуют требование, и ссылка по
изменяемому `name` ломается при переименовании и нечитаема в файле. Поэтому:

> Вводим **`slug`** — стабильный, человекочитаемый идентификатор, уникальный в
> (project × type), **неизменяемый** после создания (переименование отображаемого
> `name` не меняет slug). Slug = имя файла и цель связи.

- Генерация: транслитерация/кебаб от `name` при создании (`Авторизация по SSO` →
  `avtorizaciya-po-sso`); при коллизии — суффикс `-2`, `-3`.
- Связь становится читаемой: `- CHILD_OF: user-registration` вместо `targetId: 01J9Y...`.
- Уникальность slug в (project × type) — уже гарантируется правилом уникальности `name`
  (2.4.1) плюс дедуп-суффикс.

Итог: закрывает интент «убрать лишний id», **сохраняя целостность связей** (коллизия из
A6 разрешена). `createdAt/updatedAt` остаются (системные), `type` выводится из папки.

### 3. Формат файла требования (пример)

```markdown
### Requirement: Авторизация по SSO
- criticality: HIGH
- implemented: false
- target: Q3 2026

Продукт **SHALL** поддерживать вход через корпоративный SSO (OIDC).

#### Scenario: Успешный вход
- GIVEN сконфигурирован OIDC-провайдер
- WHEN пользователь выбирает «Войти через SSO»
- THEN создаётся сессия и происходит редирект на дашборд

#### Links
- CHILD_OF: sistema-avtorizacii
- RELATES_TO: audit-log
```

- Метаданные (criticality/implemented/target) — булиты под заголовком (парсятся строго).
- `target: Q<n> <year>` присутствует **только** при `implemented: false` (правило 2.4).
- `#### Links` — реципрокные пары, значение = `slug` цели. Тело до `#### Scenario/Links` —
  описание (markdown, ≤5000). Сценарии опциональны (новая возможность OpenSpec-формата).

### 4. Что меняется в коде (`@po/core`)

- `Requirement.id: string (ULID)` → `Requirement.slug: string`; `Link.targetId` → `targetSlug`.
- `md/markdown.ts`: `serialize/parse` переписать под OpenSpec-разметку (не frontmatter).
  Round-trip обязан оставаться **без потерь** (существующий инвариант тестов).
- `graph/*` (uniqueness, integrity, cascade) — работают по `slug` вместо `id`.
- Новый модуль `slug.ts`: генерация + дедуп + валидация (только `[a-z0-9-]`).
- Сервер: `FsRequirementRepo` путь `openspec/specs/{functions|nfr}/<slug>.md`;
  `FsProjectRepo` манифест `openspec/project.md`.

## Последствия / риски

- **Плюс:** файлы читаемы человеком и ИИ-агентом без парсера; связи наглядны; нет опаковых ID.
- **Минус:** парсинг строже (не YAML). Нужны тесты на «битые» файлы (ручная правка вне UI).
- **Отклонение от строгого OpenSpec:** один файл = одно требование (не capability). Задел
  `changes/` в MVP не используется UI — оставляем каталог для будущей истории правок.
- Slug-переименование: смена `name` не трогает slug → возможна «рассинхронизация» имени и
  файла со временем. Допустимо (slug — техническая стабильная ручка), в UI показываем `name`.
