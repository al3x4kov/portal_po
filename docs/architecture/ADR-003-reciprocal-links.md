# ADR-003 — Реципрокное (взаимно-обратное) хранение связей

Статус: **Принято** · 2026-07-02 · Автор: Архитектор
Связано: ADR-001 (адресация цели по slug), ADR-004 (атомарность многофайловой записи),
ARCH-1 / BE-7 (целостная запись пары).

## Контекст

Между требованиями существуют связи (`PARENT_OF`, `CHILD_OF`, `RELATES_TO`, `DEPENDS_ON`,
`BLOCKED_BY`). Источник истины — файлы `.md` на диске, отдельный файл на каждое требование
(ADR-001). Нужно решить, где хранить связь между A и B: только в одном файле (с
вычислением обратной стороны через индекс) или в обоих.

## Решение

Связь хранится в **обоих** файлах как взаимно-обратная пара:

- A: `PARENT_OF B` ↔ B: `CHILD_OF A`;
- A: `DEPENDS_ON B` ↔ B: `BLOCKED_BY A`;
- `RELATES_TO` симметрична (`RELATES_TO` в обоих файлах).

Цель связи адресуется по **slug** (ADR-001), а не по имени файла-с-расширением или ULID:
`- CHILD_OF: sistema-avtorizacii`.

**Обоснование:** каждый файл самодостаточен — человек или ИИ-агент читает требование и
сразу видит все его связи (и вверх, и вниз, и вбок) без построения глобального индекса
и без обхода всех файлов проекта. Это соответствует принципу «файл — источник истины,
читаемый без парсера-агрегатора».

## Последствия / риски

- **Плюс:** самодостаточность файла; наглядность связей при ручном/агентном чтении;
  отсутствие отдельного индекс-файла как второго источника истины.
- **Риск (ключевой):** одна логическая связь = запись в двух файлах. Если записать только
  одну сторону — получаем одностороннюю или висячую связь и рассинхрон. Поэтому запись
  пары должна быть **целостной**: обе стороны применяются вместе, при сбое — откат
  (см. ADR-004, ARCH-1 / BE-7). Аналогично при удалении требования — каскадная чистка
  обратных ссылок в связанных файлах.
- Ссылка на несуществующий slug (после ручной правки вне UI) → нарушение целостности;
  выявляется проверкой при загрузке, битый файл помечается, проект не роняется.
- **Остаточный риск висячих обратных ссылок в «битых» файлах `[ДОБАВЛЕНО 2026-07-07 — ARCH-10]`:**
  каскадная чистка обратных ссылок при удалении требования (`RequirementService.delete`/
  `cascadeUnlink`) сознательно **не трогает broken-файлы** (их нельзя безопасно перезаписать).
  Поэтому обратная ссылка `targetSlug` из повреждённого файла на удалённое требование остаётся
  **висячей** и невидимой для каскадной чистки. Это известное ограничение: пользователь узнаёт о
  висячих ссылках через пометку **broken** в UI (панель «Битые файлы требований», SA-4) и отчёт
  целостности; путь устранения — ручная правка/удаление битого файла во внешнем редакторе (починка
  «сырого» MD — вне приложения, §1.4). Автоматическая чистка ссылок в битых файлах в MVP не
  выполняется (принятое ограничение).
