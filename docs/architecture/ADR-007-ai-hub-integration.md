# ADR-007 — AI Hub как внешняя интеграция (чат, генерация описаний, AI-импорт)

Статус: **Принято** · 2026-07-07 · Автор: Совет (`/council`) + PO
Связано: `project.md` (§1.2 роли, §1.4 вне скоупа, FR-17…FR-21, NFR-10),
[`context.md`](../overview/context.md) (актор «Внешний LLM-провайдер»),
[`arch.md`](../overview/arch.md) §6.3, [`api.md`](api.md) (AI-эндпоинты),
ADR-005 (single-process), ADR-006 (версионирование REST).

## Контекст

Продукт получил подсистему **AI-ассистирования** поверх доменного ядра: чат-помощник,
генерация описания требования и **AI-импорт требований из архива документации**. Все три
функции обращаются к **внешнему OpenAI-совместимому сервису — «AI Hub»** (сеть, секрет-ключ,
длинные асинхронные операции). Это первая и единственная **исходящая** сетевая зависимость
приложения, которое в остальном локально и работает с файлами (`arch.md` §1, ADR-005).

Ранее интеграция существовала только в коде (`apps/server/src/routes/ai.ts`,
`routes/aiImport.ts`, `services/AiHubService.ts`, `AiImportService.ts`, `openaiClient.ts`,
`repositories/AiConfigRepo.ts`) и не была отражена ни в `arch.md`, ни в ADR — «машинное
отделение» разошлось с «пентхаусом». Настоящий ADR фиксирует решение и его компромиссы.

Продуктовое позиционирование (кто основной пользователь, приоритет фич) — в `project.md`
§1.2/§1.4/§9. Здесь — **архитектура интеграции и её риски**.

## Решение

**(а) AI Hub — внешний OpenAI-совместимый провайдер, конфигурируемый пользователем.**
`baseURL`, `apiKey` и параметры модели задаются PO на странице AI и хранятся в конфиге
проекта (см. «в»). Используются только два вызова провайдера: `models.list()` и
`chat.completions.create()` (`AiHubService.ts`). Хардкода эндпоинта нет — `baseURL` всегда из
сохранённого конфига.

**(б) Три сценария использования, что уходит наружу:**
- **Чат** (`POST /api/ai/chat`) — системный промпт + последние ≤20 сообщений истории.
- **Генерация описания** (`POST /api/ai/generate-description`) — имя/тип/критичность/текущее
  описание требования + имя и описание проекта + подсказка пользователя.
- **AI-импорт** (`POST /api/projects/:id/ai-import`) — **содержимое файлов документации**
  из загруженного архива (чанками), карта путей архива, затем типы/имена/провенанс
  извлечённых требований. Наружу уходит реальный текст документации и требований.

**(в) Хранение конфига и ключа — файл в границах `PROJECTS_ROOT`.**
`AiConfigRepo` хранит настройки в `.ai-config.json` (`baseURL`, `model`, `modelPresets`,
`apiKey`). Ключ хранится **в открытом виде** (plaintext), файл — вне архивов экспорта и в
`.gitignore`. Наружу через API ключ **не возвращается** (`GET /api/ai/config` отдаёт только
`hasApiKey: boolean`); из логов и текстов ошибок ключ редактируется (`sanitize`).

**(г) Асинхронный контракт AI-импорта (long-running job).**
Импорт — единственная длинная операция: `POST …/ai-import` возвращает `jobId` (accepted),
клиент опрашивает `GET /api/ai-import/:jobId` (поллинг ~800 мс), есть отмена. Реестр джоб —
**in-memory, в рамках одного процесса** (`AiImportJobs`). Отсюда семантика (детализируется в
ARCH-4): при рестарте/краше процесса прогресс и лог джобы **теряются** (последующий опрос →
`NOT_FOUND`); частично созданные требования остаются на диске; повторный запуск импорта
**идемпотентен по смыслу** (доливает недостающее, а не дублирует). Импорт **не является одной
транзакцией**: каждая запись требования берёт project-lock пооперационно (ADR-004), между
шагами возможны чужие правки.

**(д) Устойчивость вызова.** Пер-попытка таймаут `AI_HUB_TIMEOUT_MS = 40 000` мс,
`AI_HUB_MAX_RETRIES = 1` (худший случай одного вызова ≤ ~80 с). Параметры модели — через
пресеты (`temperature`, `maxOutputTokens`, `chunkChars`, `reasoning`) с дефолтами по id
модели и generic-фолбэком; фактический бюджет клампится `min(лимит сценария, preset)`.

**(е) Деградация.** Ядро продукта (CRUD требований, дерево, импорт/экспорт архивов, MCP,
OpenSpec) **не зависит** от AI Hub и работает офлайн. При недоступности провайдера деградируют
только AI-функции: ошибка доходит до UI как `{code,message}` без падения приложения.

## Семантика import-job (ARCH-4)

Реестр `AiImportJobs` — **in-memory, единый локальный процесс, без очереди** (решение PO §3.3).
Зафиксированная семантика (реализация `apps/server/src/services/AiImportJobs.ts`):

- **Состояния:** `running → succeeded | failed | cancelled` (`AiImportStatus`); стадия (`stage`)
  и `progress` обновляются по ходу; вид для клиента — `AiImportJobView` (`GET /api/ai-import/:jobId`).
- **Одна активная джоба на проект:** повторный `POST …/ai-import` при уже выполняющейся джобе того
  же проекта → `409 CONFLICT` (`ConflictError`).
- **TTL завершённых:** `AI_IMPORT_JOB_TTL_MS = 30 мин`. После завершения джоба хранится 30 минут
  (клиент успевает прочитать исход), затем удаляется **ленивой очисткой** (`sweep` при следующем
  обращении — таймеров нет, утечки нет). `now` инъектируется → детерминированные TTL-тесты.
- **Поведение клиента при отсутствующем/просроченном/после-рестарт job:** `get()` возвращает
  `undefined` → роут отвечает **`404 NOT_FOUND`**. При рестарте/краше процесса **всё состояние
  джоб теряется** (in-memory), поэтому `jobId`, выданный до рестарта, после него → `404`.
- **Частичные данные:** импорт **не является одной транзакцией** — каждая запись требования идёт
  под своим project-lock (ADR-004), поэтому при обрыве/краше уже созданные требования **остаются
  на диске**. Повторный запуск импорта **идемпотентен по смыслу** (доливает недостающее, не
  дублирует), что нивелирует частичный результат.
- **Отмена:** `POST …/:jobId/cancel` выставляет `cancelRequested`; раннер честит его **на границе
  чанка** (не мгновенно), затем джоба → `cancelled`.

**Задел на персистентность (обоснование «почему не сейчас»):** для локального single-user demo
персистентность прогресса между рестартами **не требуется** — потеря состояния джобы компенсируется
идемпотентным повторным запуском, а данные уже на диске целостны пофайлово. Персистентный
прогресс/резюмируемость — явный кандидат при переходе к Electron/долгоживущему процессу (частые
рестарты окна), но вне текущего MVP. Штатное завершение фоновой джобы при остановке процесса —
ARCH-8 (graceful shutdown).

## Принятый риск (осознанное решение PO, 2026-07-07)

Приложение запускается **локально на личных машинах для показа MVP** и **не разворачивается в
реальный продакшн**. С учётом этого следующие свойства AI-канала приняты **как есть** и в MVP
намеренно не усиливаются:

1. **API-ключ в открытом виде** в `.ai-config.json` (без шифрования/keychain).
2. **Проверка TLS-сертификата AI Hub отключена по умолчанию.** `buildAiDispatcher`
   (`openaiClient.ts`): при отсутствии `AI_HUB_CA_CERT` `rejectUnauthorized=false` по
   умолчанию (чтобы работать за внутренним корпоративным CA «из коробки»); включить проверку —
   `AI_HUB_INSECURE_TLS=0` или указать `AI_HUB_CA_CERT`. Настройка **scoped только на AI Hub**,
   глобальное TLS-поведение Node не меняется.
3. **Содержимое требований и документации отправляется внешнему провайдеру** — приемлемо для
   демонстрационных данных.

**Условие пересмотра:** если сценарий изменится (реальные пользователи, внешний хостинг,
чувствительные данные) — этот риск закрывается **первой волной**: secure-by-default TLS,
защита/шифрование ключа, NFR приватности AI-канала (задачи совета ARCH-2, BE-8, SA-2).

## Env-переменные интеграции

| Переменная | Назначение | Дефолт |
|---|---|---|
| `AI_HUB_CA_CERT` | путь к PEM CA для доверия внутреннему корню | не задан |
| `AI_HUB_INSECURE_TLS` | проверка TLS AI Hub (`0`/`1`) | **insecure**, если нет `AI_HUB_CA_CERT` |
| `AI_HUB_PROXY` / `HTTPS_PROXY` | HTTP(S)-прокси для запросов к AI Hub | не задан |

`baseURL`/`apiKey`/`model`/`modelPresets` берутся **не из env**, а из сохранённого конфига.

## Последствия / риски

- **Плюс:** интеграция и её границы теперь зафиксированы; новый разработчик/агент видит, что
  уходит наружу, где секрет, как деградирует продукт; async-контракт импорта задокументирован
  и попадает в OpenAPI (ARCH-7).
- **Минус / риск:** принятые риски (п. 1–3) реальны и допустимы **только** для локального demo;
  контроль условия пересмотра — на PO. Неатомарность и in-memory-состояние импорт-джобы
  (ARCH-4) обостряются под будущей Electron-обёрткой (частые рестарты).
- **Долг (вне этого ADR, отдельные задачи совета):** ARCH-4 (персистентность/семантика job),
  BE-1 (god-класс `AiImportService`), ARCH-7 (AI-эндпоинты в OpenAPI).
