# ADR-002 — MCP-сервер как тонкая обёртка поверх доменных сервисов

Статус: **Принято** · 2026-07-02 · Автор: Архитектор
Связано: ADR-001 (slug, OpenSpec), `docs/architecture/api.md` (список tools), `PLAN-dorabotka.md` A3, ARCH-4 (единый источник zod-схем), ARCH-11 (structured details ошибок).

## Контекст

Требования как источник истины должны быть доступны не только человеку через веб-UI,
но и ИИ-агентам. Для этого вводится второй канал доступа — MCP-сервер (`apps/mcp`,
`@po/mcp`, `@modelcontextprotocol/sdk`, транспорт stdio). Возникает вопрос: агент должен
ходить в существующий REST (HTTP-клиент внутри MCP) или напрямую в доменные сервисы?
REST-обёртка добавила бы сетевой слой, второй процесс-зависимость, дублирование
маппинга ошибок и рассинхрон контрактов.

## Решение

MCP-tools вызывают те же сервисы `@po/server`/`@po/core` **напрямую**, без обращения к
REST по HTTP. MCP и REST — два тонких адаптера над одним сервисным ядром.

- **Валидация входов** — те же zod-схемы из `@po/core` (единый источник правил, ARCH-4);
  енумы (`RequirementType`, `Criticality`, `LinkType`) не дублируются в MCP.
- **Read-tools** (`list_*`, `get_*`) — без сайд-эффектов; пустой результат — это `[]`,
  а не ошибка.
- **Write-tools** (`create/update/link/delete/export`) — возвращают итоговое состояние
  требования (или факт удаления), чтобы агент видел применённый результат без доп. чтения.
- **Ошибки домена** (`UNIQUENESS`, `CYCLE`, `SELF_LINK`, `MULTIPLE_PARENT`, `HAS_CHILDREN`,
  `VALIDATION`, `NOT_FOUND`, …) маппятся в MCP error-result (`isError: true`), а не в
  необработанное исключение; structured details сохраняются (напр. `CycleError.path`,
  ARCH-11).
- Общий корень данных — `PROJECTS_ROOT` (env), тот же, что у REST-сервера.

Полный список tools и сигнатуры — в `docs/architecture/api.md`.

## Последствия / риски

- **Плюс:** единый контракт REST/MCP — правила уникальности, циклов, slug (ADR-001)
  соблюдаются одинаково в обоих каналах; нет сетевого хопа и CORS внутри MCP.
- **Минус:** MCP жёстко связан с сигнатурами сервисного слоя `@po/server`/`@po/core` —
  изменение фасада ломает оба адаптера. Митигация: сервисный фасад стабилизирован и
  считается публичным контрактом, покрыт тестами на регистрацию tools и маппинг ошибок.
- MCP — отдельный процесс на том же `PROJECTS_ROOT`, что и REST → см. модель
  конкурентности в ADR-004.

## Дополнение `[ARCH-9]` — сервисный фасад как публичный контракт

Над доменным ядром теперь три адаптера: REST-роуты, MCP-tools и `AiImportService`.
Ранее все они зависели от КОНКРЕТНЫХ классов сервисов; изменение сигнатуры ломало
сразу трёх потребителей без явного контракта. Введены стабильные интерфейсы-фасады
`RequirementServicePort` / `LinkServicePort` / `ProjectServicePort`
(`apps/server/src/services/ports.ts`), которые покрывают ровно ту публичную
поверхность, что вызывают адаптеры (не больше). Классы сервисов `implements` эти порты
(проверка компилятором), фабрики `factory.ts` возвращают порт-тип, а адаптеры
(`serviceFor` в роутах, `AiImportServiceDeps.makeRequirementService/makeLinkService`,
типы стадий AI-импорта, MCP `reqService`/`linkService`) типизированы против портов.
Порты реэкспортируются из барреля `@po/server` для внешних потребителей (MCP).
Conformance-тест `apps/server/test/service-ports.test.ts` фиксирует обе стороны
контракта. Чисто типовой/структурный слой: HTTP/MCP-контракты, Zod-схемы и поведение
не менялись.
