# ADR-004 — Модель конкурентного доступа к `Projects/`

Статус: **Принято** · 2026-07-02 · **Обновлено 2026-07-07** (ARCH-3: исходная стратегия «LWW без
блокировок» **заменена** реализованным межпроцессным advisory-lock).
Автор: Архитектор · Обновление: Совет (`/council`, ARCH-3).
Связано: ADR-002 (MCP — отдельный процесс), ADR-003 (целостность пары связей),
NFR-4 (атомарная запись), NFR-9 (структурный лог). Реализация: `apps/server/src/lib/projectLock.ts`
(`withProjectLock`), покрытие — `apps/server/test/concurrency*.test.ts` (в т.ч. кросс-процессный,
QA-1).

## Контекст

Операции над требованиями следуют паттерну load → modify → write. На одном каталоге `Projects/`
(один `PROJECTS_ROOT`) работают **разные процессы**: REST-сервер (веб-UI) и MCP-сервер
(ИИ-агенты, ADR-002), а логически — несколько акторов (Product Owner и один/несколько агентов)
одновременно. Возникает риск гонок: потерянные обновления, частично записанные пары связей
(ADR-003), дубли slug.

## Решение

**Изначально (v1.0, MVP)** предполагалась стратегия «последний-записавший-побеждает»
(last-writer-wins) **без блокировок**, а сериализация записи — как «задел вне MVP».

**Реализовано (v1.1, 2026-07-07)** — межпроцессный **advisory file-lock** на уровне проекта
(`proper-lockfile`), т.к. in-process мьютекс не защищает от гонки двух ОС-процессов
(REST + MCP). Это заменяет пункт «LWW без блокировок».

- **Ключ и хранение lock:** `withProjectLock(projectsRoot, projectId, fn)` берёт advisory-lock на
  маркер `PROJECTS_ROOT/.locks/<projectId>` (`projectLock.ts`). Каталог `.locks/` скрыт и не
  перечисляется как проект; `realpath: false` позволяет лочить маркер до создания каталога
  проекта (нужно для create/import).
- **Гранулярность:** lock удерживается **только на время одной мутации** (create/update/delete/
  link/unlink/import) и освобождается в `finally`.
- **Параметры:** `stale: 20_000` мс (граница восстановления, если держатель упал);
  `retries: { retries: 200, factor: 1.2, minTimeout: 15, maxTimeout: 250, randomize: true }` —
  ожидающие **встают в очередь**, а не падают сразу.
- **Атомарность отдельной записи:** запись через temp-файл + `rename` (NFR-4) — читатель никогда
  не видит полуфайла. Сохранено.
- **Целостность связанных операций:** парные/каскадные записи (реципрокные связи, каскадное
  удаление — ADR-003) — целостная запись всех затронутых файлов под одним lock либо откат.
  Сохранено.
- **Наблюдаемость:** ФС-операции и ошибки пишутся в структурный лог (NFR-9). Сохранено.

## Последствия / риски

- **Плюс:** гонки `create/create` (дубль slug) и `update/update` (потеря обновления) между REST и
  MCP закрыты сериализацией на уровне проекта; поведение предсказуемо и покрыто тестами
  (QA-1 — реальный кросс-процессный тест).
- **Остаточный риск — crash-holder:** при аварийном завершении держателя lock освобождается
  только по `stale` (≤ 20 с); до этого ожидающие процессы ждут. Приемлемо для локального сценария;
  штатное освобождение при завершении процесса — ARCH-8 (graceful shutdown).
- **Остаточный риск — нет изоляции многошаговых операций:** AI-импорт берёт lock **пооперационно**
  (на каждую запись требования), а не как одну транзакцию на весь импорт, поэтому между шагами
  импорта возможны чужие правки (ADR-007 / ARCH-4).
- **Остаточный риск — хвостовая латентность:** при высокой конкуренции ожидание в очереди lock
  (`retries: 200`) может превышать перф-бюджет отдельного запроса; измерение — QA-4.
- **Не решается этим ADR:** оптимистическая версионность (`updatedAt`/version при записи) для
  мультипользовательского/распределённого сценария — вне MVP.
