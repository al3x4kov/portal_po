# ADR-004 — Модель конкурентного доступа к `Projects/`

Статус: **Принято** · 2026-07-02 · Автор: Архитектор
Связано: ADR-002 (MCP — отдельный процесс), ADR-003 (целостность пары связей),
NFR-4 (атомарная запись), NFR-9 (структурный лог), ARCH-1, ARCH-2 / SA-8.

## Контекст

Операции над требованиями следуют паттерну load → modify → write без блокировок.
При этом на одном каталоге `Projects/` (один `PROJECTS_ROOT`) работают **разные процессы**:
REST-сервер (веб-UI) и MCP-сервер (ИИ-агенты, ADR-002), а логически — несколько акторов
(Product Owner и один/несколько агентов) одновременно. Возникает риск гонок:
потерянные обновления, частично записанные пары связей (ADR-003), дубли slug.

## Решение (MVP)

- **Стратегия конфликтов:** «последний-записавший-побеждает» (last-writer-wins) — без
  блокировок и версионных проверок.
- **Атомарность отдельной записи:** запись файла через temp-файл + `rename` (NFR-4) —
  читатель никогда не видит полуфайла.
- **Целостность связанных операций:** для парных/каскадных записей (реципрокные связи,
  каскадное удаление — ADR-003, ARCH-1) — целостная запись всех затронутых файлов либо
  откат; частичный результат недопустим.
- **Наблюдаемость:** все ФС-операции и ошибки пишутся в структурный лог (NFR-9), чтобы
  постфактум восстановить порядок конкурентных записей.
- LWW явно фиксируется как **известное допущение MVP**, а не как гарантия.

**Задел (вне MVP):** сериализация записи через lock-файл или optimistic-lock
(версия/`updatedAt` при записи) — ARCH-2 / SA-8.

## Последствия / риски

- **Плюс:** простая, предсказуемая модель без инфраструктуры блокировок; корректна для
  типового локального сценария (один активный редактор).
- **Риск:** гонка `create/create` с одинаковым выводимым slug в двух процессах → возможен
  дубль/перетирание, т.к. дедуп-суффикс (ADR-001) вычисляется по снимку каталога до записи.
  Риск задокументирован; тест-задача и план защиты — ARCH-2.
- **Риск:** конкурентные правки двух акторов → тихая потеря одного обновления (LWW).
  Приемлемо для MVP; при мультипользовательском сценарии потребуется optimistic-lock.
