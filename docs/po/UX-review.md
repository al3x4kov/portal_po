Портал уже умеет: дерево ФТ/НФТ, создание/редактирование, связи, поиск, фильтр критичности,

Ниже — что мешает удобной работе PO и что доработать.

## TODO (приоритизировано)

### T1 (a) Фильтр по колонке «Реализация» — HIGH
**Проблема:** нельзя быстро отобрать только нереализованные (плановые) или только готовые
требования. Фильтр критичности есть, а по статусу реализации — нет.
**Решение:** мультиселект-фильтр в тулбаре рядом с «Критичность»: значения «Реализовано» и
«Не реализовано» (плановые с кварталом/годом). Работает через тот же слой видимости
(`computeVisibleRows`): совпадения + их предки; пересечение с поиском и фильтром критичности.
**Приёмка PO:** выбрав «Не реализовано», вижу только плановые требования (и их предков);
сброс возвращает всё; комбинируется с другими фильтрами без «сирот».

### T2 (г) Показ связей в карточке ФТ/НФТ — HIGH
**Проблема:** открыв требование, PO не видит его связи — приходится держать в голове.
**Решение:** в модалке редактирования — блок «Связи»: список текущих связей требования
(тип + название цели, человекочитаемо, напр. «блокируется «Соответствие PCI DSS»»).
Данные уже есть (`requirement.links` + карта slug→имя). Пустое состояние: «Связей нет».
**Приёмка PO:** открыв ФТ с связями, вижу их списком с типом и названием цели; у требования
без связей — явное пустое состояние.

### T3 (б) Удаление связей — HIGH
**Проблема:** связи можно создавать, но не удалять из UI (хотя API `DELETE /links` есть).
**Решение:** в блоке «Связи» (T2) у каждой связи — кнопка удаления с подтверждением
(как у удаления требования). Удаляет реципрокную пару (используется `useDeleteLink`).
**Приёмка PO:** могу удалить любую связь требования; после подтверждения она исчезает у обоих
концов; отмена ничего не меняет.

### T4 (в) Добавить НФТ прямо из строки ФТ с преднастроенной связью — MEDIUM
**Проблема:** чтобы «повесить» на функцию нефункциональное ограничение, нужно много шагов:
создать НФТ отдельно, потом вручную связать.
**Решение:** в строке ФТ — действие «+ НФТ» (быстрое). Открывает модалку создания НФТ; после
сохранения автоматически создаётся связь **ФТ `BLOCKED_BY` новое НФТ** (функция ограничена/
блокируется этим нефункциональным требованием — напр. «Оплата картой» *блокируется*
«Соответствие PCI DSS»). Тип связи предустановлен, источник = строка ФТ, цель = новое НФТ.
> Решение по направлению связи (обсуждено с Архитектором): источник — ФТ, тип — `BLOCKED_BY`,
> цель — новое НФТ. На стороне НФТ появится реципрокная `DEPENDS_ON`.
**Приёмка PO:** со строки ФТ создаю НФТ; оно появляется в секции НФТ и сразу связано с этой
ФТ как `BLOCKED_BY`; в карточке ФТ (T2) эта связь видна.

### T5 (д) Экспорт в Excel «как в UI» — MEDIUM
**Проблема:** текущий экспорт — 2 «сырых» листа (Requirements, Links), которые невозможно
читать глазами. PO нужен человекочитаемый вид.
**Решение:** один лист, максимально приближённый к таблице портала:
- Колонки как в UI: **Требование** (с отступом по уровню иерархии), **Тип** (ФТ/НФТ),
  **Критичность** (текст: Low…Blocker), **Реализация** (`Реализовано` или `Q3 2026`),
  **Описание**, **Связи** (человекочитаемо: «блокируется «…», связана с «…»»).
- Порядок строк — как в дереве (секция ФТ с иерархией, затем НФТ); отступ показывает вложенность.
- Заголовок листа/шапка жирным; по возможности — цветовая пометка критичности.
**Приёмка PO:** открыв .xlsx, вижу таблицу, повторяющую экран портала: иерархию с отступами,
статусы и связи словами; отдельный «технический» лист связей не обязателен.

## Дополнительные наблюдения (мелкие, в рамках текущих функций)
- Удаление связи и удаление требования — деструктивны → всегда с подтверждением (консистентно).
- Фильтры «Реализация» + «Критичность» + поиск должны жить в одном слое видимости (без гонок).
- Пустые состояния обязательны: «Связей нет», пустой результат фильтра «Реализация».

## Процесс
1. → Дизайнер делает макеты T1–T5, PO валидирует. 2. → Архитектор проверяет архитектуру и
пишет постановку (unit/BE/FE/e2e). 3. → Агенты реализуют. 4. → PO принимает; при несоответствии
— возврат к дизайну/архитектуре.
