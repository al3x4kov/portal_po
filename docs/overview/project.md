## 1. Контекст и цель

### 1.1 Проблема и цель
Product Owner'у нужен инструмент, чтобы через UI описывать **функциональные (ФТ)** и
**нефункциональные (НФТ)** требования продукта, строить между ними **древовидные связи**
(функции → подфункции, без ограничения вложенности) и хранить результат в
**машиночитаемом Markdown** — для дальнейшей агенто-ориентированной разработки (когда
требования скармливаются ИИ-агентам как источник истины).

### 1.2 Пользователи и роли `[ОБНОВЛЕНО v1.2]`

Система обслуживает **две аудитории**: человека (PO) и программного потребителя (ИИ-агент).
Это отражает главный дифференциатор продукта — «AI-ready» требования.

- **Product Owner (основная роль в MVP)** — локальный пользователь приложения (человек).
  Создаёт/редактирует ФТ и НФТ через UI, строит дерево, экспортирует архив.
  `[ДОПУЩЕНИЕ]` Многопользовательский режим, аутентификация и права вне скоупа MVP —
  приложение запускается локально и работает с локальной файловой системой.

- **ИИ-агент / интеграция (второй потребитель, стейкхолдер)** `[ДОБАВЛЕНО v1.2, SA-11/PO-7]` —
  программный клиент, читающий и (опционально) изменяющий требования через **MCP-сервер**
  (`apps/mcp`, stdio) или **REST** (`?format=openspec`). Не человек; взаимодействует без UI.
  - **Потребности:** машиночитаемый, стабильный формат требований как источник истины;
    предсказуемые контракты; доменные ошибки в разборном виде; отсутствие «висячих» связей.
  - **Fit-критерии (измеримые):**
    - **Детерминизм экспорта:** для неизменного проекта два вызова
      `GET /api/projects/:id/requirements?format=openspec` возвращают **байт-в-байт**
      идентичный OpenSpec-текст (стабильные порядок, разметка, переводы строк).
    - **Единый контракт:** входные схемы MCP-tools и REST совпадают (общие Zod-схемы из
      `@po/core`); отклонение полей одинаково на обоих каналах.
    - **Разборные ошибки:** доменная ошибка (напр. `CYCLE`) доходит до агента с кодом
      и деталями (`path`), а не как необработанное исключение.
    - **Round-trip:** экспортированный архив импортируется без потери требований и связей.

Полный набор акторов и границы системы — в [`context.md`](context.md).

### 1.3 Метрика успеха `[ДОБАВЛЕНО]`
- PO может за один сеанс создать проект, внести ≥ 20 требований, связать их в дерево и
  выгрузить архив, ни разу не редактируя файлы вручную.
- Экспортированный архив повторно импортируется без потери данных и связей (round-trip).

### 1.4 Вне скоупа (MVP) `[ДОБАВЛЕНО]`
- Облачное хранилище, синхронизация между устройствами, совместное редактирование.
- Версионирование/история изменений требований (кроме того, что даёт git вне приложения).
- Аутентификация и разграничение прав.
- Редактирование Markdown «как текста» — приложение управляет структурой, не сырым MD.

## 2. Ключевые понятия и модель данных

### 2.1 Сущности `[ОБНОВЛЕНО v1.2 — slug/OpenSpec, ADR-001]`
- **Project (Проект)** — каталог в директории `Projects/` портала. Главный путь к нему —
  **Main Path**. Содержит требования в раскладке OpenSpec и манифест `openspec/project.md`.
- **Requirement (Требование)** — функциональное (`FUNCTION`) или нефункциональное (`NFR`).
  Каждое хранится в отдельном файле `openspec/specs/{functions|nfr}/<slug>.md` (см. 2.5).
- **Link (Связь)** — типизированная направленная связь между двумя требованиями, адресуемая
  по `targetSlug`.
- **Scenario (Сценарий)** — опциональный блок `#### Scenario:` (GIVEN/WHEN/THEN/AND) внутри
  файла требования. В MVP — **read-only из импорта / вне MVP для авторинга** (см. §2.6, SA-10).

### 2.2 Поля требования `[ОБНОВЛЕНО v1.2 — slug вместо ULID, +BLOCKER; ADR-001]`
| Поле | Тип | Обяз. | Правила |
|------|-----|-------|---------|
| `slug` | string `[a-z0-9-]` | да | Стабильный человекочитаемый идентификатор. Генерируется системой из `name` при создании (кебаб/транслит; при коллизии суффикс `-2`,`-3`), **уникален в рамках проекта**, **неизменяем** (переименование `name` не меняет slug). Служит именем файла и целью связей. См. ADR-001. `[ИЗМЕНЕНО]` |
| `type` | `FUNCTION` \| `NFR` | да | Задаётся при создании, не меняется; выводится из папки (`functions`/`nfr`). |
| `name` | string | да | **Уникально в рамках своего типа внутри проекта** (см. 2.4). 1–200 симв. |
| `criticality` | enum (5) | да | `LOW` \| `MEDIUM` \| `HIGH` \| `CRITICAL` \| `BLOCKER`. Шкала/порядок — см. ниже. `[ИЗМЕНЕНО +BLOCKER]` |
| `description` | string (markdown) | усл. | До 5000 симв. Проверяемость: непустое описание **ИЛИ** ≥1 сценарий (см. 2.4.9). `[ОБНОВЛЕНО]` |
| `implemented` | boolean | да | «Реализовано / не реализовано» |
| `targetQuarter` | `Q1..Q4` | усл. | Обязателен, **только если** `implemented = false` |
| `targetYear` | int | усл. | Обязателен, **только если** `implemented = false`; диапазон 2020–2100. Прошлый год — **предупреждать** (см. ниже). `[ОБНОВЛЕНО]` |
| `scenarios` | Scenario[] | нет | Опциональные `#### Scenario:` (GIVEN/WHEN/THEN). См. §2.6. |
| `links` | Link[] | нет | См. 2.3 |
| `createdAt`/`updatedAt` | datetime | да | Системные. |

**Шкала `criticality` (5 значений, по возрастанию важности) `[ДОБАВЛЕНО v1.2, BA-2/SA-5]`:**

`LOW` < `MEDIUM` < `HIGH` < `CRITICAL` < **`BLOCKER`**.

- **LOW** — желательное; отсутствие почти не влияет на ценность.
- **MEDIUM** — заметно улучшает продукт, но есть обходные пути.
- **HIGH** — важное; отсутствие значимо снижает ценность релиза.
- **CRITICAL** — критично для релиза; без него релиз неполноценен.
- **BLOCKER** — **блокирующее**: без него релиз/поставка невозможны (высший приоритет,
  `BLOCKER > CRITICAL`). Используется для абсолютных предусловий (напр. юридическое/
  безопасностное ограничение, без которого продукт нельзя выпускать).

Enum ТЗ = код (`packages/core/src/domain/types.ts`, `CRITICALITIES`) = дизайн-токены.

**Правило `targetYear` в прошлом `[ДОБАВЛЕНО v1.2, BA-9]`:** если `implemented = false` и
`targetYear` (с учётом `targetQuarter`) уже в прошлом относительно текущей даты — система
**предупреждает** (не блокирует сохранение). Обоснование: план мог сдвинуться, и жёсткий
запрет мешал бы фиксировать «просроченные» требования — их как раз важно видеть; при этом
диапазон 2020–2100 остаётся жёсткой валидацией (защита от опечаток). Реакция: неблокирующее
предупреждение в форме («Плановый срок в прошлом») + запись сохраняется.

### 2.3 Связи (Link)
- Типы связей `[ДОБАВЛЕНО, уточнено]`:
  - `PARENT_OF` / `CHILD_OF` — иерархия (дерево функций/подфункций).
  - `RELATES_TO` — нетипизированная ассоциация (двусторонняя).
  - `DEPENDS_ON` / `BLOCKED_BY` — зависимость.
- Связь хранится **в обоих** файлах требований как взаимно-обратная пара
  (A: `PARENT_OF B`, B: `CHILD_OF A`). См. ADR-003 (reciprocal-хранение).
- Поле связи: `{ type, targetSlug }` — цель адресуется по **slug** требования. `[ИЗМЕНЕНО v1.2]`
  `[ИСТОРИЧЕСКОЕ]` в v1.0 поле называлось `targetId` (ULID) — заменено на `targetSlug` (ADR-001).

### 2.4 Ограничения целостности `[ДОБАВЛЕНО — «проверки на уникальность и др.»]`
1. **Уникальность имени:** `name` уникально в пределах (project × type), сравнение
   регистронезависимое с обрезкой пробелов. Автопроверка в реальном времени в форме
   (как указано в исходном ТЗ) и финальная проверка на сервере при сохранении.
2. **Уникальность slug:** slug **уникален в рамках проекта** (по всем типам, не только
   внутри типа — см. ADR-001 A6#8); при создании/импорте не должен конфликтовать с
   существующими. При потенциальной коллизии добавляется суффикс `-2`, `-3`. `[ИЗМЕНЕНО v1.2]`
3. **Запрет циклов:** связи `PARENT_OF`/`CHILD_OF` и `DEPENDS_ON` не должны образовывать
   цикл (A→B→…→A). Перед сохранением связи выполняется проверка на цикл, при нарушении —
   ошибка с указанием пути цикла.
4. **Одна иерархия-родитель:** у требования может быть **не более одного** `CHILD_OF`
   (один родитель) — дерево, а не граф. Дополнительные нелинейные связи выражаются через
   `RELATES_TO`/`DEPENDS_ON`. `[ДОПУЩЕНИЕ]`
5. **Запрет self-link:** нельзя связать требование само с собой.
6. **Согласованность типов:** иерархические связи допускаются только между требованиями
   одного типа (FUNCTION↔FUNCTION, NFR↔NFR). `[ДОПУЩЕНИЕ]`
7. **Целостность ссылок:** при удалении требования все обратные ссылки на него в других
   файлах удаляются; «висячих» ссылок быть не должно.
8. **Имя проекта (каталога):** валидное имя каталога ОС, уникально в `Projects/`,
   запрещённые символы отклоняются. `[ДОБАВЛЕНО]`
9. **Минимальная проверяемость требования `[ДОБАВЛЕНО v1.2, BA-8]`:** сохранённое требование
   обязано нести хотя бы одно из: **непустое описание** (после trim) **ИЛИ** **≥1 сценарий**
   (`#### Scenario:`). Пустое требование (только имя, без описания и сценариев) не является
   проверяемым и **не должно сохраняться** как валидное. Правило продукта; проверяется при
   сохранении и учитывается в отчёте целостности. Обоснование: требование без содержания
   нельзя ни реализовать, ни протестировать (принцип Вигерса «каждое требование проверяемо»).

### 2.5 Формат хранения (машиночитаемый MD) `[ДОБАВЛЕНО]`
Каждое требование — один файл `requirements/<id>.md` с YAML-frontmatter + телом-описанием:
```markdown
---
id: 01J9Z...ULID
type: FUNCTION
name: Авторизация по SSO
criticality: HIGH
implemented: false
targetQuarter: Q3
targetYear: 2026
links:
  - { type: CHILD_OF, targetId: 01J9Y... }
  - { type: RELATES_TO, targetId: 01J9X... }
createdAt: 2026-06-29T10:00:00Z
updatedAt: 2026-06-29T10:00:00Z
---

Текст описания функции в Markdown.
```
Манифест проекта `project.json` (или `project.md` с frontmatter): имя, версия схемы,
дата создания. `[ОТКРЫТО]` финальный выбор имени манифеста — за разработкой.

## 3. Функциональные требования

### FR-1. Стартовая страница
- **FR-1.1** Экран с тремя действиями: **Новый проект** / **Импорт** / **Открыть существующий**.

### FR-2. Новый проект
- **FR-2.1** Пользователь вводит имя проекта.
- **FR-2.2** В директории портала `Projects/` создаётся новый каталог с этим именем.
- **FR-2.3** Если каталога `Projects/` нет (был удалён) — проверить и **воссоздать** его.
- **FR-2.4** После создания — переход на основной экран; показать уведомление с путём
  (**Main Path**) созданного каталога.
- **FR-2.5** При имени, уже занятом в `Projects/`, — ошибка/запрос другого имени. `[ДОБАВЛЕНО]`

### FR-3. Импорт проекта
- **FR-3.1** Предложить загрузить архив `.zip` или `.tar.gz`.
- **FR-3.2** Пользователь задаёт имя; в `Projects/` создаётся каталог с этим именем
  (с воссозданием `Projects/`, если удалён — как в FR-2.3).
- **FR-3.3** Содержимое архива распаковывается в каталог проекта; выполняется валидация
  структуры и схемы требований. `[ДОБАВЛЕНО]`
- **FR-3.4** При повреждённом архиве/неверной структуре — понятная ошибка, каталог не
  оставляется в полусобранном виде (атомарность). `[ДОБАВЛЕНО]`

### FR-4. Открыть существующий
- **FR-4.1** Сканировать `Projects/`, вывести список всех доступных каталогов + кнопка «Назад».
- **FR-4.2** Выбор каталога открывает основной экран этого проекта. `[ДОБАВЛЕНО]`

### FR-5. Основной экран
- **FR-5.1 Top:** всегда отображается **Main Path** текущего проекта.
- **FR-5.2 Middle:** табличное/древовидное представление ФТ и НФТ (см. FR-7).
- **FR-5.3 Bottom:** кнопки «Добавить Функцию», «Добавить НФТ», «Экспорт в архив»
  (с выбором `.zip` или `.tar.gz`).

### FR-6. Добавление/редактирование требования
- **FR-6.1** Две секции над таблицей: «Функциональные требования» и «Нефункциональные
  требования», у каждой кнопка **+**.
- **FR-6.2** По **+** открывается модальное окно с полями: Название (автопроверка
  уникальности), Критичность, Описание, Реализовано/не реализовано, и при «не
  реализовано» — Квартал и Год реализации.
- **FR-6.3** Кнопки **Применить** и **Отменить**. «Отменить» → подтверждение
  «точно отменить?».
- **FR-6.4** При «Применить» в каталоге проекта создаётся/обновляется `.md` файл
  требования и **автоматически сохраняется**; в файл закладывается `id` для связей.
- **FR-6.5** Клик по требованию открывает его в модальном окне на **редактирование**;
  после изменений — подтверждение сохранения. `[ИСПРАВЛЕНО: в исходнике опечатка «точно
  ли удалить» при редактировании — трактуется как «точно сохранить изменения?»]`
- **FR-6.6** Автопроверка уникальности имени работает в реальном времени и не даёт
  сохранить дубль (см. 2.4.1).

### FR-7. Представление Middle (дерево/таблица)
- **FR-7.1** Колонки: (1) древовидное отображение функций/НФТ с раскрытием вложенности,
  (2) Описание, (3) Критичность, (4) Квартал и год реализации.
- **FR-7.2** Для каждой строки — кнопки **«Связать»** и **«Удалить»**.
- **FR-7.3** Раскрытие/сворачивание узлов дерева; отображение уровня вложенности. `[ДОБАВЛЕНО]`
- **FR-7.4** `[ОТКРЫТО]` Поведение колонки «Описание» при клике (в исходнике обрыв фразы
  «если на него нажать, то») — предлагается: раскрывать полное описание в поповере/детали.

### FR-8. Связывание требований
- **FR-8.1** «Связать» открывает модальное окно: выбор **типа связи** + поле **поиска**
  по существующим требованиям (с чем связать).
- **FR-8.2** Потребителю явно показывается формулировка: «**что** связываем», «**тип
  связи**», «**с чем** связываем» (напр.: «Функция А является родителем Функции Б»).
- **FR-8.3** При сохранении связь записывается в `.md` **обоих** требований как взаимно
  обратная пара (по их `id`).
- **FR-8.4** Перед сохранением — проверки целостности (2.4): циклы, один родитель,
  self-link, согласованность типов. При нарушении — ошибка с пояснением. `[ДОБАВЛЕНО]`

### FR-9. Удаление требования
- **FR-9.1** «Удалить» сопровождается предупреждением «точно удалить?».
- **FR-9.2** При подтверждении удаляются файл требования и все обратные ссылки на него
  в других файлах (2.4.7).
- **FR-9.3** `[ОТКРЫТО]` Поведение при удалении узла с потомками: предложить варианты —
  каскадно удалить поддерево или «поднять» потомков на уровень выше. По умолчанию —
  запретить удаление, пока есть потомки, с подсказкой. `[ДОПУЩЕНИЕ]`

### FR-10. Экспорт
- **FR-10.1** Экспорт каталога проекта в архив `.zip` или `.tar.gz` (выбор формата).
- **FR-10.2** Экспортируется полный, самодостаточный набор `.md` + манифест,
  пригодный для повторного импорта (round-trip). `[ДОБАВЛЕНО]`

## 4. Нефункциональные требования

- **NFR-1 Платформа:** локальное приложение на **Node.js + TypeScript**; UI — веб
  («top сайта»), запускается локально. Кроссплатформенно (macOS/Windows/Linux). `[ДОБАВЛЕНО]`
- **NFR-2 Хранение:** источник истины — файлы на диске (`.md` + манифест), без СУБД.
  Машиночитаемый формат (YAML-frontmatter), стабильная схема. `[ДОБАВЛЕНО]`
- **NFR-3 Производительность:** плавная работа дерева до ~1000 требований в проекте;
  операции CRUD < 200 мс на типовом ПК. `[ДОПУЩЕНИЕ]`
- **NFR-4 Надёжность/атомарность:** запись файлов атомарна (temp + rename); импорт/экспорт
  не оставляют проект в повреждённом состоянии. `[ДОБАВЛЕНО]`
- **NFR-5 Безопасность ФС:** все операции ограничены каталогом `Projects/`; защита от
  path traversal (имена проектов/файлов санируются). `[ДОБАВЛЕНО]`
- **NFR-6 UX:** деструктивные действия — с подтверждением; ошибки — человекочитаемые;
  локализация интерфейса — русский (MVP). `[ДОБАВЛЕНО]`
- **NFR-7 Доступность:** клавиатурная навигация в модалках, контраст WCAG AA. `[ДОБАВЛЕНО]`
- **NFR-8 Тестируемость:** покрытие unit-тестами бизнес-логики (валидации, связи,
  сериализация MD) и Playwright E2E на ключевые сценарии. `[ДОБАВЛЕНО]`
- **NFR-9 Наблюдаемость:** логирование операций ФС и ошибок. `[ДОБАВЛЕНО]`

## 5. Краевые случаи и обработка ошибок `[ДОБАВЛЕНО]`

- Каталог `Projects/` отсутствует/нет прав на запись → воссоздать или показать ошибку.
- Дубликат имени проекта / имени требования → блокировка с пояснением.
- Импорт битого/неполного архива, неизвестный формат → откат, понятная ошибка.
- Ручное редактирование/повреждение `.md` вне приложения → при чтении валидировать,
  помечать «битые» требования, не падать.
- Висячие/обратные ссылки при частично повреждённых данных → отчёт о целостности.
- Попытка создать цикл или второго родителя → отклонить с указанием конфликта.
- Очень длинные имена/описания, спецсимволы, эмодзи → валидация длины и санитизация.
- Конкурентные изменения файлов другим процессом → последний-записавший побеждает + лог. `[ДОПУЩЕНИЕ]`

## 8. Доработки v2 `[ДОБАВЛЕНО 2026-07-01]`

Принятые решения (детали — в `docs/architecture/`):

1. **Формат хранения — OpenSpec** (реальный формат). Требование = отдельный файл
   `openspec/specs/{functions|nfr}/<slug>.md` в разметке `### Requirement:` /
   `#### Scenario:`; манифест `openspec/project.md`. См. `ADR-001-openspec-storage.md`.
2. **`slug` вместо ULID `id`.** Непрозрачный идентификатор заменён человекочитаемым
   стабильным slug (уникален в рамках проекта, неизменяем при переименовании `name`).
   Связи ссылаются по `targetSlug`. Закрывает риск нечитаемых/висячих связей.
3. **Экспорт в Excel `.xlsx`** — дополнительно к архивам (листы `Requirements`, `Links`).
   Только выгрузка: xlsx **не импортируется** (импорт остаётся archive-only, round-trip).
4. **Единый слой видимости строк.** Поиск, «Скрыть зависимости» и мультиселект-фильтр
   критичности вычисляют один набор видимых строк; совпадение всегда показывается вместе
   с предками (без «сирот»). Поиск ∩ фильтр = пересечение.
5. **FR-7.4 закрыт:** длинное описание открывается в боковой панели (drawer) по клику.
6. **AI-ready:** REST `?format=openspec` + MCP-сервер (`apps/mcp`, stdio) поверх сервисов.

Соответственно закрыты открытые вопросы §7.1 (описание — drawer) и уточнён §2.5
(манифест — `openspec/project.md`).
