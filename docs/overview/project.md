## 1. Контекст и цель

### 1.1 Проблема и цель
Product Owner'у нужен инструмент, чтобы через UI описывать **функциональные (ФТ)** и
**нефункциональные (НФТ)** требования продукта, строить между ними **древовидные связи**
(функции → подфункции, без ограничения вложенности) и хранить результат в
**машиночитаемом Markdown** — для дальнейшей агенто-ориентированной разработки (когда
требования скармливаются ИИ-агентам как источник истины).

### 1.2 Пользователи и роли `[ОБНОВЛЕНО v1.2]`

Система обслуживает **две аудитории**: человека (PO) и программного потребителя (ИИ-агент).
Это отражает главный дифференциатор продукта — «AI-ready» требования.

- **Product Owner (основная роль в MVP)** — локальный пользователь приложения (человек).
  Создаёт/редактирует ФТ и НФТ через UI, строит дерево, экспортирует архив.
  `[ДОПУЩЕНИЕ]` Многопользовательский режим, аутентификация и права вне скоупа MVP —
  приложение запускается локально и работает с локальной файловой системой.

- **ИИ-агент / интеграция (второй потребитель, стейкхолдер)** `[ДОБАВЛЕНО v1.2, SA-11/PO-7]` —
  программный клиент, читающий и (опционально) изменяющий требования через **MCP-сервер**
  (`apps/mcp`, stdio) или **REST** (`?format=openspec`). Не человек; взаимодействует без UI.
  - **Потребности:** машиночитаемый, стабильный формат требований как источник истины;
    предсказуемые контракты; доменные ошибки в разборном виде; отсутствие «висячих» связей.
  - **Fit-критерии (измеримые):**
    - **Детерминизм экспорта:** для неизменного проекта два вызова
      `GET /api/projects/:id/requirements?format=openspec` возвращают **байт-в-байт**
      идентичный OpenSpec-текст (стабильные порядок, разметка, переводы строк).
    - **Единый контракт:** входные схемы MCP-tools и REST совпадают (общие Zod-схемы из
      `@po/core`); отклонение полей одинаково на обоих каналах.
    - **Разборные ошибки:** доменная ошибка (напр. `CYCLE`) доходит до агента с кодом
      и деталями (`path`), а не как необработанное исключение.
    - **Round-trip:** экспортированный архив импортируется без потери требований и связей.

Полный набор акторов и границы системы — в [`context.md`](context.md).

### 1.3 Метрика успеха `[ДОБАВЛЕНО]`
- PO может за один сеанс создать проект, внести ≥ 20 требований, связать их в дерево и
  выгрузить архив, ни разу не редактируя файлы вручную.
- Экспортированный архив повторно импортируется без потери данных и связей (round-trip).

### 1.4 Вне скоупа (MVP) `[ДОБАВЛЕНО]`
- Облачное хранилище, синхронизация между устройствами, совместное редактирование.
- Версионирование/история изменений требований (кроме того, что даёт git вне приложения).
- Аутентификация и разграничение прав.
- Редактирование Markdown «как текста» — приложение управляет структурой, не сырым MD.

## 2. Ключевые понятия и модель данных

### 2.1 Сущности `[ОБНОВЛЕНО v1.2 — slug/OpenSpec, ADR-001]`
- **Project (Проект)** — каталог в директории `Projects/` портала. Главный путь к нему —
  **Main Path**. Содержит требования в раскладке OpenSpec и манифест `openspec/project.md`.
- **Requirement (Требование)** — функциональное (`FUNCTION`) или нефункциональное (`NFR`).
  Каждое хранится в отдельном файле `openspec/specs/{functions|nfr}/<slug>.md` (см. 2.5).
- **Link (Связь)** — типизированная направленная связь между двумя требованиями, адресуемая
  по `targetSlug`.
- **Scenario (Сценарий)** — опциональный блок `#### Scenario:` (GIVEN/WHEN/THEN/AND) внутри
  файла требования. В MVP — **read-only из импорта / вне MVP для авторинга** (см. §2.6, SA-10).

### 2.2 Поля требования `[ОБНОВЛЕНО v1.2 — slug вместо ULID, +BLOCKER; ADR-001]`
| Поле | Тип | Обяз. | Правила |
|------|-----|-------|---------|
| `slug` | string `[a-z0-9-]` | да | Стабильный человекочитаемый идентификатор. Генерируется системой из `name` при создании (кебаб/транслит; при коллизии суффикс `-2`,`-3`), **уникален в рамках проекта**, **неизменяем** (переименование `name` не меняет slug). Служит именем файла и целью связей. См. ADR-001. `[ИЗМЕНЕНО]` |
| `type` | `FUNCTION` \| `NFR` | да | Задаётся при создании, не меняется; выводится из папки (`functions`/`nfr`). |
| `name` | string | да | **Уникально в рамках своего типа внутри проекта** (см. 2.4). 1–200 симв. |
| `criticality` | enum (5) | да | `LOW` \| `MEDIUM` \| `HIGH` \| `CRITICAL` \| `BLOCKER`. Шкала/порядок — см. ниже. `[ИЗМЕНЕНО +BLOCKER]` |
| `description` | string (markdown) | усл. | До 5000 симв. Проверяемость: непустое описание **ИЛИ** ≥1 сценарий (см. 2.4.9). `[ОБНОВЛЕНО]` |
| `implemented` | boolean | да | «Реализовано / не реализовано» |
| `targetQuarter` | `Q1..Q4` | усл. | Обязателен, **только если** `implemented = false` |
| `targetYear` | int | усл. | Обязателен, **только если** `implemented = false`; диапазон 2020–2100. Прошлый год — **предупреждать** (см. ниже). `[ОБНОВЛЕНО]` |
| `scenarios` | Scenario[] | нет | Опциональные `#### Scenario:` (GIVEN/WHEN/THEN). См. §2.6. |
| `links` | Link[] | нет | См. 2.3 |
| `createdAt`/`updatedAt` | datetime | да | Системные. |

**Шкала `criticality` (5 значений, по возрастанию важности) `[ДОБАВЛЕНО v1.2, BA-2/SA-5]`:**

`LOW` < `MEDIUM` < `HIGH` < `CRITICAL` < **`BLOCKER`**.

- **LOW** — желательное; отсутствие почти не влияет на ценность.
- **MEDIUM** — заметно улучшает продукт, но есть обходные пути.
- **HIGH** — важное; отсутствие значимо снижает ценность релиза.
- **CRITICAL** — критично для релиза; без него релиз неполноценен.
- **BLOCKER** — **блокирующее**: без него релиз/поставка невозможны (высший приоритет,
  `BLOCKER > CRITICAL`). Используется для абсолютных предусловий (напр. юридическое/
  безопасностное ограничение, без которого продукт нельзя выпускать).

Enum ТЗ = код (`packages/core/src/domain/types.ts`, `CRITICALITIES`) = дизайн-токены.

**Правило `targetYear` в прошлом `[ДОБАВЛЕНО v1.2, BA-9]`:** если `implemented = false` и
`targetYear` (с учётом `targetQuarter`) уже в прошлом относительно текущей даты — система
**предупреждает** (не блокирует сохранение). Обоснование: план мог сдвинуться, и жёсткий
запрет мешал бы фиксировать «просроченные» требования — их как раз важно видеть; при этом
диапазон 2020–2100 остаётся жёсткой валидацией (защита от опечаток). Реакция: неблокирующее
предупреждение в форме («Плановый срок в прошлом») + запись сохраняется.

### 2.3 Связи (Link)
- Типы связей `[ДОБАВЛЕНО, уточнено]`:
  - `PARENT_OF` / `CHILD_OF` — иерархия (дерево функций/подфункций).
  - `RELATES_TO` — нетипизированная ассоциация (двусторонняя).
  - `DEPENDS_ON` / `BLOCKED_BY` — зависимость.
- Связь хранится **в обоих** файлах требований как взаимно-обратная пара
  (A: `PARENT_OF B`, B: `CHILD_OF A`). См. ADR-003 (reciprocal-хранение).
- Поле связи: `{ type, targetSlug }` — цель адресуется по **slug** требования. `[ИЗМЕНЕНО v1.2]`
  `[ИСТОРИЧЕСКОЕ]` в v1.0 поле называлось `targetId` (ULID) — заменено на `targetSlug` (ADR-001).

### 2.4 Ограничения целостности `[ДОБАВЛЕНО — «проверки на уникальность и др.»]`
1. **Уникальность имени:** `name` уникально в пределах (project × type), сравнение
   регистронезависимое с обрезкой пробелов. Автопроверка в реальном времени в форме
   (как указано в исходном ТЗ) и финальная проверка на сервере при сохранении.
2. **Уникальность slug:** slug **уникален в рамках проекта** (по всем типам, не только
   внутри типа — см. ADR-001 A6#8); при создании/импорте не должен конфликтовать с
   существующими. При потенциальной коллизии добавляется суффикс `-2`, `-3`. `[ИЗМЕНЕНО v1.2]`
3. **Запрет циклов:** связи `PARENT_OF`/`CHILD_OF` и `DEPENDS_ON` не должны образовывать
   цикл (A→B→…→A). Перед сохранением связи выполняется проверка на цикл, при нарушении —
   ошибка с указанием пути цикла.
4. **Одна иерархия-родитель:** у требования может быть **не более одного** `CHILD_OF`
   (один родитель) — дерево, а не граф. Дополнительные нелинейные связи выражаются через
   `RELATES_TO`/`DEPENDS_ON`. `[ДОПУЩЕНИЕ]`
5. **Запрет self-link:** нельзя связать требование само с собой.
6. **Согласованность типов:** иерархические связи допускаются только между требованиями
   одного типа (FUNCTION↔FUNCTION, NFR↔NFR). `[ДОПУЩЕНИЕ]`
7. **Целостность ссылок:** при удалении требования все обратные ссылки на него в других
   файлах удаляются; «висячих» ссылок быть не должно.
8. **Имя проекта (каталога):** валидное имя каталога ОС, уникально в `Projects/`,
   запрещённые символы отклоняются. `[ДОБАВЛЕНО]`
9. **Минимальная проверяемость требования `[ДОБАВЛЕНО v1.2, BA-8]`:** сохранённое требование
   обязано нести хотя бы одно из: **непустое описание** (после trim) **ИЛИ** **≥1 сценарий**
   (`#### Scenario:`). Пустое требование (только имя, без описания и сценариев) не является
   проверяемым и **не должно сохраняться** как валидное. Правило продукта; проверяется при
   сохранении и учитывается в отчёте целостности. Обоснование: требование без содержания
   нельзя ни реализовать, ни протестировать (принцип Вигерса «каждое требование проверяемо»).

### 2.5 Формат хранения (OpenSpec / slug) `[ОБНОВЛЕНО v1.2 — ADR-001, BA-1]`

> **Источник истины по формату — [`ADR-001-openspec-storage.md`](../architecture/ADR-001-openspec-storage.md).**
> Ниже — нормативное краткое изложение; ULID/YAML-frontmatter/`targetId` — исторические
> формулировки v1.0, заменены на OpenSpec/slug/`targetSlug`.

**Раскладка проекта (OpenSpec, гибрид «1 файл = 1 требование»):**
```
<project>/
  openspec/
    project.md                 # манифест: name, schemaVersion, createdAt (frontmatter)
    specs/
      functions/<slug>.md      # одно ФТ = один файл
      nfr/<slug>.md            # одно НФТ = один файл
    changes/                   # [задел] дельты правок; в MVP не заполняется UI
```

**Файл требования** `openspec/specs/{functions|nfr}/<slug>.md` — самодостаточный
OpenSpec-фрагмент: заголовок `### Requirement:`, метаданные-булиты, тело-описание,
опциональные `#### Scenario:` и `#### Links`:
```markdown
### Requirement: Авторизация по SSO
- criticality: HIGH
- implemented: false
- target: Q3 2026

Продукт **SHALL** поддерживать вход через корпоративный SSO (OIDC).

#### Scenario: Успешный вход
- GIVEN сконфигурирован OIDC-провайдер
- WHEN пользователь выбирает «Войти через SSO»
- THEN создаётся сессия и происходит редирект на дашборд

#### Links
- CHILD_OF: sistema-avtorizacii
- RELATES_TO: audit-log
```

- **Идентификатор — `slug`** (не ULID): имя файла и цель связей; неизменяем, уникален в
  рамках проекта (2.4.2). `type` выводится из папки (`functions`/`nfr`).
- **Связи** — булиты `#### Links`, значение = **`slug`** цели (не `targetId`); хранятся
  реципрокно в обоих файлах (2.3, ADR-003).
- **`target: Q<n> <year>`** присутствует **только** при `implemented: false` (2.4).
- **Манифест** — `openspec/project.md` (frontmatter: `name`, `schemaVersion`, `createdAt`).
  `schemaVersion` проверяется при чтении/импорте; при несовпадении с текущей — ошибка
  (миграции в MVP нет), см. §5, ADR-006/SA-9.
- Тело до `#### Scenario/Links` — описание (markdown, ≤5000). Round-trip
  сериализация↔парсинг — без потерь (DoD §6, S1).

`[ИСТОРИЧЕСКОЕ]` v1.0: `requirements/<ULID>.md` с YAML-frontmatter и связями по
`targetId` — заменено на раскладку выше (ADR-001).

### 2.6 Сценарии (Scenario) `[ДОБАВЛЕНО v1.2 — SA-10]`

`#### Scenario:` (GIVEN/WHEN/THEN/AND) — опциональный блок внутри файла требования,
даёт проверяемый критерий приёмки требования (принцип Вигерса; см. 2.4.9).

- **Статус в MVP:** сценарии **read-only из импорта** — парсятся из существующих `.md`,
  отображаются, участвуют в правиле проверяемости (2.4.9) и подсчёте «неполных сценариев»
  (нет WHEN/THEN → флаг-предупреждение, S6). **Авторинг/редактирование сценариев в UI —
  вне MVP** (нет FR и UI-редактора). Решение SA-10: не вводить в MVP отдельный FR
  «Авторинг сценариев»; вынесено из области (см. §1.4, `context.md` «Вне области»).
- Обоснование: модель и парсер уже поддерживают сценарии (задел OpenSpec-формата), но
  UI-редактор сценариев не даёт ценности PO в MVP относительно стоимости; при появлении
  потребности — оформляется отдельным FR + product use case.

## 3. Функциональные требования

### FR-1. Стартовая страница
- **FR-1.1** Экран с тремя действиями: **Новый проект** / **Импорт** / **Открыть существующий**.

### FR-2. Новый проект
- **FR-2.1** Пользователь вводит имя проекта.
- **FR-2.2** В директории портала `Projects/` создаётся новый каталог с этим именем.
- **FR-2.3** Если каталога `Projects/` нет (был удалён) — проверить и **воссоздать** его.
- **FR-2.4** После создания — переход на основной экран; показать уведомление с путём
  (**Main Path**) созданного каталога.
- **FR-2.5** При имени, уже занятом в `Projects/`, — ошибка/запрос другого имени. `[ДОБАВЛЕНО]`

### FR-3. Импорт проекта
- **FR-3.1** Предложить загрузить архив `.zip` или `.tar.gz`.
- **FR-3.2** Пользователь задаёт имя; в `Projects/` создаётся каталог с этим именем
  (с воссозданием `Projects/`, если удалён — как в FR-2.3).
- **FR-3.3** Содержимое архива распаковывается в каталог проекта; выполняется валидация
  структуры, `schemaVersion` манифеста и схемы требований. При `schemaVersion` ≠ текущей —
  ошибка, каталог не создаётся (§5, SA-9). `[ОБНОВЛЕНО v1.2]`
- **FR-3.4** При повреждённом архиве/неверной структуре — понятная ошибка, каталог не
  оставляется в полусобранном виде (атомарность). `[ДОБАВЛЕНО]`

### FR-4. Открыть существующий
- **FR-4.1** Сканировать `Projects/`, вывести список всех доступных каталогов + кнопка «Назад».
- **FR-4.2** Выбор каталога открывает основной экран этого проекта. `[ДОБАВЛЕНО]`

### FR-5. Основной экран
- **FR-5.1 Top:** всегда отображается **Main Path** текущего проекта.
- **FR-5.2 Middle:** табличное/древовидное представление ФТ и НФТ (см. FR-7).
- **FR-5.3 Bottom:** кнопки «Добавить Функцию», «Добавить НФТ», «Экспорт в архив»
  (с выбором `.zip` или `.tar.gz`).

### FR-6. Добавление/редактирование требования
- **FR-6.1** Две секции над таблицей: «Функциональные требования» и «Нефункциональные
  требования», у каждой кнопка **+**.
- **FR-6.2** По **+** открывается модальное окно с полями: Название (автопроверка
  уникальности), Критичность, Описание, Реализовано/не реализовано, и при «не
  реализовано» — Квартал и Год реализации.
- **FR-6.3** Кнопки **Применить** и **Отменить**. «Отменить» → подтверждение
  «точно отменить?».
- **FR-6.4** При «Применить» в каталоге проекта создаётся/обновляется `.md` файл
  требования и **автоматически сохраняется**; в файл закладывается `id` для связей.
- **FR-6.5** Клик по требованию открывает его в модальном окне на **редактирование**;
  после изменений — подтверждение сохранения. `[ИСПРАВЛЕНО: в исходнике опечатка «точно
  ли удалить» при редактировании — трактуется как «точно сохранить изменения?»]`
- **FR-6.6** Автопроверка уникальности имени работает в реальном времени и не даёт
  сохранить дубль (см. 2.4.1).

### FR-7. Представление Middle (дерево/таблица)
- **FR-7.1** Колонки: (1) древовидное отображение функций/НФТ с раскрытием вложенности,
  (2) Описание, (3) Критичность, (4) Квартал и год реализации.
- **FR-7.2** Для каждой строки — кнопки **«Связать»** и **«Удалить»**.
- **FR-7.3** Раскрытие/сворачивание узлов дерева; отображение уровня вложенности. `[ДОБАВЛЕНО]`
- **FR-7.4** `[ОТКРЫТО]` Поведение колонки «Описание» при клике (в исходнике обрыв фразы
  «если на него нажать, то») — предлагается: раскрывать полное описание в поповере/детали.
- **FR-7.5** Кнопка **«Добавить дочернее требование»** (иконка в строке ФТ) открывает
  форму создания новой функции. **Создаваемая функция становится дочерней для выбранной**
  (связь `созданное CHILD_OF выбранное`; реципрокно у родителя — `PARENT_OF`). Направление
  строго такое: выбранная строка остаётся родителем, новая — потомком; инверсия недопустима.
  Подсказка в форме сообщает: «Создаваемая функция будет дочерней для «…» (CHILD_OF)».
  Критичность и статус реализации не предзаполняются (см. FR-21). `[ДОБАВЛЕНО]`

### FR-8. Связывание требований
- **FR-8.1** «Связать» открывает модальное окно: выбор **типа связи** + поле **поиска**
  по существующим требованиям (с чем связать).
- **FR-8.2** Потребителю явно показывается формулировка: «**что** связываем», «**тип
  связи**», «**с чем** связываем» (напр.: «Функция А является родителем Функции Б»).
- **FR-8.3** При сохранении связь записывается в `.md` **обоих** требований как взаимно
  обратная пара (по их `id`).
- **FR-8.4** Перед сохранением — проверки целостности (2.4): циклы, один родитель,
  self-link, согласованность типов. При нарушении — ошибка с пояснением. `[ДОБАВЛЕНО]`

### FR-9. Удаление требования
- **FR-9.1** «Удалить» сопровождается предупреждением «точно удалить?».
- **FR-9.2** При подтверждении удаляются файл требования и все обратные ссылки на него
  в других файлах (2.4.7).
- **FR-9.3** `[РЕШЕНО v1.2 — SA-7]` При удалении узла, у которого есть потомки, операция
  **отклоняется** с подсказкой, перечисляющей блокирующих потомков (сначала снимите/
  переназначьте связи). Каскадное удаление поддерева и «подъём» потомков — **вне MVP**.
  Fit-критерий: `HasChildrenError` с перечнем потомков (S15).

### FR-10. Экспорт
- **FR-10.1** Экспорт каталога проекта в архив `.zip` или `.tar.gz` (выбор формата).
- **FR-10.2** Экспортируется полный, самодостаточный набор `.md` + манифест,
  пригодный для повторного импорта (round-trip). `[ДОБАВЛЕНО]`
- **FR-10.3** Экспорт в Excel `.xlsx` (`GET …/export.xlsx`) — только выгрузка; xlsx
  **не импортируется** (импорт archive-only, round-trip). `[ДОБАВЛЕНО v1.2]`
- **FR-10.4** Экспорт машиночитаемого OpenSpec-текста для агентов:
  `GET …/requirements?format=openspec` (детерминированный, байт-в-байт, см. §1.2). `[ДОБАВЛЕНО v1.2]`

### FR-11. Фильтр по статусу реализации `[ДОБАВЛЕНО v1.2 — E15/T1, BA-3]`
- **FR-11.1** Мультиселект-фильтр «Реализация» со значениями **Реализовано** (`implemented=true`)
  и **Запланировано** (`implemented=false`); бейдж-счётчик активных значений, «Применить»/«Сбросить».
- **FR-11.2** Фильтр — часть **единого слоя видимости строк** (§8.4): комбинируется по **И** с
  поиском и фильтром критичности; предки видимых совпадений остаются видны как контекст (без «сирот»).

### FR-12. Просмотр связей в карточке требования `[ДОБАВЛЕНО v1.2 — E15/T2, BA-3]`
- **FR-12.1** В режиме редактирования требования отображается блок **«Связи»**: каждая связь
  человекочитаемо (тип связи + **название** цели, не slug). Пустое состояние — «Связей нет».

### FR-13. Удаление связи из карточки `[ДОБАВЛЕНО v1.2 — E15/T3, BA-3]`
- **FR-13.1** У каждой связи в блоке «Связи» — действие удаления с инлайн-подтверждением.
- **FR-13.2** Удаляется **реципрокная пара** у обоих концов (2.3); список обновляется без «висячих» ссылок.

### FR-14. Добавление НФТ из строки ФТ `[ДОБАВЛЕНО v1.2 — E15/T4, BA-3]`
- **FR-14.1** В строке функционального требования — действие «+ НФТ»: открывает модалку создания
  НФТ с подсказкой о будущей связи.
- **FR-14.2** После создания НФТ автоматически создаётся связь: **источник — ФТ, тип `BLOCKED_BY`,
  цель — новое НФТ** (реципрокно у НФТ — `DEPENDS_ON`). Решение направления — за архитектурой (E15/T4).

### FR-15. Excel-экспорт «как в UI» `[ДОБАВЛЕНО v1.2 — E15/T5, BA-3]`
- **FR-15.1** Лист **«Требования»** повторяет таблицу портала: колонки Требование (с отступом
  по дереву), Тип, Критичность (текст), Реализация (`Реализовано`/`Q3 2026`), Описание, Связи
  (типы + названия целей). Порядок строк: секция ФТ в порядке дерева (DFS), затем секция НФТ.

### FR-16. Раскладка таблицы требований `[ДОБАВЛЕНО v1.2 — E16, BA-3]`
- **FR-16.1** Отдельная колонка **«Связи»** (неиерархические чипы `RELATES_TO`/`DEPENDS_ON`/
  `BLOCKED_BY`), вынесенная из колонки названия; пусто — «—».
- **FR-16.2** Колонка действий вмещает до 3 кнопок («+ НФТ», «Связать», «Удалить») без переполнения/
  клиппинга; действия целиком внутри своей ячейки и карточки секции.
- **FR-16.3** Полноэкранная раскладка: секции ФТ/НФТ используют всю ширину экрана (без `max-width`).
- **FR-16.4** Инвариант «без перекрытий»: контент ячеек не выходит за границы карточки; нет
  горизонтального выхода страницы за экран на типовых ширинах (1280/1680).

## 4. Нефункциональные требования `[ОБНОВЛЕНО v1.2 — fit-критерии, BA-4/SA-2]`

Каждому НФТ добавлен **Fit criterion** — проверяемое числовое/булево условие приёмки
(методология Volere). Измерения производительности — на **reference-конфигурации** (ниже).

> **Reference-конфигурация «типового ПК» (эталон для NFR-3):**
> CPU 4 ядра ≥ 2.5 ГГц (напр. Apple M1 / Intel i5-8xxx), RAM 8 ГБ, SSD; Node.js LTS 20;
> проект **1000 требований**, средняя глубина дерева 5. Бенчмарк выполняется в CI на
> зафиксированном раннере; при смене раннера эталон пересматривается.

- **NFR-1 Платформа:** локальное приложение на **Node.js + TypeScript**; UI — веб,
  запускается локально; кроссплатформенно (macOS/Windows/Linux).
  - **Fit criterion:** `lint + typecheck + unit + e2e` зелёные на Node.js LTS 20; запуск одной
    командой на 3 ОС (CI-матрица или ручная проверка на каждой).
- **NFR-2 Хранение:** источник истины — файлы на диске (OpenSpec `.md` + манифест), без СУБД;
  машиночитаемый формат, стабильная схема (`schemaVersion`).
  - **Fit criterion:** отсутствует зависимость от СУБД (нет драйверов БД в `package.json`);
    round-trip serialize↔parse без потерь (S1); `schemaVersion` присутствует в манифесте и
    проверяется при чтении/импорте (ADR-006/SA-9).
- **NFR-3 Производительность:** плавная работа дерева и быстрые операции на типовом ПК.
  - **Fit criterion (измеримо):** на reference-конфигурации при **1000 требований** —
    построение/фильтрация видимых строк дерева **< 200 мс** (p95); одна CRUD-операция
    (создание/правка/удаление требования, вкл. запись файла) **< 200 мс** (p95); первичный
    рендер основного экрана **< 1.5 с**. Бенчмарк `visibility`/CRUD в CI, порог гейтит сборку. `[ИЗМЕНЕНО]`
  - **Статус проверки (2026-07-04):** критерий подтверждён на reference-машине —
    `apps/server/test/perf.test.ts` (CRUD+list @1000: факт p95 = 73–154 мс, каждый прогон
    логирует «target p95<200ms: met/MISSED»), `apps/web/src/lib/visibility.perf.test.ts`
    (1200 узлов @ 50 мс), `e2e/tests/scale.spec.ts` (первичный рендер @1000: факт ≈1.0–1.1 с,
    замер в perf-аннотации). CI-гейты выставлены с анти-флаки-запасом ×2–3 от факта
    (CRUD 400 мс, рендер 3.5 с), чтобы вариативность раннера не давала ложных падений;
    деградация против целевого критерия видна по логу бенчмарка. `[ДОБАВЛЕНО]`
- **NFR-4 Надёжность/атомарность:** запись файлов атомарна (temp + rename); импорт/экспорт
  не оставляют проект в повреждённом состоянии.
  - **Fit criterion:** тест «сбой на 2-й записи пары/каскада» не оставляет частичного состояния
    (ARCH-1/BE-7); тест «битый архив» → целевой каталог не создан, temp очищен (S-строка импорта).
- **NFR-5 Безопасность ФС:** все операции строго внутри `Projects/`; защита от path traversal.
  - **Fit criterion:** любой путь с `../`/сепаратором/абсолютный — отклонён (S21, `pathSafe`);
    tar/zip-запись, выходящая за корень, отклонена; **0** проходящих traversal-тестов «в обход».
- **NFR-6 UX:** деструктивные действия — с подтверждением; ошибки — человекочитаемые;
  локализация интерфейса — русский (MVP).
  - **Fit criterion:** **каждое** деструктивное действие (удаление требования/связи, отмена
    правок) требует подтверждения (e2e); ошибки доходят как `{code,message}` с русским текстом,
    без «сырых» стектрейсов в UI. Включён в DoD. `[ДОБАВЛЕНО]`
- **NFR-7 Доступность:** клавиатурная навигация в модалках, контраст WCAG AA.
  - **Fit criterion:** axe-скан ключевых экранов и открытых модалок — **0 serious/critical**;
    focus-trap + Esc + возврат фокуса (e2e); контраст текста **≥ 4.5:1** (WCAG AA) в обеих темах.
    Включён в DoD. `[ДОБАВЛЕНО]`
- **NFR-8 Тестируемость:** unit-покрытие бизнес-логики и Playwright E2E ключевых сценариев.
  - **Fit criterion:** порог покрытия `packages/core` **≥ 90%** и `apps/server` **≥ 80%** в гейте
    CI; матрица ситуаций S1–S34 покрыта тестами (см. `test-situations.md`).
- **NFR-9 Наблюдаемость:** структурное логирование операций ФС и ошибок.
  - **Fit criterion:** каждая мутация ФС (create/write/delete/import/export) даёт структурную
    лог-запись; MCP логирует в stderr; тест проверяет наличие лога на ключевой операции.
    Включён в DoD. `[ДОБАВЛЕНО]`

## 5. Краевые случаи и обработка ошибок `[ДОБАВЛЕНО]`

- Каталог `Projects/` отсутствует/нет прав на запись → воссоздать или показать ошибку.
- Дубликат имени проекта / имени требования → блокировка с пояснением.
- Импорт битого/неполного архива, неизвестный формат → откат, понятная ошибка.
- Ручное редактирование/повреждение `.md` вне приложения → при чтении валидировать,
  помечать «битые» требования, не падать.
- Висячие/обратные ссылки при частично повреждённых данных → отчёт о целостности.
- Попытка создать цикл или второго родителя → отклонить с указанием конфликта.
- Очень длинные имена/описания, спецсимволы, эмодзи → валидация длины и санитизация.
- Конкурентные изменения файлов другим процессом → **последний-записавший побеждает + лог**
  (MVP). Модель конкурентности и путь к сериализации/optimistic-lock — ADR-004/SA-8. `[ДОПУЩЕНИЕ]`
- **Импорт архива с `schemaVersion` ≠ текущей `[ДОБАВЛЕНО v1.2 — SA-9/ARCH-006]`:** миграции в
  MVP нет → импорт **отклоняется** с явной ошибкой (несовместимая версия схемы); целевой
  каталог проекта **не создаётся**, temp очищается (как при битом архиве, FR-3.4). Аналогично —
  при открытии проекта с несовместимым `schemaVersion`: ошибка чтения, без «тихой» деградации.
- **Граница round-trip `[ДОБАВЛЕНО v1.2 — SA-9]`:** через импорт сохраняются **все** требования,
  их поля, сценарии и связи (archive-only: `.zip`/`.tar.gz`). Экспорт **`.xlsx` и
  `?format=openspec`-текст — только выгрузка** и в round-trip **не участвуют** (xlsx не
  импортируется — S19; OpenSpec-текст — для агентов, не путь импорта). `changes/` (задел
  дельт) в MVP не пишется/не читается UI.

## 8. Доработки v2 `[ДОБАВЛЕНО 2026-07-01]`

Принятые решения (детали — в `docs/architecture/`):

1. **Формат хранения — OpenSpec** (реальный формат). Требование = отдельный файл
   `openspec/specs/{functions|nfr}/<slug>.md` в разметке `### Requirement:` /
   `#### Scenario:`; манифест `openspec/project.md`. См. `ADR-001-openspec-storage.md`.
2. **`slug` вместо ULID `id`.** Непрозрачный идентификатор заменён человекочитаемым
   стабильным slug (уникален в рамках проекта, неизменяем при переименовании `name`).
   Связи ссылаются по `targetSlug`. Закрывает риск нечитаемых/висячих связей.
3. **Экспорт в Excel `.xlsx`** — дополнительно к архивам (листы `Requirements`, `Links`).
   Только выгрузка: xlsx **не импортируется** (импорт остаётся archive-only, round-trip).
4. **Единый слой видимости строк.** Поиск, «Скрыть зависимости» и мультиселект-фильтр
   критичности вычисляют один набор видимых строк; совпадение всегда показывается вместе
   с предками (без «сирот»). Поиск ∩ фильтр = пересечение.
5. **FR-7.4 закрыт:** длинное описание открывается в боковой панели (drawer) по клику.
6. **AI-ready:** REST `?format=openspec` + MCP-сервер (`apps/mcp`, stdio) поверх сервисов.

Соответственно закрыты открытые вопросы §7.1 (описание — drawer) и уточнён §2.5
(манифест — `openspec/project.md`).

## 9. Приоритизация (MoSCoW) и состав MVP `[ДОБАВЛЕНО v1.2 — BA-6]`

Каждому требованию присвоен приоритет: **Must** (без него нет MVP), **Should** (важно, но MVP
может выйти без него), **Could** (желательно, если есть ресурс), **Won't** (осознанно не в этом
релизе).

### Функциональные

| Приоритет | Требования |
|-----------|-----------|
| **Must** | FR-1, FR-2, FR-3, FR-4, FR-5, FR-6, FR-7, FR-8, FR-9, FR-10 (.1/.2 — архивы, round-trip) |
| **Should** | FR-10.4 (`?format=openspec` — «AI-ready» дифференциатор), FR-11 (фильтр реализации), FR-12 (просмотр связей), FR-13 (удаление связи), FR-16 (раскладка/без перекрытий) |
| **Could** | FR-10.3 (`.xlsx`-выгрузка), FR-14 (НФТ из строки ФТ), FR-15 (Excel «как в UI») |
| **Won't (этот релиз)** | Каскадное удаление/подъём потомков (альтернатива FR-9.3), авторинг сценариев в UI (§2.6/SA-10), импорт `.xlsx`, undo/история изменений (§1.4) |

### Нефункциональные

| Приоритет | Требования |
|-----------|-----------|
| **Must** | NFR-1, NFR-2, NFR-4, NFR-5, NFR-8 |
| **Should** | NFR-3 (перф-бюджет), NFR-6 (UX/подтверждения), NFR-7 (a11y WCAG AA), NFR-9 (наблюдаемость) |

### Состав MVP (явно)

**MVP = все Must (FR/NFR) + Should-набор**, дающий целевой поток «создать проект → внести
требования → связать в дерево → экспорт/импорт» и минимальную «AI-ready» ценность:
FR-1…FR-10 (вкл. FR-10.4 OpenSpec-экспорт), FR-11/FR-12/FR-13/FR-16; NFR-1…NFR-9.
**Вне MVP:** всё из строки **Won't** и требования уровня **Could** (FR-10.3, FR-14, FR-15) —
поставляются как инкремент после MVP. Границы MVP согласованы с §1.4 «Вне скоупа» и
[`context.md`](context.md) «Вне области».

## 10. Product use cases (SA-3) `[ДОБАВЛЕНО v1.2]`

FR из §3 — перечень возможностей; ниже ключевые FR раскрыты как **product use cases** (PUC)
с нормальным ходом, альтернативами и исключениями. Каждый шаг связан со строками матрицы
ситуаций S1–S34 (см. [`test-situations.md`](../architecture/test-situations.md)).

### PUC-3 — Импорт проекта (FR-3)
- **Актор:** PO. **Предусловие:** есть архив `.zip`/`.tar.gz`.
- **Нормальный ход:** (1) PO выбирает архив и задаёт имя → (2) система распаковывает во
  временный каталог → (3) валидирует структуру, `schemaVersion` и схему всех `.md` →
  (4) проверяет целостность связей → (5) атомарно вкатывает в `Projects/<name>` → (6) открывает
  проект. **Трассировка:** round-trip импорта — **S17** (zip), **S20** (tar.gz); авто-создание
  `Projects/` — **S23**.
- **Альтернативы:** `Projects/` отсутствует → воссоздать (FR-2.3, **S23**).
- **Исключения:** битый/неполный архив или неизвестный формат → откат, каталог не создаётся
  (FR-3.4); попытка импортировать `.xlsx` → отклонить (**S19**); `schemaVersion` ≠ текущей →
  ошибка, каталог не создаётся (§5/SA-9); имя с запрещёнными символами → отклонить (**S22**).

### PUC-6 — Создание/редактирование требования (FR-6)
- **Актор:** PO (или ИИ-агент — `create_requirement`/`update_requirement`). **Предусловие:** проект открыт.
- **Нормальный ход:** (1) PO открывает модалку по «+» → (2) вводит имя (live-проверка
  уникальности) → (3) критичность, описание, реализовано/квартал+год → (4) «Применить» →
  (5) система генерирует `slug`, сериализует OpenSpec-файл, атомарно сохраняет.
  **Трассировка:** round-trip serialize↔parse — **S1**; генерация/дедуп slug — **S7**.
- **Альтернативы:** одинаковое имя в другом типе (FUNCTION/NFR) — разрешено (**S9**);
  переименование `name` не меняет slug/файл/связи (**S10**).
- **Исключения:** дубль имени в своём типе (case-insensitive) → отклонить (**S8**);
  `implemented=false` без target / `implemented=true` с target → ошибка (**S2**, **S3**);
  описание > 5000 → ошибка (**S5**); пустое требование без описания и сценария → не сохранять
  (2.4.9); неполный сценарий (нет WHEN/THEN) → сохранить с флагом (**S6**).

### PUC-8 — Связывание требований (FR-8)
- **Актор:** PO (или ИИ-агент — `link_requirements`). **Предусловие:** ≥2 требования.
- **Нормальный ход:** (1) «Связать» → (2) выбор типа связи + поиск цели → (3) система проверяет
  целостность → (4) записывает реципрокную пару в оба файла (ADR-003).
- **Альтернативы:** `RELATES_TO` — симметрична, без ограничения цикла.
- **Исключения:** self-link → отклонить (**S11**); цикл PARENT_OF/CHILD_OF или DEPENDS_ON →
  отклонить с путём (**S12**, через MCP — **S33**); второй родитель → отклонить (**S13**);
  цель — несуществующий slug → отклонить, нет висячих (**S16**); разные типы для иерархии →
  отклонить (2.4.6).

### PUC-9 — Удаление требования (FR-9)
- **Актор:** PO (или ИИ-агент — `delete_requirement`). **Предусловие:** требование существует.
- **Нормальный ход:** (1) «Удалить» → подтверждение → (2) система удаляет файл и **все обратные
  ссылки** в других файлах. **Трассировка:** каскадная чистка обратных ссылок — **S14**.
- **Исключения:** у узла есть потомки → **отклонить с перечнем потомков** (FR-9.3, **S15**).

### PUC-10 — Экспорт (FR-10)
- **Актор:** PO (архив/xlsx) и ИИ-агент (`export_project`, `?format=openspec`).
- **Нормальный ход:** (1) PO выбирает формат (`.zip`/`.tar.gz`/`.xlsx`) → (2) система собирает
  самодостаточный набор → (3) отдаёт файл. **Трассировка:** archive round-trip — **S17**/**S20**;
  валидный `.xlsx` — **S18**; экспорт через MCP — **S34**.
- **Альтернативы:** агент запрашивает `?format=openspec` → детерминированный OpenSpec-текст
  (§1.2 fit-критерий байт-в-байт).
- **Исключения:** нет проекта → `404 NOT_FOUND`; неверный `format` → `400 BAD_REQUEST` (api.md).
