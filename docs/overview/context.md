# Границы системы и контекст (Volere) — «Управление требованиями для PO»

> Версия 1.0 · 2026-07-02 · Дополняет project.md (§1.2 акторы, §3 FR). SA-1.

Документ фиксирует **границы работы (work scope)** и **контекст системы** по методологии
Volere (Джеймс Робертсон): кто взаимодействует с системой (акторы), какие бизнес-события
пересекают её границу и что система выдаёт в ответ. Разграничение work scope vs product
scope — в §4.

Связанные документы: [`project.md`](project.md) (ТЗ, роли §1.2, FR §3, вне скоупа §1.4),
[`../architecture/api.md`](../architecture/api.md) (REST `?format=openspec`, MCP-tools),
[`../architecture/ADR-001-openspec-storage.md`](../architecture/ADR-001-openspec-storage.md)
(формат хранения OpenSpec/slug — источник истины).

---

## 1. Акторы

- **Product Owner (человек, первичный актор)** — локальный пользователь приложения. Через
  UI создаёт/редактирует ФТ и НФТ, строит дерево связей, импортирует и экспортирует
  архивы. Единственная роль-человек в MVP (аутентификация/права вне скоупа, project.md §1.4).

- **ИИ-агент через MCP (программный, stdio)** — клиент MCP-сервера `apps/mcp` (`@po/mcp`).
  Читает и (опционально) изменяет требования через MCP-tools поверх сервисов `@po/server`
  и общего `PROJECTS_ROOT`. Не человек, работает без UI. Доменные ошибки получает разборно
  (`isError: true`, текст `[CODE] message`).

- **ИИ-агент / скрипт через REST (программный, HTTP)** — клиент REST-контура `apps/server`,
  запрашивает машиночитаемый OpenSpec через `GET /api/projects/:id/requirements?format=openspec`
  (детерминированный, байт-в-байт стабильный вывод). Не человек, без UI.

- **Файловая система / внешний редактор (внешний источник)** — редактор или git-операция
  вне приложения, изменяющая `.md`-файлы требований напрямую в `Projects/`. Изменения
  приложение не контролирует; при чтении обязано валидировать и не падать.

- **Архив импорта (внешний источник)** — файл `.zip`/`.tar.gz` со структурой OpenSpec-проекта,
  передаваемый PO при импорте. Внешний по отношению к системе носитель данных.

Первичный актор-человек — **Product Owner**; остальные акторы — программные клиенты или
внешние источники данных.

## 2. Контекстная диаграмма

```
                      Product Owner (человек)
                              │
              UI-действия ▼   │   ▲ экраны, дерево,
              (CRUD, связи,   │   │ уведомления, скачивание
               импорт/экспорт)│   │ архива/xlsx
                              ▼   │
   ИИ-агент (MCP, stdio)  ┌───────┴────────────────────────┐   Архив импорта (.zip/.tar.gz)
   ── вызовы tools ──────▶│                                │◀── файл архива ── (вход, FR-3)
   ◀── requirement/       │   СИСТЕМА                       │
       broken/deleted ────│   «Управление требованиями PO»  │── архив .zip/.tar.gz ──▶
                          │                                │   / файл .xlsx (выход, FR-10)
   ИИ-агент/скрипт (REST) │   apps/web · apps/server ·      │
   ── GET ?format=openspec│   apps/mcp · packages/core      │
      ───────────────────▶│   хранилище: Projects/ (OpenSpec)│
   ◀── OpenSpec text /     │                                │
       JSON+broken ───────└───────┬────────────────────────┘
                                  │   ▲
             запись .md (atomic)  ▼   │  чтение .md
             экспорт/импорт           │  (валидация, пометка broken)
                          ┌───────────┴───────────┐
                          │  Файловая система /     │
                          │  внешний редактор       │
                          │  (ручная правка .md)    │
                          └────────────────────────┘
```

Легенда: стрелки `──▶` — вход в систему, `◀──` — выход из системы. Хранилище `Projects/`
показано внутри границы системы (источник истины), но правится и снаружи — внешним
редактором (нижний актор).

Каждое событие пересекает границу системы. Столбец «FR / MCP-tool» связывает событие с
функциональным требованием project.md §3 и/или именем MCP-tool (api.md).

## 4. Вне области (Out of scope)

Volere различает **границу работы (work scope)** — что система вообще обрабатывает как
события — и **границу продукта (product scope)** — какие из этих событий автоматизирует
поставляемый MVP. Ниже перечислено то, что **вне области**: либо не является событием
системы вовсе (за пределами work scope), либо сознательно исключено из MVP (за пределами
product scope).

**За пределами work scope (система этим не занимается вообще):**
- **Аутентификация и разграничение прав** — приложение локальное, single-user; нет
  события «вход пользователя», нет ролей/ACL (project.md §1.4).
- **Многопользовательский режим и совместное редактирование** — нет событий от нескольких
  одновременных пользователей; конкурентная правка файла = «последний записал побеждает» + лог.
- **Облачное хранилище и синхронизация между устройствами** — источник истины только
  локальная ФС `Projects/`; события синхронизации отсутствуют.
- **Версионирование / история изменений требований** — кроме того, что даёт **git вне
  приложения**; внутри приложения нет undo/истории/diff как событий.
- **Редактирование сырого Markdown как текста** — приложение управляет структурой (поля,
  связи), а не свободным текстом файла; «сохранить произвольный MD» не является событием
  системы (правка сырого файла проходит только через внешнего актора, событие #24).

**За пределами product scope (событие возможно, но в MVP не автоматизировано):**
- **Импорт `.xlsx`** — только выгрузка (событие #13); round-trip остаётся **archive-only**
  (импорт лишь `.zip`/`.tar.gz`). Обратный разбор Excel в MVP не реализуется.
- **Авторинг сценариев (`#### Scenario:`) в UI** — сценарии **read-only из импорта**;
  создание/редактирование сценариев через UI **вне MVP** (project.md §2.1, §2.6, SA-10).
- **Миграция схемы при `schemaVersion` ≠ текущей** — при несовпадении версии схемы в MVP
  система выдаёт **ошибку** (не мигрирует автоматически); автоконвертация форматов вне MVP.
