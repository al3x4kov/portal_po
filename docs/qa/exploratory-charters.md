# Session-Based Exploratory Testing — Charters (QA-5)

Формат: session-based test management (SBTM). Каждый чартер — тайм-боксированная
исследовательская сессия с явной миссией, областью и рисками. Заряды покрывают
квадрант Q3 (exploratory / edge / UAT) — то, что плохо ловится скриптовыми e2e.

Обозначения: **TB** — тайм-бокс; **O** — области; **R** — риски/гипотезы дефектов.
Автоматизированные follow-up указаны ссылкой на спеку `e2e/tests/*`.

---

## CH-1 · Устаревшие данные и конкурентные сессии

- **Миссия:** выяснить, что происходит при правке/удалении требования, которое
  параллельно изменила «другая сессия» (второй REST/MCP-клиент или вторая вкладка).
- **TB:** 60 мин.
- **O:** RequirementModal (save/confirm), ConfirmDialog удаления, LinkModal,
  инвалидация react-query, REST `PUT/DELETE /requirements/:slug`, lock проекта.
- **R:** тихая потеря обновления (last-write-wins); «воскрешение» удалённой записи;
  висячая связь после гонки; неинформативная ошибка вместо консистентности.
- **Автоматизация:** `e2e/tests/stale-boundary.spec.ts` (QA-5b) — правка и удаление
  записи, удалённой другой сессией, дают видимую ошибку и консистентное состояние.

## CH-2 · Граничные и «злые» имена

- **Миссия:** проверить именование требований/проектов на границах.
- **TB:** 45 мин.
- **O:** поле «Название» RequirementModal, живой check-name, слугификация,
  создание проекта.
- **R:** пустое/из одних пробелов имя проходит; обрезка на 200 символов теряет
  данные без предупреждения; Unicode/emoji ломают slug или отображение; коллизии
  регистра (FR-6.6) обходятся.
- **Автоматизация:** `e2e/tests/stale-boundary.spec.ts` (QA-5c) — пусто / пробелы /
  200 символов / Unicode+emoji; `edge-cases.spec.ts` — дубликаты/регистр.

## CH-3 · Целостность связей на границах (UX-4)

- **Миссия:** попытаться создать недопустимую связь всеми путями UI.
- **TB:** 45 мин.
- **O:** LinkModal (типы связей, недоступные цели, причины), чипы связей в дереве,
  реципрокные пары, каскад при удалении.
- **R:** несовместимая цель кликабельна; submit пропускает цикл/второго родителя;
  реципрокная связь не удаляется у второго конца; расхождение клиент/сервер.
- **Автоматизация:** `edge-cases.spec.ts` (цикл, второй родитель — блокировка в
  модалке), `po-ux.spec.ts` (T2/T3 реципрокное удаление).

## CH-4 · Доступность с клавиатуры и скринридером

- **Миссия:** пройти основные сценарии только с клавиатуры; проверить фокус-ловушку.
- **TB:** 60 мин.
- **O:** все модалки/диалоги (Modal, ConfirmDialog, LinkModal), тосты (aria-live),
  фильтры-дропдауны, дерево (шеврон-тоггл), контраст вторичного текста.
- **R:** фокус уходит за модалку; не возвращается на триггер; деструктивная кнопка
  в фокусе по умолчанию; тост не озвучивается; контраст < WCAG AA.
- **Автоматизация:** `e2e/tests/a11y.spec.ts` (QA-1) — axe + фокус-ловушка/Esc/возврат.

## CH-5 · Масштаб и отзывчивость

- **Миссия:** оценить usability большого проекта (сотни требований).
- **TB:** 45 мин.
- **O:** дерево, поиск, фильтры критичности/реализации, sticky-тулбар, экспорт.
- **R:** горизонтальный скролл страницы; заметные задержки поиска/фильтра;
  «Показано N из M» рассинхронизирован; экспорт таймаутит.
- **Автоматизация:** `e2e/tests/scale.spec.ts` (QA-2) — ~300 требований, поиск,
  фильтр, отсутствие горизонтального скролла.

## CH-6 · Импорт/экспорт и битые данные

- **Миссия:** проверить round-trip и устойчивость к плохим архивам/битым файлам.
- **TB:** 45 мин.
- **O:** экраны Import/Export, панель `broken-panel`, xlsx/zip/tar.gz, версии схемы.
- **R:** битый .md рушит загрузку вместо пометки; импорт принимает будущую
  schemaVersion; частичный импорт; xlsx-ошибка не показана.
- **Автоматизация:** `import-export.spec.ts`, `xlsx-export.spec.ts`,
  `edge-cases.spec.ts` (битый/чужой формат).

# Запись сессии №1 (первая проведённая)

- **Чартер:** CH-1 · Устаревшие данные и конкурентные сессии.
- **Дата:** 2026-07-02.
- **Тестировщик:** QA (session-based).
- **Длительность:** 60 мин (setup 10 / test 40 / bug-investigation 10).
- **Сборка:** ветка `council-rework`, реальный сервер + web (playwright webServer).

### Что делали (test notes)

1. Создали проект, добавили ФТ «F-stale». Открыли модалку редактирования.
2. Вторым клиентом (REST `DELETE /requirements/:slug`, эмуляция второй сессии)
   удалили ту же запись.
3. Сохранили правку в открытой модалке → получили видимую ошибку `req-error`
   (NotFound), модалка не закрылась «молча». После reload запись отсутствует —
   правка её НЕ воскресила и не задублировала. ✅ Консистентно.
4. Повторили для удаления: открыли диалог удаления листа, удалили запись второй
   сессией, подтвердили удаление → `delete-dialog-error` видима. ✅
5. Побочно проверили гонку create/create одинакового имени (два параллельных
   POST): второй отклонён по уникальности, манифест валиден, дублей slug нет.

### Наблюдения / риски

- **R-1 (известный, ARCH-2/QA-3):** правка требования, у которого другая сессия
  сменила *только имя* (slug неизменен), проходит по схеме last-write-wins —
  «тихая» перезапись без предупреждения. Явной optimistic-lock (If-Match/версия)
  нет. Для сценариев «удалено другой сессией» поведение корректно (ошибка), для
  «изменено другой сессией» — потенциальная тихая потеря. Отнесено к системному
  риску конкурентности (вне правок QA; фикс — на бэкенде).
- **O-1:** тосты успеха создаются и озвучиваются (aria-live) — обратная связь есть.

  delete-then-delete).
- Открыто для бэкенда: optimistic concurrency для update (R-1) — см. ARCH-2/QA-3.
