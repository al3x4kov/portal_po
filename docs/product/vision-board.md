# Product Vision Board — «Управление требованиями для PO»

> Дата: 2026-07-07 · Автор: draft по итогам совета (PO-2). **Статус: `[НА РЕВЬЮ PO]`** —
> черновик на основе `project.md` §1 и легализации AI (v1.3). Правьте свободно; поля Vision Board
> по Пихлеру. После утверждения снять пометку и сослаться из `project.md` §1.

## Vision (зачем продукт существует)

> Дать Product Owner'у **локальный, файловый источник истины требований**, который одновременно
> **читаем человеком и машиной** (OpenSpec/MCP), чтобы требования можно было вести без БД и
> сервера и напрямую отдавать ИИ-агентам как контекст разработки. AI-ассистент **ускоряет ввод**
> (черновики из документации, генерация описаний), но ответственность за содержание остаётся за PO.

## Target Group (для кого)

- **Первичный пользователь:** Product Owner / системный аналитик, ведущий требования продукта
  локально, ценящий версионируемость (git) и отсутствие облачной зависимости.
- **Вторичный потребитель:** ИИ-агент разработки, читающий требования через OpenSpec-экспорт / MCP.
- **Не целевые (сейчас):** распределённые команды с одновременным редактированием, менеджмент без
  инженерного контекста, крупные организации с требованием SSO/прав (см. §1.4 «вне скоупа»).

## Needs (какую проблему решаем)

- Требования разрознены (вики/таблицы/чаты), не машиночитаемы, «протухают» относительно кода.
- Нужен инструмент, где требования — **структурированные файлы** (тип, критичность, срок, связи,
  сценарии), с проверками целостности (уникальность, дерево без циклов, один родитель), экспортом/
  импортом и **машинным контрактом** для агентов — без развёртывания БД/облака.
- Быстро превратить сырой документ (PDF/Word/архив) в структурированные ФТ/НФТ — задача AI-импорта.

## Product (что это, ключевые фичи)

- Локальный SPA + Node-сервер, источник истины — `.md` в `Projects/` (OpenSpec/slug, ADR-001).
- CRUD требований, дерево/граф связей, проверки целостности, импорт/экспорт (zip/tar.gz/xlsx),
  OpenSpec-экспорт (`?format=openspec`), MCP-сервер для агентов.
- **AI-надстройка (ускоритель, v1.3):** чат-помощник, генерация описания, AI-импорт ФТ/НФТ из
  документации (внешний LLM, ADR-007). Ядро работает без AI.

## Business Goals (зачем это нам / оправдание)

> `[НА РЕВЬЮ PO — заполнить/уточнить]` Ориентиры (draft):
- Продукт — **инструмент PO для agent-ready разработки**: ценность в том, что требования становятся
  прямым, поддерживаемым контекстом для ИИ-агентов (OpenSpec/MCP), сокращая петлю «требование → код».
- Для локального demo-MVP бизнес-цель — **валидировать две гипотезы ценности** (см. `metrics.md`):
  (1) машиночитаемый вывод реально используется агентами; (2) AI-импорт даёт качественный черновик,
  экономящий время PO.
- Монетизация/масштабирование — **вне текущего MVP**; сначала подтверждение ценности.

## Дифференциатор (актуальная реальность)

- **Главная гипотеза (ядро):** *AI-consumable output* — требования как источник истины для агентов
  (OpenSpec + MCP). Это отличает продукт от обычных трекеров требований.
- **Вторичная гипотеза (ускоритель):** *AI-assisted authoring* — AI черновит требования из
  документации, PO ревьюит. Ценно, но подчинено ядру; подлежит отдельной проверке (метрики PO-4).
- Осознанный выбор (подтверждён PO 2026-07-07): продукт — **не** «AI пишет требования вместо PO»,
  а «PO ведёт машиночитаемые требования, AI помогает вводить».
