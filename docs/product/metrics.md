# Метрики успеха и обратная связь — «Управление требованиями для PO»

> Дата: 2026-07-07 · Автор: draft по итогам совета (PO-4). **Статус: `[НА РЕВЬЮ PO]`.**
> Расширяет `project.md` §1.3 (там было 2 активационные метрики). Пороги — черновые, на подтверждение.

## 1. Активация и удержание PO (ядро продукта)

| KPI | Определение | Целевой ориентир `[НА РЕВЬЮ]` |
|---|---|---|
| Активация | PO создал проект → внёс ≥20 требований → выполнил экспорт | достигается в 1-ю сессию |
| Round-trip целостность | экспорт → импорт без потери требований/связей | 100% (инвариант, тест S17/S20) |
| Возврат | PO возвращается к проекту повторно (≥2 сессии) | `[НА РЕВЬЮ — задать порог]` |

## 2. Ценность машиночитаемого вывода (ГЛАВНАЯ гипотеза)

> Гипотеза: требования реально используются ИИ-агентами как источник истины (OpenSpec/MCP).

| KPI | Определение | Порог «гипотеза подтверждается» |
|---|---|---|
| Использование OpenSpec/MCP | факт чтения требований агентом (экспорт `?format=openspec` / вызовы MCP-tools) | `[НА РЕВЬЮ]` — есть регулярное потребление |
| Полнота критериев приёмки | доля требований БЕЗ `incomplete[]`-пометки (есть описание/сценарии) | растёт со временем; ориентир ≥70% |

*Примечание: продукт уже отслеживает «неполные» требования через `incomplete[]` (мягкая пометка, не
блок — см. BA-2, §2.4.9). Это прямой сигнал проверяемости.*

## 3. Ценность AI-ускорителя (ВТОРИЧНАЯ гипотеза, самая рисковая)

> Для каждой AI-фичи — измеримая метрика и порог «фича оправдана / нет».

| Фича | Метрика | Порог «оправдана» `[НА РЕВЬЮ]` |
|---|---|---|
| AI-импорт из документации (FR-20) | acceptance-rate: доля извлечённых ФТ/НФТ, принятых PO без существенной правки | напр. ≥60% принятых |
| — качество извлечения | провенанс сохранён; нет «домысленных» требований вне источника (golden rule FR-20.3) | 0 домыслов в выборке ревью |
| Генерация описания (FR-19) | доля сгенерированных описаний, принятых/минимально правленых | напр. ≥50% |
| AI-чат (FR-18) | adoption: доля сессий с обращением к чату | `[НА РЕВЬЮ]` |

**Правило де-рискинга (PO-5):** если AI-импорт не проходит порог качества извлечения — не
инвестировать в полировку параметров, а вернуться к валидации ядра ценности.

## 4. Петля обратной связи

> Даже для локального single-user demo нужен лёгкий механизм.

- `[НА РЕВЬЮ PO]` Минимальный вариант: короткая заметка/лог решений PO (что принял/отклонил из
  AI-черновиков) — источник acceptance-rate без телеметрии наружу (приватность, ADR-007).
- Периодический само-ревью против метрик §2–§3 (напр. раз в релиз): подтверждается ли главная
  гипотеза; оправдан ли AI-ускоритель.
- Явный чек «что мешает» — какие требования остаются `incomplete[]`, где AI-импорт ошибается.
