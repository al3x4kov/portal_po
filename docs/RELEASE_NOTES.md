# Release Notes

## 2026-08-04 — Логическое дерево «навык AI Product Owner» в AI-импорте документации (buildTree)

По пилоту: на большой документации извлекаются сотни ФТ/НФТ, но легаси-этап
структуризации не может создавать группирующие узлы (родителем может быть только
другое извлечённое требование) и обрезает список допустимых родителей до 4000
символов — итог закономерно деградировал в плоский список из ~1000 корневых ФТ.

- **Новый opt-in этап (чекбокс «Собрать логическое дерево требований (навык AI
  Product Owner)» в модалке AI-импорта; multipart-поле `buildTree`, по умолчанию
  выключено — легаси-путь не изменён).** Вместо зеркалирования структуры файлов
  модель-«PO» работает в два прохода:
  1. **Таксономия** — map-reduce по батчам имён (150/раунд): модель проектирует
     компактную бизнес-таксономию (домены → разделы, ровно 2 уровня; «Прочее»/
     имена файлов запрещены промптом), каждый раунд видит и расширяет текущую.
     Слияние детерминированно: первый ответ побеждает, капы ширины (16 корней
     на тип, 20 разделов у домена), глубже двух уровней — перевешивание под
     домен, циклы рвутся до записи.
  2. **Раскладка** — каждому требованию ровно один узел по короткому id
     («F1.2», «N3»; батчи по 40): неизвестные id, чужой тип и посторонние имена
     отбрасываются с warn — требование остаётся корневым, job не падает.
- **Группирующие узлы создаются как обычные требования** (origin `AI_DOCS` — 
  подсветка «создано ИИ, не проверено» работает и для них) через существующий
  aggregate/populate: дедуп, разрыв циклов, идемпотентный re-run и gap-fill
  переиспользованы без изменений; совпадение имени узла с извлечённым
  требованием не дублирует запись — требование само становится узлом.
- **Structured output по прецеденту бэклог-хотфикса:** у каждого вида вызова
  СВОЯ строгая json_schema (`po_taxonomy_nodes`, `po_tree_assignments`) с
  фолбэком json_object → текст; сквозной тест закрепляет имена схем.
- Чекпоинт хранит `buildTree` (resume продолжает в том же режиме; старые
  чекпоинты читаются как false). Лог этапа — по-русски: раунды таксономии,
  сводка «доменов/разделов», счётчики раскладки и создаваемых узлов.
- Тесты: 3 контрактных (@po/core) + 11 unit слияния таксономии + 7 изолированных
  этапа + 3 сквозных сервисных (дерево/идемпотентность/легаси-путь без вызовов)
  + 2 компонентных на чекбокс; полная регрессия unit/component зелёная (2020).

## 2026-08-04 — Подсветка непроверенных ИИ-требований в дереве (task26)

После AI-импорта было не видно, что уже провалидировано, а что нет — всё дерево
выглядело единообразно. Теперь созданное ИИ подсвечено, пока PO не отметит проверку.

- **Признак происхождения в контракте:** у требования появились `origin`
  (`AI_DOCS` / `AI_BACKLOG`, проставляет только сервер при импорте) и `aiValidated`.
  Правило подсветки живёт в ядре одним хелпером `isAiPendingReview` — фронт его
  потребляет, не дублирует. Поля переживают round-trip `.md` и экспорт/импорт
  архива; старые файлы без полей читаются как «создано человеком» (ретро-пометки нет).
- **Дерево:** непроверенные ИИ-строки залиты мягким тоном и несут бейдж «ИИ»
  с подписью «Создано ИИ, не проверено» (цвет — не единственный признак).
- **Карточка требования:** для ИИ-требований блок «Проверка» с переключателем
  «Проверено» — включение снимает подсветку без перезагрузки, выключение возвращает
  (отметка обратима). У требований, созданных вручную, блока нет.
- **Фильтр и счётчик:** в панели фильтров — «Непроверенные» (полная формулировка
  в подсказке) и счётчик «Не проверено: N» по всему проекту; клик по счётчику
  включает фильтр, сброс фильтров — выключает. Фильтр пересекается с поиском и
  остальными фильтрами, предки показываются как контекст.
- Тесты: 25 контрактных + 14 серверных + 22 компонентных + 5 E2E
  (`ai-pending-highlight.spec.ts`: подсветка после обоих импортов, снятие и возврат
  отметки, ручное требование, фильтр со счётчиком).

Вне объёма v1 (по решению PO): массовое снятие отметок, ретро-миграция уже
загруженных требований, история проверок, подсветка в графе и на дашборде.

## 2026-08-04 — Редактирование разметки на шаге выверки AI-импорта бэклога (task25)

До записи в проект строки разметки теперь можно править прямо в таблице выверки:

- **Бизнес-имя** — инлайн-редактирование (Enter/blur сохраняет, Esc отменяет,
  пустое имя не принимается); бейдж «изменено» у отредактированных строк.
- **Узел (куда встроится)** — поповер с регистронезависимым поиском по
  существующим узлам нужного типа (с подсказкой типа и родителя), пунктом
  «Создать новый узел: „…“» (корневой) и кнопкой «Вернуть предложенное».
- **«Срок реализации»** (переименованная колонка Target, в выверке и отчёте) —
  выбор квартала и года в ячейке; маркер «из файла» сменяется на «изменено».
- Контракт: `POST /api/ai-import/:jobId/apply` принимает опциональные
  `overrides` по строкам (имя / узел existing|new / срок парой); сервер
  валидирует (русские 400: несуществующий узел типа строки, пустое имя, год вне
  2020–2100 — шаг выверки при этом жив), мерджит правки до записи, новый узел
  дедупится с предложенными моделью; правки персистятся в чекпоинт
  (идемпотентный повторный apply). Обратная совместимость: apply без overrides
  работает как раньше. Отчёт показывает отредактированные значения.
- Дубли-строки не редактируются. Правки живут до записи (v1).
- Тесты: 8 контрактных + 7 серверных + 12 компонентных + 6 E2E
  (`ai-backlog-review-edit.spec.ts`), регрессия бэклог-сьюта зелёная.

Известное (вне объёма, follow-up): контентная эвристика колонок xlsx считает
заголовок «непустой ячейкой» — у файла с ОДНОЙ строкой данных колонки ключа и
срока не распознаются (порог 0.6); лечится порогом по строкам данных.

## 2026-08-04 — Хотфикс: AI-импорт бэклога не размечал строки на реальных моделях

По логу пилота (log1.log): каждый ответ модели на разметку бэклога «не распознан»,
батчи делились до одной строки, прогон падал с MODEL-01.

- **Причина:** матч-вызовы бэклога отправляли модели `response_format` со схемой
  ДРУГОЙ стадии (извлечения из документации, `extracted_requirements`). Модель,
  соблюдающая строгую json_schema (DeepSeek и др.), возвращала записи без
  `rowId`/`businessName` — парсер законно браковал 100% ответов.
- **Фикс:** негоциатор structured output параметризован схемой стадии; матч-вызовы
  шлют собственную строгую схему `backlog_match_answers` (корень `{"answers":[…]}`,
  поля зеркалят контракт разметки). Фолбэк json_object/none и путь документации
  не изменились.
- **Гард от регрессии:** unit-тест воспроизводит прод-баг (analyze-схема в
  матч-вызове → отказ парсера); e2e-стаб модели теперь «уважает» присланную
  json_schema как реальная модель — отвечает по чужой схеме без rowId и валит
  тест при повторении ошибки; в happy-path обеих модалок — ассерты имени схемы.
- Тесты: +9 unit (server), стаб-гард + ассерты в E2E; бэклог-сьют 6/6, полная
  регрессия AI-сьютов зелёная.

## 2026-08-04 — Экономика вызовов AI-импорта документации (todo_23)

По итогам разбора реального лога пилота (89 минут прогона: 71% вызовов с нулевым
результатом, ~30% вызовов — ложные повторы «контроля полноты», ~39 минут в
тайм-аутах, «создано 0» при 1037 извлечённых записях).

- **Батчинг мелких файлов:** файлы одного класса источника пакуются в общий фрагмент
  до размера чанка (разделители «=== Файл: … ===», provenance пофайльно); сотни
  одиночных вызовов схлопываются в десятки. Смета это учитывает; прогресс показывает
  «фрагмент X из Y (N файлов)»; чекпоинты/resume работают по пакетам.
- **Контроль полноты — только для release notes:** максимум один повторный проход
  на фрагмент; для остальных классов повторов больше нет (строки произвольных
  md-таблиц не считаются «ожидаемыми записями»).
- **Честные счётчики:** в прогрессе и результатах — «извлечено (ждёт записи): N ФТ,
  M НФТ» (живые с этапа анализа, переживают resume); при остановке/ошибке с
  незаписанным извлечённым — явная строка «сохранены в контрольной точке,
  „Продолжить“ доведёт до создания», и кнопка «Продолжить» теперь есть и в
  состоянии «Остановлено» (раньше — только при ошибке/рестарте).
- **Быстрее после сбоев:** первый повтор после тайм-аута вызова ждёт 15–30 с
  (вместо полного цикла); параллелизм после деградации восстанавливается
  (+1 после каждых 3 успешных вызовов, с INFO-строками об изменении K).
- **Пульс инвентаризации:** стадии распаковки/описи/классификации пишут прогресс
  («Опись: просмотрено файлов A из B…»), минут тишины в начале больше нет.
- Тесты: 16 unit backend + 6 контрактных + 8 компонентных + E2E-сьют
  `ai-import-todo23.spec.ts` (батчинг, остановка→«Продолжить» через UI без дублей,
  сбой→resume, пульс описи, восстановление параллелизма); полная регрессия
  AI-сьютов зелёная.
- Вне объёма (зафиксировано): инкрементальный populate; глобальный пул параллелизма
  по пакетам (сейчас пакеты идут последовательно — отдельное ТЗ).

## 2026-08-03 — AI-импорт бэклога из xlsx (todo_22, задача 2)

Новый сценарий: выгрузка бэклога (Jira-xlsx: «Issue key» + «Summary») превращается в
требования, встроенные в существующее дерево ФТ/НФТ. Кнопка «AI подгрузка из бэклога» —
рядом с «AI подгрузка из документации».

### Поток
- **Загрузка и предпросмотр:** колонки (ключ / формулировка / срок) распознаются по
  содержимому, не по заголовкам; первые строки, счётчики, мини-смета; поле «целевой
  квартал/год» для строк без срока в файле (сроки из файла — приоритетнее: xlsx-даты
  и текстовые «Q1 2027» понимаются).
- **AI-соотнесение (батчи ≤20):** модель получает карту дерева и для каждой строки
  возвращает бизнес-имя, тип (ФТ/НФТ), узел — существующий или НОВЫЙ бизнесовый
  (технические группировки вида «Бэклог»/«Прочее» запрещены промптом); галлюцинации
  родителей/дублей нейтрализуются кодом; реюз всей устойчивости todo_20 (ретраи,
  тайм-ауты, чекпоинты на батч, resume, таксономия ошибок).
- **Выверка перед записью (гейт PO):** до подтверждения в проект не пишется НИЧЕГО.
  Таблица разметки с чекбоксами (дубли выключены), список создаваемых узлов,
  «Записать в проект (N)». Закрытие модалки сохраняет разметку — шаг переоткрывается
  из истории; повторный импорт при заброшенной выверке подсказывает, где её завершить.
- **Запись:** новые узлы → требования → связи CHILD_OF; описание = исходная
  формулировка + «Ключ бэклога: …»; `implemented=false` + target; у каждого
  требования источник нового типа **«Бэклог»** (`SourceType BACKLOG`, авто-словарь
  «Бэклог: <файл>»); идемпотентный повторный apply. Итоговый отчёт: счётчики +
  полная таблица соответствий (бейджи «дубль»/«НФТ»/«новый узел»), usage, лог файлом.

### Технически
- xlsx-ридер: adm-zip + fast-xml-parser (новая лёгкая зависимость сервера); shared/
  inline strings, кэш формул, лимиты 10 МБ / 5000 строк; битые файлы → понятные
  ошибки DATA-04/DATA-05.
- Контракт: `SourceType += BACKLOG` (обратная совместимость .md), `kind:
  'docs'|'backlog'` у джоб, статус `awaiting-review`, схемы preview/mapping/review/
  report, роуты `POST /api/projects/:id/ai-backlog-import`, `POST
  /api/ai-import/:jobId/apply`, confirm с телом `{targetQuarter, targetYear}`.
- История джоб — общая, с бейджем типа («Документация»/«Бэклог»).
- Тесты: 45 unit server/core (включая фикстуру реальной Jira-выгрузки на 293 строки),
  20 компонентных, 6 E2E (happy-path с выверкой и снятием строки, дубль, сбой→resume
  без переоплаты батчей, отмена без записи, история, 409-подсказка); полная регрессия
  AI-сьютов зелёная.

### Известное (не блокер)
- Счётчик «дублей пропущено» в отчёте считает дубли среди ВЫБРАННЫХ строк; в UI дубли
  по умолчанию сняты и попадают в «не выбрано» (сам дубль виден в таблице с бейджем).
  Семантику счётчиков можно уточнить отдельной задачей.

## 2026-08-03 — Качество AI-анализа загруженной документации (todo_20)

Полная переработка конвейера AI-импорта: полнота извлечения на слабых моделях, живучесть
длинных прогонов, человеческие ошибки с планом действий. Закрывает и пилотное замечание №3
(неинформативный «Timeout»).

### Подготовка данных до вызовов модели
- Опись и контентный триаж архива после распаковки: класс источника (release notes /
  руководства / администрирование / безопасность / API / конфигурация / прочее)
  определяется по содержимому, не по именам файлов; неопознанное классифицирует модель
  батчами, при недоступности — класс «прочее» (файл всё равно обрабатывается). Исключения
  (изображения, бинарные) — всегда с причиной.
- Format-aware нормализация: JSON-массивы записей (любые диалекты ключей), MD-таблицы и
  YAML разворачиваются детерминированным кодом до текста для модели.
- Приоритет обработки по ценности источника (release notes первыми).
- Шаг «Смета» до старта: файлов/фрагментов/вызовов/токенов; выше порога (настраиваемый,
  дефолт 2 млн токенов) — явное подтверждение «Запустить всё равно».
- Лимит архива поднят до 200 МБ / 2000 текстовых файлов (опись потоковая).

### Конвейер, дружелюбный к слабым моделям
- Адаптивные фрагменты: половинение при обрезании ответа/невалидном JSON/context_length,
  восстановление после серии успехов.
- Structured output (`response_format: json_schema → json_object`) с фолбэком на
  «текст + парсер» — бэкенды без поддержки (vLLM/Ollama/прокси) работают не хуже прежнего.
- Плоская схема извлечения + few-shot примеры по классу источника.
- Детерминированная дедупликация результатов фрагментов (нормализация имени + fuzzy),

## 2026-07-06 — AI-импорт: `maxOutputTokens` = полный бюджет вызова (лечит «ответ обрезан по лимиту токенов»)

Правка бэкенда для «думающих» моделей (`reasoning: 'strip'`), которые тратят часть бюджета на
`<think>…</think>` ДО JSON-ответа.

- **`max_tokens` вызовов импорта = `preset.maxOutputTokens` целиком** (было
  `min(константа_шага, preset.maxOutputTokens)`). Раньше per-call константы (2000 извлечение /
  4000 структура и связи) резали бюджет вниз, и поднятие `maxOutputTokens` выше 4000 ни на что не
  влияло — ответ думающей модели обрезался. Теперь `maxOutputTokens` — реальный бюджет генерации
  на один вызов импорта (reasoning + ответ): маленький оверрайд реально уменьшает, большой —
  увеличивает. Мёртвый параметр `maxTokens` убран из `chatWithJsonRetries` и call-sites
  (извлечение/структура/связи).
- **Дефолты «думающих» моделей подняты под reasoning:** `Qwen/Qwen3.6-27B` 6000 → **12000**,
  `Qwen/Qwen3.5-397B-A17B` 8000 → **16000**. `Qwen/Qwen3-Coder-Next` и generic `__default__` —
  без изменений (4000).
- **Chat и генерация описания не затронуты:** там `max_tokens` по-прежнему клампится своими
  небольшими константами (`AI_CHAT_MAX_TOKENS` 1000 / `AI_GEN_MAX_TOKENS` 700), а
  `maxOutputTokens` служит только верхней границей.

## 2026-07-05 — AI-импорт: привязка НФТ к ФТ (RELATES_TO)

### Что изменилось
- **НФТ больше не только глобальные.** Если документация явно говорит, что нефункциональное
  требование ограничивает конкретную функцию («время ответа поиска ≤ 200 мс» → ФТ «Поиск»),
  импорт создаёт связь `RELATES_TO` НФТ → ФТ (симметричная запись на обоих концах).
  Иерархия CHILD_OF по-прежнему только внутри одного типа — это ассоциативная связь.
- **Привязка извлекается только на этапе extraction** — там модель видит текст фрагмента
  и есть доказательство. Structure-вызов текста не видит и привязку не строит (защита от
  галлюцинаций). Новое опциональное поле ответа модели: `relatedFunctions: [имена ФТ]`
  (до 20, только у НФТ; у ФТ игнорируется с warn). Новых вызовов к AI hub нет.
- **Резолв имён**: регистронезависимый; работает и для ФТ, существовавших в проекте до
  импорта. Неизвестная ФТ → warn «связанная ФТ … не найдена — связь пропущена», job
  продолжается.
- **Идемпотентность re-run**: повторный импорт докомплектовывает недостающие RELATES_TO
  и никогда не дублирует существующие.
- **Счётчик**: новое поле `relatesLinks` в результате job; в done/cancel-сводках лога и
  в модалке — «связей НФТ→ФТ: N».
- Гипотеза о ложных CYCLE при перекрёстных привязках проверена и опровергнута тестом:
  `RELATES_TO` исключён из цикл-проверки в core (ранний return в integrity), LinkService
  не менялся; DomainError на создании связи на всякий случай деградирует в warn.

### Тесты
Unit: 1054 зелёных (+18: схема, union при дублях, регистронезависимый резолв, pre-existing ФТ,
идемпотентность, FUNCTION-игнор, DomainError→warn, cancel, счётчики, гипотеза assertNoCycle).
E2E: 170 зелёных (+4: сквозная связь через API и UI-счётчик, warn на неизвестную ФТ,

## 2026-07-05 — AI-импорт: валидность дерева ФТ/НФТ/связей (аудит структуризации)

### Исправлено
- **Обрезка ответа структуризации (баг).** Structure-вызов шёл с общим лимитом 2000 токенов,
  а JSON-ответ на батч из 100 узлов занимает ~3000–5000 — ответ гарантированно обрезался,
  3 ретрая не помогали, и на крупных проектах дерево всегда деградировало в плоский список.
  Теперь отдельный `AI_IMPORT_STRUCTURE_MAX_TOKENS = 4000` и батч 50 (`AI_IMPORT_STRUCTURE_BATCH`
  перенесён в `@po/core`).

### Качество дерева и связей
- **Восстановление обрезанного JSON**: если массив оборван на середине объекта, парсер
  достраивает его по последнему полному узлу; `finish_reason='length'` детектится и логируется
  warn «ответ модели обрезан по лимиту токенов».
- **Анти-фрагментация батчей**: каждый structure-батч получает полный список всех требований
  («допустимые родители», бюджет 4000 символов) — родитель может быть из другого батча.
- **Провенанс в структуризации**: строки батча теперь `TYPE\tимя\tисточник` («файл § раздел») —
  модель группирует требования по реальной структуре документации.
- **Разрыв циклов до наполнения**: цепочки родителей проверяются заранее, цикл рвётся
  детерминированно с warn «Цикл разорван: «X» становится корневым» (раньше — невнятная
  ошибка на создании связи).
- **Best-effort на 3-й попытке**: из частично невалидного ответа принимаются валидные узлы
  (warn «принято N из M») вместо потери всего батча.

### Логирование (под progress bar)
- Стартовый лог объёма: «Модель: X. Файлов: N, фрагментов: M.»
- Отчёт покрытия каждого батча: посторонние узлы (игнорируются и не попадают в дерево),
  требования без узла в ответе (останутся корневыми), конфликты узлов (первый выигрывает).
- Отдельный warn для родителя другого типа (иерархия только внутри ФТ/ФТ и НФТ/НФТ).
- Сводка дерева: «Дерево: ФТ — X корней, Y с родителем; НФТ — …; максимальная глубина D».
- Ретрай extraction теперь срабатывает и когда массив пришёл, но все записи невалидны
  (чистый `[]` — валидный ответ «требований нет», не ретраится).
- При 0 извлечённых требований стадия структуризации пропускается без вызовов к AI hub.

## 2026-07-05 — AI-импорт: древовидная структура ФТ/НФТ, чистые поля, ретраи JSON

### Что изменилось
- **Дерево вместо двух плоских списков.** В пайплайн импорта добавлена новая стадия
  `structure` (unpack → analyze → **structure** → aggregate → populate): после извлечения
  требований AI hub получает полный список ФТ/НФТ и карту архива и возвращает дерево
  `{type, name, parentName|null}` — корневые группы-разделы и дети под ними, как в
  эталонном проекте Jenkins. Родитель из structure-ответа перекрывает parentName из
  extraction (structure видит весь набор целиком). Иерархия — только внутри одного типа
  (FUNCTION под FUNCTION, NFR под NFR). Батчи по 100 записей; если после 3 попыток батч
  не разобран — warn «записи останутся корневыми», импорт продолжается плоско (job не
  фейлится: требования важнее дерева).
- **Поле «Источник» больше не заполняется.** Это бизнес-поле (кто запрашивал ФТ/НФТ);
  имена файлов первоисточника туда не пишутся. Провенанс (`source` в extraction-ответе)

## 2026-07-05 — AI-импорт: фикс «В архиве нет файлов документации» на реальных архивах

### Причина
Распаковка передавала имена записей архива в защиту от zip-slip как есть. Архивы, где
записи хранятся с абсолютными путями (`/documentation/…/index.md`), Windows-разделителями
(`docs\…`) или префиксом диска (`C:\…`), **молча** теряли все записи как «небезопасные» —
пользователь получал «В архиве нет файлов документации», хотя .md в архиве были.

### Исправлено
- Имена записей нормализуются перед проверкой (`\`→`/`, срез ведущих `/`, `./` и `C:`),
  такие архивы теперь распаковываются в свою относительную структуру. Защита от zip-slip
  не ослаблена: сегменты `..` по-прежнему отклоняются (закреплено тестами).
- macOS-мусор Finder-архивов (`__MACOSX/`, AppleDouble `._*.md`) больше не считается
  документацией и не уходит мусором в модель.
- Ошибка «нет файлов документации» стала диагностичной: показывает, сколько файлов в
  архиве и какие расширения найдены («В архиве 120 файлов: .html — 100, .png — 15…»),
  отдельно — счётчик записей, пропущенных как небезопасные; пустой архив — «Архив пуст».

### Тесты
- Unit: 992 зелёных (+12: абсолютные пути, backslash-zip и -tar, `C:\`-префикс,
  `__MACOSX`/`._*`, диагностика расширений, пустой архив, `..` остаётся заблокирован).

## 2026-07-04 — Интеграция с AI Hub

### Экран «AI» (пункт меню слева)
- Новый пункт меню «AI» (иконка-искра) в боковой панели — виден для любого открытого проекта,
  ведёт на экран `/p/:id/ai`.
- Экран из 2 частей: слева — подключение к AI Hub (API-ключ, Base URL, выбор модели из списка),
  справа — пошаговая инструкция по подключению (авторизация → API-ключ → Base URL → список
  моделей → первый запрос) со ссылкой на hub.ai.sbt и примером кода.
- **Хранение настроек (гибрид):** API-ключ и Base URL — глобально (персональный набор на
  пользователя); выбранная модель — per-project. Ключ хранится в локальном `.ai-config.json`
  (в `.gitignore`), в UI маскируется, наружу (в API) в открытом виде не отдаётся и не логируется.
- Список моделей подтягивается из AI Hub; при недоступности — ручной ввод model id.

### Генерация описания требования (AI Hub generation)
- В форме создания/редактирования требования у поля «Описание» — кнопка «AI Hub generation»:
  запрос в AI Hub → **превью** → «Отменить» / «Применить». «Применить» добавляет описание в конец
  текущего с новой строки (не затирая введённое). Без настроенного ключа/модели кнопка неактивна
  и ведёт на экран «AI».
- В запрос передаётся контекст требования (имя, тип, критичность, текущее описание, имя проекта) +
  опциональная подсказка пользователя. Промпт спроектирован по best practices инженерии требований:
  явные критерии качества (недвусмысленность, понятность, корректность, проверяемость), стиль
  портала, few-shot, запрет на выдумывание фактов сверх контекста; вывод на русском.

### API (AI Hub, OpenAI-совместимый)
- `GET /api/ai/config` (ключ не отдаётся — только `hasApiKey`), `PUT /api/ai/config`,
  `GET /api/ai/models`, `POST /api/ai/generate-description`.
- Клиент — обёртка над `openai` SDK; `baseURL` берётся из конфига. Зависимость `openai` добавлена
  на сервер.

### Безопасность
- API-ключ наружу не отдаётся и не логируется; ошибки апстрима санитизируются (ключ вырезается).
  `baseURL` валидируется как URL. Приложение локальное однопользовательское — SSRF-риск от
  пользовательского `baseURL` (свой же хост) принимается осознанно.

### Подключение за корпоративным CA / прокси (исправление)
AI Hub (`api.ai.sbt`) часто закрыт внутренним корпоративным CA, которому доверяет ОС/`curl`, но
не Node (его `fetch`/undici) — из-за чего сохранение/загрузка моделей падали с 502 «Connection
error.». Настройка TLS/прокси вынесена в env и применяется **только** к клиенту AI Hub (не
глобально), к обеим операциям — списку моделей и генерации описания:
- **По умолчанию проверка TLS для AI Hub отключена** (scoped только на AI Hub, не глобально) —
  чтобы работало «из коробки» за внутренним CA. Это осознанный временный дефолт; ужесточить —
  задать `AI_HUB_INSECURE_TLS=0` или указать `AI_HUB_CA_CERT`.
- `AI_HUB_CA_CERT=/путь/к/ca.pem` — доверять корпоративному корневому CA (безопасный вариант;
  автоматически включает проверку). Эквивалент штатного `NODE_EXTRA_CA_CERTS` тоже работает.
- `AI_HUB_INSECURE_TLS=0` — принудительно ВКЛЮЧИТЬ проверку TLS для AI Hub.
- `AI_HUB_PROXY` / `HTTPS_PROXY` — ходить в AI Hub через HTTP(S)-прокси (Node `fetch` не читает
  прокси-переменные сам).
Плюс сообщение об ошибке 502 теперь показывает всю цепочку причин (напр.
`… ← unable to verify the first certificate (UNABLE_TO_VERIFY_LEAF_SIGNATURE)`) с вырезанным ключом.

## 2026-07-03 — Экспорт: группировка фильтров + выбор данных для выгрузки

### Экраны выбора требований (экспорт и TaskTracker)
- Фильтры на экранах «Выбор требований для экспорта» и «Выбор ФТ/НФТ для TaskTracker» (общий
  компонент `RequirementPickerModal`) разбиты на **именованные группы**: «Критичность»,
  «Реализация», «Источник», и отдельная группа «Выбор» («Выбрать все / Снять выделение» + счётчик).
- Фильтр по «Источник» теперь **кейс-инсенситивный**: значения, отличающиеся только регистром
  (напр. «АС21» и «ас21»), считаются одним значением и группируются в один чип.

### Экран «Формат выгрузки» — выбор данных для выгрузки
- Добавлен блок «Данные для выгрузки» из двух групп чекбоксов:
  - **Обязательные данные** (всегда включены, снять нельзя): Название, Критичность, Статус реализации.
  - **Дополнительные данные** (переключаемые, по умолчанию все включены): Источник требования,
    Описание, Справочная информация, Связи.
- Выбор данных влияет на **содержание всех трёх форматов** (Excel `.xlsx`, `.zip`, `.tar.gz`):
  - **Excel**: динамический набор колонок. По умолчанию 8 колонок
    (Требование · Тип · Критичность · Реализация · Источник · Описание · Справочная информация · Связи);
    ранее было 6 (без Источника и Справочной информации). Справочная информация выводится многострочно
    «тип: значение»; заливка критичности и отступ по дереву сохранены.
  - **OpenSpec-архивы (`.zip`/`.tar.gz`)**: `.md` требования содержит только выбранные секции
    (`- source`, тело описания + `#### Scenario`, `#### Info`, `#### Links`). Обязательные поля и
    техническое `createdAt`/`updatedAt` присутствуют всегда; пустые опциональные секции не выводятся.
- **Превью-подсказка**: по текущему выбору показывает, какие колонки Excel и секции OpenSpec попадут
  в выгрузку.
- **Обратная совместимость / round-trip**: при выбранных всех полях выгрузка байт-в-байт совпадает с
  прежней (лосслесс). Отфильтрованный архив — «выгрузка для чтения»: он валидно импортируется, но
  снятые данные в него не попадают.

### Excel учитывает выбор требований
- Excel-выгрузка теперь **учитывает выбор конкретных требований** (шаг 1 модалки), как и архивы:
  при подмножестве в `.xlsx` попадают только выбранные требования; при выбранных всех — весь проект.
  Ранее `.xlsx` игнорировал выбор требований и всегда выгружал проект целиком.

### API
- Единый контракт полей в `@po/core`: `EXPORT_OPTIONAL_FIELDS`, `parseExportFields`,
  `serialize(req, { fields })`.
- Endpoints принимают выбор полей: `GET /api/projects/:id/export?...&fields=...`,
  `POST /api/projects/:id/export/selected` (`fields` в теле), `GET /api/projects/:id/export.xlsx?fields=...`.
  Параметр `fields` отсутствует ⇒ все поля; пустой ⇒ минимум (только обязательные).
- `POST /api/projects/:id/export/selected` теперь принимает `format: 'xlsx' | 'zip' | 'targz'`:
  при `xlsx` возвращает книгу только с выбранными требованиями. `GET /export.xlsx` (весь проект)
  сохранён для случая «выбраны все».
